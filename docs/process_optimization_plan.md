# 流程优化方向分析（v3.7.8 规划）

> 结论先行：**硬件层面（CPU 单核/多核、GPU 内核）已经贴近上限**；综合效率的差距集中在
> 「命中记录路径」与「扫描/匹配两段串行」这两处流程问题上。

## 一、并行度已到 SMT 天花板（不是瓶颈）

`tools/opt_probe23.cpp`，Java 8192²（6710 万锚点），同机 6C/12T：

| 场景 | 1 线程 | 12 线程 | 加速比 |
|---|---|---|---|
| 密度 g=2 thr=0.5（命中 351 万） | 250.0 ms | 48.1 ms | 5.2× |
| 密度 g=5 thr=0.3（命中 15.3 万） | 130.2 ms | 25.9 ms | 5.0× |
| 密度 g=5 thr=1.0（命中 0） | 86.3 ms | 15.3 ms | 5.6× |

6 物理核 + 超线程的理论上限约 7~8×，实测 5~5.6× ⇒ **线程数再堆也不会明显变好**。

## 二、真正的瓶颈：命中记录路径（每次命中约 150 ns）

对照实验（同一张位图，只有命中数不同）：

| 场景 | 匹配耗时 | 命中数 | 每次命中成本 |
|---|---|---|---|
| g=5 thr=1.0（全绿才命中） | 3.0 ms | 0 | —（0.045 ns/锚点） |
| g=5 thr=0.3 | 14 ms | 15.3 万 | ~100 ns |
| g=2 thr=0.5 | 36.5 ms | 351 万 | **~125 ns** |

命中为 0 时匹配只要 3 ms（67M 锚点 = 0.045 ns/锚点，已到 ALU 极限）；
一旦命中变多，匹配时间几乎与命中数成正比 ⇒ **成本在 `recordMatchAt`，不在窗口计数**。

`recordMatchAt` 每次命中要做：`std::hypot`（≈30~40 周期）、构造 `MatchResult`、
堆插入（`Scored` 含 40+ 字节，6 次比较与搬移）、以及**一次全局原子自增** `bumpLiveMatches()`。
12 线程同时打同一个原子变量 ⇒ 缓存行来回弹，是 125 ns 的主要来源。

## 三、第二瓶颈：扫描与匹配完全串行

引擎流程是「整幅扫描 → 整幅匹配」两段，互不重叠：

| 场景 | 总耗时 | 扫描 | 匹配 | 匹配占比 |
|---|---|---|---|---|
| Java 8192² g=2 thr=0.5 | 48.1 ms | 11.6 ms | 36.5 ms | 76% |
| Java 8192² g=5 thr=0.3 | 25.9 ms | 11.4 ms | 14.5 ms | 56% |
| Java 8192² g=5 thr=1.0 | 15.3 ms | 12.3 ms | 3.0 ms | 20% |
| 基岩 4096² g=2 thr=0.5 | 70.0 ms | 58.1 ms | 11.9 ms | 17% |

GPU 路径更明显：GPU 扫描 7~8 ms 后，CPU 才开始匹配 ⇒ GPU 在匹配阶段完全空转。

## 四、主攻方向（按收益/成本排序）

### P1 命中记录路径重写（预期 2~3×，命中密集场景）
1. `hypot` → 直接比较平方距离（只在最终结果里开方，或按需开方）；
2. 全局原子计数改为线程本地计数 + 每 1024 次批量提交；
3. `MatchResult` 延迟构造：先判「能否进堆」，能进才构造；
4. 命中密集时用线程本地候选池 + 结束后 partial_sort，替代逐次堆操作。

### P2 扫描/匹配流水线重叠（预期省 15~25%）
按瓦片流水：GPU（或 CPU 扫描线程）扫第 N+1 块时，另一组线程匹配第 N 块的行带，
匹配结果直接进各自线程本地堆。基线已有 GPU 双缓冲流水线（v3.7.2），把它从
「扫描 + 集成」扩展成「扫描 + 集成 + 匹配」。

### P3 自适应路由（避免 3× 的负优化）
实测 Java GPU 固定开销约 0.3~0.5 ms、峰值 247 亿区块/秒、CPU 12 线程 57 亿：
**临界点 ≈ 3000 万区块**。低于它 Java 应走 CPU；基岩临界点仅 ≈ 12 万区块，
几乎总是 GPU 更快。目前只有「全局开关」，没有按版本/规模自动选择。

### P4 参数复算复用（交互场景 3~10×）
用户改阈值/图案再搜同一区域时，位图不变 ⇒ 只重跑匹配、跳过扫描。
当前每次搜索都从头扫。

### P5 GPU 固定开销合并
多瓦片单次派发、设备缓冲复用（前缀表已常驻）、集成与匹配并行。

## 五、不打算再投入的方向（已证上限）

- CPU 扫描内核（Java 0.84 ns/区块、基岩 24.5 ns/区块，均在乘法端口上限附近）；
- 严格匹配与 k=g² 密度快路（已到「每 64 锚点一次字操作」量级）；
- 线程数/亲和性（SMT 天花板已到）；
- GPU 内核指令级微调（本轮 5 个实验全部无收益或 <5%）。

## 六、3.8.0 已落地（P1 + P3）与实测

### 6.1 P1 命中记录路径重写
1. 用「2×偏移的整数平方距离」先判断能否进榜，不行就直接返回（不算 hypot、不构造结果、不动堆）；
2. `hypot` 换成 `0.5*sqrt(整数平方距离)`，且只在真正入堆时算；
3. 实时命中计数由「每次命中一个全局原子」改为线程本地累加 + 每 4096 次批量提交；
4. 命中密集时用「精确整数门限」替掉 ±2 浮点带：由浮点判定反解出等价的整数阈值，
   SIMD 掩码只产出真命中（原来 34% 的锚点都要进一遍浮点判定，现在只走 5% 的真命中）。

### 6.2 P3 GPU 自适应路由
按版本给不同门槛（Java 3000 万区块、基岩 9.6 万区块），低于门槛自动 CPU。

### 6.3 实测（引擎级完整搜索）

|---|---|---|---|
| Java 8192² 密度 g=2 thr=0.5 · CPU 12 线程 | 48.8 ms | **28.3 ms** | 1.72× |
| Java 8192² 密度 g=2 thr=0.5 · GPU | 42.6 ms | **21.8 ms** | 1.95× |
| 基岩 4096² 密度 g=2 thr=0.5 · CPU 12 线程 | 62.3 ms | **56.3 ms** | 1.11× |

多段构建会出现「扫了 1.4 亿区块却一条缓存都没写」（GUI 自检捕获）。

### 6.5 下一版（3.8.1）待办

- P4 参数复算复用（改阈值/图案只重跑匹配）；
- P1 剩余：命中密集时线程本地候选池 + 结束一次性 partial_sort（当前仍逐次堆操作）。

## 七、GPU 流式匹配探针验证（2026-11-07，v3.9.0 前置）

### 7.1 两个探针

**探针 A（`tools/opt_probe24.cpp`）：只看内核形态**
区域 1.34 亿区块，只算判定、不回读：

| 形态 | 吞吐 |
|---|---|
| V1 每 item 1 区块（输出 uchar） | 537.9 亿区块/秒 |
| V2 每 item 8 区块（输出 uchar） | 1070.3 亿区块/秒 |
| **V3 每 item 64 区块（ulong，= 产品实现）** | **1226.3 亿区块/秒** |
| V4 每 item 64 区块（纯 32 位改写） | 900.5 亿区块/秒（更慢，说明现写法已最优） |

**结论**：内核本身完全不慢——**1226 亿区块/秒**，是引擎级 96 亿的 12.8 倍。
之前的 96 亿/秒是「回读 + 集成 + 派发」这些**流程成本**吃掉的。

**探针 B（`tools/opt_probe25.cpp`）：全 GPU 流式匹配**
work-group 内建共享位图（256×32 区块），GPU 内完成「判定 → g×g 窗口计数 → 只回写命中」，
不回传位图、CPU 不参与匹配：

| 项目 | 结果 |
|---|---|
| 正确性（2048×1024，g=5 阈值 8） | CPU 命中 4740，GPU 命中 4740，**逐项一致** |
| 吞吐（8192² = 6710 万区块，g=5） | **454.5 亿区块/秒**（含判定 + 窗口统计 + 命中回写） |

### 7.2 与现状、社区的对照

| 指标 | 数值 |
|---|---|
| 现引擎 GPU 扫描（含回读+集成） | 96 亿/秒 |
| 现引擎 GPU 全搜索（扫描+CPU 匹配） | 约 32 亿/秒 |
| **流式探针（全 GPU）** | **454.5 亿/秒** |
| 社区工具（归一化到本机） | 约 870 亿/秒 |

⇒ 流式方案能立刻把引擎级效率提高 **5.5 倍**（对全搜索是 14 倍），
达到社区归一化值的 **52%**（用户说的「接近社区一半」正好对上）。

### 7.3 流程影响（落地前必须处理）

1. **结果语义**：流式内核回来的命中是**无序**的，必须按与现实现完全相同的
   (距离, rank) 规则排序、去重（严格模式跨变体去重）、并统计 totalFound；
2. **取消与进度**：按瓦片派发天然支持取消（每瓦片检查一次），进度按「已派发瓦片/总瓦片」上报；
3. **缓存（useCache / buildMode）**：现有缓存是「逐区块位图 + 覆盖声明」，
   流式内核没有位图 ⇒ 有缓存参与时必须回退位图路径（同 v3.8.0 的构建模式处理）；
4. **热力图/扫描覆盖率**：UI 这些展示依赖位图，流式路径需要按需懒生成或改用「命中密度」口径；
5. **命中数量上限**：阈值很低时命中可能是天文数字（如阈值 0 ⇒ 每个锚点都命中），
   必须分批回写 + 上限保护（探针用的是 400 万条上限）；
6. **基岩版**：同一套流式框架可复用，但每区块 396 步链的计算量不变，收益主要来自去掉回读。

### 7.4 建议落地顺序（3.9.0）

1. 先把流式内核做成**可选快路径**（仅密度模式、无缓存、无热力图时启用），CPU 路径原样保留；
2. 用现有 117 项参考 + GUI 自检做逐项一致性验证（顺序、去重、计数）；
3. 再逐步放开：严格图案模式 → 缓存参与场景 → 基岩版。

## 八、3.8.1 落地：全 GPU 流式匹配（2026-11-07）

把探针 B 的方案正式接进产品，作为「密度模式」的 GPU 快路径：

- 新增内核 `density_stream`（work-group 内建共享位图 → 组内按锚点分区求窗口计数 → 只回写命中）；
- 新增会话方法 `GpuSession::matchDensityStream`（Z 分带派发、带间可取消、命中上限保护）；
- 适配器实现 `matchDensity`，引擎侧 **零改动**（原有 GPU 密度匹配入口一直在等这个实现）；
- 命中过多（默认 >20 万）自动回退 CPU，保证结果语义不变；
- GPU 结果入榜前用整数平方距离剪枝，命中密集时不再逐条 `hypot` + 堆操作。

### 实测（CPU 12 线程 vs GPU 流式，同一进程内对跑）

| 场景（密度 g=5 thr=0.5，稀疏命中） | CPU 总 | GPU 流式总 | 加速 | 命中一致 |
|---|---|---|---|---|
| Java 16384²（2.68 亿区块） | 67.72 ms | **8.98 ms** | **7.5×** | 58 = 58 |
| Java 32768²（10.7 亿区块） | 252.64 ms | **27.98 ms** | **9.0×** | 240 = 240 |
| 基岩 16384²（2.68 亿区块） | 782.90 ms | **152.86 ms** | **5.1×** | 21 = 21 |

换算：Java 32768² 的 **384 亿区块/秒**（此前引擎级约 32 亿，提升 12 倍），
达到社区归一化值（约 870 亿）的 **44%**。

### 已知边界

- 命中密集（>20 万）时回退 CPU：此时瓶颈变成「命中搬运 + CPU 入榜」；
- 严格图案模式、带缓存/构建模式仍走原路径（缓存需要位图与覆盖声明）；
- 热力图/扫描覆盖率仍依赖位图路径（流式模式不产生位图）。

### 下一版（3.8.2 候选）

1. 流式结果直接在 GPU 侧做「近似 top-N 预筛」，进一步压命中搬运；
2. 严格图案的流式化（用图案行掩码在共享位图上做位并行匹配）；
3. P2：扫描/匹配流水线重叠（对非流式路径仍然有效）。

## 九、3.8.2：内核微优化（A1 否证、除法消除采纳）

### 9.1 A1「可分离卷积」被实测否证
把「每锚点 g 次两字 popcount」换成「先算每行 g 连加（写共享内存）+ 锚点只做 g 次加」：

| 版本 | 流式内核吞吐 |
|---|---|
| 除法消除版（基线） | 493 亿区块/秒 |
| 可分离卷积版 | 460 亿区块/秒（**更慢**） |

原因：共享内存写读 + 额外屏障的成本超过省下的 popcount。**不再走这条**。

### 9.2 除法消除（采纳，进产品）
GPU 的整数除法是软件模拟（几十条指令）。锚点遍历原来每锚点两次除法，
改成「按行嵌套 + 行内跨步」后：

| | 探针吞吐 |
|---|---|
| 改前 | 457 亿区块/秒 |
| 改后 | **493 亿区块/秒（+7.7%）** |

产品内核同步更新，回归验证全部通过。

### 9.3 现状与下一步

- 产品级流式（Java 32768²，10.7 亿区块）：**~28 ms ≈ 384 亿区块/秒**；
- 探针级流式内核：**493 亿区块/秒**；
- 探针级纯判定内核：**1226 亿区块/秒**；
- 瓶颈已从「回读/匹配」转到「每区块判定指令数（≈45）」与「线程/屏障开销」。

下一步候选（按实测可能性排序）：
1. 判定阶段「增量尾项」：x 的二次项用差分递推（3 次加法替代 3 次乘法），预期 1.2~1.4×；
2. 更大 tile + 减少屏障次数，预期 1.15×；
3. 命中密集时的 GPU 侧预筛（当前 >20 万直接回退 CPU）。

## 十、3.8.3：判定增量递推（采纳）

Java 判定的 x 尾项是 x 的二次式，可以用差分递推把「每区块 3 次乘法」换成「3 次加法」：
  t1(x) = (x^2)·4987142，t2(x) = x·5947611
  t1(x+1) = t1(x) + d(x)，d(x+1) = d(x) + 2·4987142，t2(x+1) = t2(x) + 5947611
再把 64 位状态拆成两个 uint32（含符号扩展的进位/借位修正），LCG 乘法保持 32×32→64。

| 版本 | 纯判定内核吞吐 | 校验 |
|---|---|---|
| 旧（每区块 3 次乘法） | 1226.9 亿区块/秒 | — |
| **新（差分递推）** | **1355.6 亿区块/秒（+10.5%）** | 32768 个字逐位比对，0 处不同 |

已同步进产品（scan_java_words 与 density_stream 两处），
全量一致性比对（Java 4096×1024×4、基岩 1024×1024）与 117 项参考全部通过。

另：分带派发从 1024 行加到 4096 行**无收益**（28.12 vs 28.10 ms），已回退——
说明产品级流式的瓶颈不在派发次数。

## 十二、否证记录：两个「看起来该有收益」的微优化（2026-11-07）

在 3.8.3 之后又试了两个常见方向，**实测都没有收益，均已回退**（记下来避免重复投入）：

| 实验 | 做法 | 结果 |
|---|---|---|
| 流式缓冲常驻复用 | 把 `matchDensityStream` 每次新建的 3 个 cl_mem 改成会话内常驻 | Java 32768²：28.25 vs 28.21 ms（**无差异**），且常驻会多占最多 48 MB 显存 ⇒ 回退 |
| tile 加高（32→128 行） | 共享位图 4 KB、每线程 4 个字、边界浪费从 14% 降到 5% | Java 32768²：28.08 vs 28.21 ms（**噪声级**）⇒ 回退 |

结论：产品级流式路径当前瓶颈**不在**缓冲分配、也不在 tile 形状/屏障次数，
而是「每区块判定指令数」和「命中处理」。这两个方向已到当前架构的性价比边界。

## 十三、继续突破需要换层级（候选）

1. **GPU 侧 top-N 预筛**（补命中密集空洞）：GPU 内先按距离做两遍/直方图筛选，
   只回传可能进榜的命中 ⇒ 命中 >20 万时也能走流式，而不是回退 CPU；
2. **严格图案流式化**：图案行掩码在共享位图上做位并行匹配，覆盖目前完全走 CPU 的场景；
3. **判定再瘦身**：把 48 位 LCG 进一步拆成两段 32 位运算、去掉每次的 48 位掩码（预期 10~15%）。

这三项都不是「调参」，而是需要改数据流/内核结构的活，适合下一轮集中做。

## 十四、判定内核形态扫描（probe24 六种写法，2026-11-07）

把「每 work-item 处理多少区块」与「判定式怎么写」系统扫了一遍（同区域 1.34 亿区块、只算判定）：

| 写法 | 吞吐 | 结论 |
|---|---|---|
| V1 每 item 1 区块（uchar） | 538 亿/秒 | 写放大太重 |
| V2 每 item 8 区块（uchar） | 1069 亿/秒 | 接近 |
| V3 每 item 64 区块（ulong，原产品写法） | 1224 亿/秒 | 基准 |
| V4 纯 32 位改写（每区块重算尾项） | 897 亿/秒 | 更慢 |
| **V5 差分递推尾项** | **1361 亿/秒** | **最优（已进产品，3.8.3）** |
| V6 差分递推 + 去 48 位掩码/64 位合成 | 1171 亿/秒 | **更慢，否证** |

要点：编译器对 64 位掩码/合成已优化得很好，手工拆成两段 32 位反而增加指令；
**判定内核的最优形态就是 V5（每 item 64 区块 + 差分递推）**，已到该写法的上限。

## 十五、结论：内核层面已无廉价收益，剩余空间在结构

到此为止，以下方向**全部实测过**：
- 判定写法（6 种形态、增量递推、32 位拆分）→ 最优 V5，已进产品；
- 匹配阶段（可分离卷积、两字 popcount、锚点除法消除、tile 高度/宽度、缓冲复用、分带大小）；
- 派发/屏障/缓冲/尺寸类调参。

剩余待做的都是**结构级**改动：
1. **GPU 侧 top-N 预筛**（命中密集场景，当前 >20 万命中直接回退 CPU）；
2. **严格图案流式化**（图案模式目前完全走 CPU 位图路径）；
3. **多流/多队列并发**（把多个瓦片同时排进队列，压 GPU 空闲间隙）。

## 十六、三个候选方向的快速可行性测试（2026-11-07）

### 16.1 多命令队列并发 —— 否证
把同一批重活（210 万个 work-item，每个 2×396 步链）分别排到 1/2/3/4 个 command queue：

| 队列数 | 耗时 |
|---|---|
| 1 | **2.07 ms** |
| 2 | 2.16 ms |
| 3 | 6.93 ms（抖动） |
| 4 | 2.31 ms |

单次派发已经吃满 GPU，多队列**没有收益**（甚至因争用变慢）⇒ 不做。

### 16.2 命中回写成本 —— 内核侧不是瓶颈，宿主侧才是
同一内核在稀疏（g=5 thr=8）与密集（g=2 thr=2，命中约 350 万）下的吞吐：

| 配置 | 吞吐 |
|---|---|
| g=5 thr=8（稀疏） | 462 亿区块/秒 |
| g=2 thr=2（密集，350 万命中） | **497 亿区块/秒** |
| g=5 thr=2（更密） | 434 亿区块/秒 |

⇒ 命中回写对内核吞吐几乎无影响。
但把产品级「命中上限」从 20 万放宽到 400 万后端到端**反而崩溃式变慢**（Java 8192² 530 ms）
且结果出现偏差 ⇒ 说明瓶颈在「宿主侧 350 万个命中的结果构造 + 入榜」，
而不是 GPU；也说明密集命中场景的正确性边界还没打磨好。

**结论：保持 20 万上限（已验证路径不变），密集命中继续走 CPU。**

### 16.3 严格图案流式化 —— 本轮未测（留待下轮）
需要新内核（图案行掩码在共享位图上做位并行匹配），改动量比前两项大，本轮时间不够。

### 16.4 本轮净结论
三个候选里：多队列否证、命中回写没问题但宿主侧是瓶颈、图案流式未测。
**产品代码本轮无改动（仍是已验证的 3.8.3）**，避免为无收益改动引入风险。

## 十七、严格图案流式化 —— 可行性测试通过（大收益）

探针 `tools/opt_probe27.cpp`：在共享位图上按图案行掩码做位并行 AND，只回传命中。
以最典型的「5×5 全绿」验证：

| 项目 | 结果 |
|---|---|
| 正确性（1024×512） | CPU 命中 0、GPU 命中 0，一致（该区域 5×5 全绿概率极低） |
| 吞吐（8192² = 6710 万区块） | **797.7 亿区块/秒**（含判定 + 图案匹配 + 命中回写） |

与产品当前图案路径对比：

| 路径 | 效率 |
|---|---|
| 产品·严格 2×2 2000²（扫描+匹配） | 约 18 亿区块/秒 |
| 产品·严格 2×2 4000² 精确 | 约 64 亿区块/秒 |
| **图案流式探针** | **797.7 亿区块/秒** |

⇒ 图案搜索有 **12~44 倍**的潜在提升空间，是目前剩下最大的一块。

### 落地要点（下一版）

1. 引擎侧新增「图案流式」入口，条件：图案模式 + 非加权 + 无缓存 + 区域足够大；
2. **旋转变体**：引擎目前会评估 4/8 个旋转变体（方向锁定时除外），内核需按变体循环
   （每个变体一组行掩码），或按变体分别派发再合并；
3. 结果仍需按 (距离, rank) 排序、去重、计数，与 CPU 路径逐项一致；
4. 命中上限与回退策略沿用密度流式的做法（超限或异常回退 CPU）。

### 18.3 从未尝试过的方向（按可行性排序）

| 方向 | 说明 | 预计收益 |

## 二十、密集命中：宿主侧裁剪实验 —— 否证（需要 GPU 侧预筛）

思路：命中可能上百万，先按整数距离在**宿主侧**筛出「最可能进榜」的候选，再构造 MatchResult。
已实现（`DensityMatchParams` 增加 `startX/startZ/keepCandidates/outTotalFound`，
适配器用 `nth_element` 取最近 keep 条；引擎用 `outTotalFound` 还原命中总数）。

实测（Java 8192²，g=2，阈值 0.5，351 万命中）：

| 阶段 | 裁剪前 | 裁剪后 |
|---|---|---|
| 结果转换+入堆（引擎侧） | 17.57 ms | **0.07 ms** |
| matchDensity（GPU + 回读 + 适配器筛选） | 59.17 ms | **64.21 ms** |
| 合计 | 76.7 ms | 64.7 ms（CPU 路径 28.6 ms） |

结论：**宿主侧裁剪不解决问题**。命中回读 28 MB（约 3 ms）+ 对 351 万条算距离
+ `nth_element`（约 20~30 ms）已经超过收益；瓶颈是「把 350 万条命中搬到主机」本身。

⇒ 要让密集命中走 GPU，必须**在 GPU 内完成筛选**（直方图两遍：先统计距离分布定阈值，
再只回写阈值内的命中）。宿主侧这套参数与 totalFound 回传保留（无害，且是 GPU 预筛的基础设施），
默认仍按 20 万上限回退 CPU。
