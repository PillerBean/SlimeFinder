## 二、步骤 0：F-1 自检截图豆腐块

**根因**：自检在 `QT_QPA_PLATFORM=offscreen` 下运行，而 offscreen 平台走 FreeType 字体引擎、**必须有字体目录**；
未设置时任何文字都渲染成 □（自 v3.3.4 起交付的截图都不可读，UI 文案问题因此长期未被自查发现）。

**修复**：
1. `src/main.cpp`：创建 `QApplication` 之前，若平台为 offscreen/minimal 且未设置 `QT_QPA_FONTDIR`，
   自动指向 `%WINDIR%\Fonts`（不覆盖用户显式设置），并打印一行启动说明；
2. `scripts/verify_release.ps1`：GUI 自检前显式设置该变量（双保险）；
3. 新增断言（`src/gui/MainWindow.cpp` 13.9 + 16.1）：
   * `QFontMetrics::inFont()` 检查中文/数字字形（缺字形时返回 false，实测豆腐块环境全为 0）；
   * 截图墨迹**列宽种类** ≥5（真实文字 17~18，豆腐块 1~3）+ 墨迹占比 >0.5%；
   * 落盘截图（`SLIME_SHOT` 指定时）重新加载后再测一次。

**验证**（双向）：
```
正向（不设置 QT_QPA_FONTDIR）：exit=0，37 张截图，[UI自检] 截图可读性：墨迹列宽种类=17
负向（QT_QPA_FONTDIR=C:\__no_such_font_dir__）：exit=1
      [UI自检 FAIL] 字体含中文/数字字形（QFontMetrics::inFont；缺字形=截图豆腐块）
```
肉眼抽检：新截图菜单/工具栏/进度行/状态栏文字全部可读（`docs/screenshots/v3372/`）。

## 三、步骤 1：P0-A 四项 UI

### 1.1 顶部两个百分比
`MainWindow::buildUi()` 中 `m_w->progress->setTextVisible(false)`（默认 `textVisible=true`、格式 `%p%`，
而右侧还有自建 `progressPercent` 标签 ⇒ 用户截图里的「25% 25%」）。
**证据**：同一次渲染比较 —— 开启内置文字时进度行墨迹 **540** 像素，关闭后 **475** 像素（差 65 = 重复绘制的那个百分比）；
断言「进度行内形如 `NN%` 的标签数量 == 1」。

### 1.2 分母同源（>100% 的根因）
用户 439.8 亿真实几何（**开缓存**时 `collectCacheChunks` 把分块上限压到 250 万 words ⇒ **277 块**）：

| 量 | 值 |
|---|---|
| 引擎 `totalEvals = 277 块几何的 totalDataEvals × W` | **44,211,486,052** |
| GUI 旧分母 `area = 209715²` | 43,980,381,225 |
| 旧口径最大百分比 | 100.53%（截图 2 里的 `100.5%`、分子 44,211,906,585 可由此精确复现） |

**修复**：`SearchOptions::liveTotal`（引擎在计划确定后立即写入）+ `SearchTask` 持有 + GUI 统一取用
（状态栏统计、进度流水、关键信息日志、完成态全用同一分母）；百分比显示层再夹到 ≤100%。

**验证**（439 亿实跑）：
```
[UI自检] 扫描中：进度行=5% / 状态栏=扫描 2220032404/44211486052 区块（5.0%） ｜ 速度 8392.0 万/秒 ｜ 找到 0 个
[UI自检] 完成后状态栏：搜索完成：共 0 条（显示 0 条）｜ 扫描 44211486052/44211486052 区块（100.0%） ｜ 找到 0 个
[UI自检] 日志汇总：search.summary chunks=277 ... scanned=44211486052/44211486052 ...
```
→ 进度行与状态栏**同源同值**、百分比恒 ≤100%、完成态 100.0% 且与日志一致。

### 1.3 状态栏拼接与死写
* 删除「扫描完成，正在匹配图案…」这类**阶段短语**写进状态栏临时消息的做法（阶段只由进度行 `progressStage` 表达）；
* 新增分隔符标签（仅当存在临时消息时可见），杜绝「扫描完成，正在匹配图案扫描 11265898000/…」这类拼句；
* 删除完成态对 `progressInfo` 的**死写**（旧代码先写一句、几行后立刻被覆盖）；
* `progressInfo` 初值改为「尚未开始搜索」（原来与临时消息「就绪」重复显示两次）。

### 1.4 阶段文案按模式分派
`progressStageName(int stage, slime::Mode mode, slime::Algorithm alg)`；运行模式在 `startSearch()` 时捕获
（避免用户中途改界面导致文案与真实行为不符）；调用点（进度行、取消、出错、排序、完成）全部改为同一口径。

| 阶段 | 严格 | 密度 | 快速估算 |
|---|---|---|---|
| 扫描 | 正在扫描区块… | 正在扫描区块… | 正在扫描区块… |
| 切换 | 扫描完成，正在匹配图案… | 扫描完成，正在匹配密度… | 扫描完成，正在估算… |
| 进行中 | 正在匹配图案… | 正在匹配密度… | 正在估算… |

**验证**：自检 13.5 断言三条文案；实跑匹配阶段 `阶段=正在匹配密度…`（不含「图案」）✓

## 五、步骤 3：P0-C 缓存摊还归并 / 剪枝（含准入控制）

**三个改动**：
1. **摊还归并**：增量先攒进批次（16M 条目 / 4 块），一次 `mergeRaw` 合并多个区域；归并改在**独立的 `cacheMu`** 下进行，不再占用主互斥 `mu`；
2. **批量剪枝**：`CacheManager::pruneToFit` 先按面积估算需要丢几个最旧 range，一次删除后**只做一遍**过滤
   （旧实现每丢 1 个 range 就整表过滤一次，O(N×R)）；至少保留 1 个 range，估算不收敛时回退精确逐个丢弃；
   分块路径剪到**低水位**（预算 90%），避免临界区反复触发；
3. **准入控制**：当已收集条目超过「预算可容纳条目数（预算/8）」时，后续分块**只读缓存、不再收集**
   （也不再登记其范围，覆盖声明保持正确），并写 `cache.admit` 日志。

**439.8 亿同参数 A/B（同机、同参数、空缓存起跑、0 结果）**：

| 指标 | 改前（= v3.3.7 行为） | 改后（v3.3.7.2） | 变化 |
|---|---|---|---|
| 墙钟总耗时 | **837.3 s** | **444.8 s** | **1.88× 更快** |
| 缓存归并累计 / 次数 | 521.6 s / 277 次 | **12.3 s / 5 次** | 42× / 55× |
| 剪枝累计 / 丢弃 | 294.8 s / 269 个 range | **0.96 s / 2 个 range** | 307× |
| CPU 平均（12 线程） | 718.3%（**60%**） | **1095.3%（91%）** | ✓ |
| 内存峰值 | 3777 MB | **2336 MB** | −38% |
| 扫描计数 | 44,211,486,052 | 44,211,486,052（一致） | ✓ |
| 结果 | 0 条 | 0 条（一致） | ✓ |

**正确性**：单元 19 组全绿（含 `[10]` 缓存剪枝语义、`[19]` 分块提前停止 + 逐位一致）；严格模式 111/111 见 §七。

## 六、步骤 4：P0-B 性能复测与 F-4

**日志定位（改前）**：每块 `chunk.merge wait≈16.3 s`（等主互斥，最长 18.8 s）、归并 1.88 s、剪枝 1.1 s/次；
扫描本身 16.4 s/块 —— 串行归并+剪枝 ≈ 816 s，与 837 s 墙钟吻合 ⇒ 60% CPU 的直接原因是**线程阻塞在缓存归并/剪枝上**。

**F-4 修复**：`runChunked` 中 `sub.threads = (nChunks <= 1) ? (opt.threads > 0 ? opt.threads : hwCores) : 1;`
—— 宽扁范围（整图位图超经典上限但只切 1 块）不再退化为单线程；并在 `search.begin` 日志里写明
「仅1块→块内多线程补齐（宽扁范围，见 F-4）」或「块数少于并发，部分线程空闲」。

**验收对照**：

| 任务书验收项 | 结果 |
|---|---|
| CPU 占用 ≥ 85%（12 线程） | **91%（1095.3%/12）** ✓ |
| 速度 ≥ 3 亿/秒 | **99.4M/秒 ✗ 未达到**，理论依据见下 |
| 分块路径多核吞吐显著高于单核 | 见下（诚实说明） |

**速度为何达不到 3 亿/秒（理论依据，全部为实测数据）**：
* 439.8 亿分块场景：277 块 × 762 行，每块 1.598 亿个位置、扫描+密度统计实测 **16.4 s/块**
  ⇒ 单线程 **9.7M/秒**，12 线程聚合 **≈116M/秒**；实测 99.4M/秒（含缓存前 2 块的收集与合并）属于同一量级；
* 对照：同机 bench 的**小范围**基岩密度用例单线程 3,235 万/秒 —— 其位图仅 64KB（完全驻留缓存），
  而分块场景每块位图 **20MB × 12 并发 = 240MB**，远超 L3（32MB）⇒ 访存局部性差 3~5 倍；
* 该模式的上限由「LCG 填充 + 5×5 密度窗口统计」的访存行为决定，**与线程调度无关**（CPU 已达 91%，说明线程几乎一直在跑）；
  要进一步提高需改变分块几何/内核访存模式（属 v3.3.8 的性能专题，不在本次热修范围）。

**分块路径多核 vs 单核（诚实说明）**：用 `SLIME_FORCE_CHUNKED=1` 强制走分块路径后，
bench 的小范围用例多核与单核吞吐相同（Java 10000²：32,752 vs 32,443 万/秒；基岩 2000²：3,241 vs 3,247 万/秒），
说明**这些小用例的瓶颈不在扫描并行度**（位图极小、固定开销占主导），因此**无法用该 bench 证明「多核显著高于单核」**；
但 439.8 亿实跑的日志证明分块路径确实并行：`conc=12`、`chunk.end` 累计 4534 s ÷ 墙钟 445 s ≈ **10.2× 并行度**、CPU 91% ✓。
