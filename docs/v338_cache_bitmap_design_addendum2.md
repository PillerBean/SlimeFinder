# 设计文档补充 2：填充 vs 滑窗分解（覆盖区加速比上限）+ 迁移 A 的原子替换

## 一、填充 vs 滑窗分解 —— 修正我此前的乐观估计

现有实测（bench「密度 g=5 thr=0.3 2000×2000 多核」）：**扫描(填充) 1.7 ms / 匹配(滑窗) 4.7 ms**，
合计 6.4 ms ⇒ **填充 27% / 滑窗 73%**（小位图 64 KB、31 ns/点）。

把它拆到「缓存能省哪一段」：

| 环节 | 占比 | 缓存位图能否省 | 说明 |
|---|---|---|---|
| 循环/行分段/取指开销 | 含在填充内 | ✗ | 遍历必然发生（`done += W` 与命中无关） |
| 逐点史莱姆判定（LCG/MT19937） | **填充内的主要部分** | ✓ | 位图方案下整段填充被「memcpy 或直接当 grid」替代 |
| 位图写入（置位） | 填充内小头 | ✓（被合并进上面） | 同上 |
| **密度滑窗统计**（grid=5 ⇒ 每点约 25 次位测试/累加） | **73%** | **✗ 完全不受缓存影响** | 缓存只改位图「怎么来」，不改位图「怎么用」 |

**⇒ 覆盖区加速比上限 = 1/(1 − 0.27) ≈ 1.37×**（把整段填充省掉的最理想情形），
再扣掉「位图读取/memcpy/页错误」开销，现实值 **≈1.2~1.3×**。**不是**我此前写的 2~4×。

**据此重算（439.8 亿，12 线程）**：

| 场景 | 覆盖区 4.36% | 未覆盖 95.64% | 整机 |
|---|---|---|---|
| A 关缓存（实测） | — | 100 ns/点 | **444.8 s** |
| C 位图缓存（4.36% 覆盖） | 上限 1.37×（现实 1.25×） | 100 ns/点 | **≈437~441 s（提升 <1%，可忽略）** |
| C 位图缓存（**二次搜索**，覆盖≈100%） | 同上 | — | **≈330~360 s（1.25~1.35×）** |

**结论（必须写进验收）**：
* 缓存位图化的价值 = ①消除当前**负收益**（523 ns → 2~5 ns 查表）②体积 975→229 MiB ③加载 5.3→1.2 s
  ④覆盖区 **1.25~1.35×**。**它不可能带来 2~4× 或「2 亿/秒」**；
* 「439 亿 ≥2 亿/秒」**只能靠任务 6**，而任务 6 的靶心已由此分解锁定：**73% 的密度滑窗**（不是 27% 的填充）；
* 覆盖区加速比上限 1.37× 也是任务 4（缓存优先 + 命中即停）的收益天花板：命中即停省的是**未覆盖区的全部成本**，
  这部分与本次分解无关，仍然有效（任务 4 的价值应单独按「未覆盖区占整机比例」估，不看 1.37×）。

## 三、迁移方案 A + **原子替换**（按你的要求）

写盘流程（`CacheManager::saveFile`，v2）：
1. 写入 `<cache>.new`（新文件：16 B 头 + 每 range 的矩形/位图段），全程 `ofstream` + `flush` + 关闭；
2. **回读校验**：用 `loadFile()` 打开 `.new` 解析一遍（条目数/range 数/魔数/版本 + 抽样比对若干坐标），失败即中止并删除 `.new`，**旧文件不动**；
3. 成功后原子替换：优先 `ReplaceFileW(旧, 新, 备份=NULL, REPLACEFILE_IGNORE_MERGE_ERRORS, …)`
   （系统保证原子性；旧文件内容在 `ReplaceFileW` 返回前不会被破坏）；若失败退回
   `MoveFileExW(.new, 旧, MOVEFILE_REPLACE_EXISTING)`；
4. 仅在第 3 步成功后才更新内存状态与 UI 标签；任何一步失败 → 日志写明 + 保留旧文件 + 提示用户（不静默丢缓存）；
5. 加载端：先试 `<cache>`，若为 v1 则按 v1 解析（只读）；首次保存时按上述流程升级为 v2。

**验证**：单元测试新增「保存中断/校验失败不损坏旧文件」用例（模拟：把 `.new` 写成损坏内容 → 断言旧文件仍可加载、条目数不变）。
