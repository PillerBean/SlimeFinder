# 外部 AI 提速想法的逐条检验（2026-11-06）

结论先行：**在真实史莱姆判定上，这批想法里没有一条能超过现有实现**；只有两条"大图案"思路在我们的实现里仍是空白（
两占位候选：大图案改用双点哈希连接、以及 5×5 全绿的逆向求解），其中第一条已被本次测量确认有 8× 空间。

测试机：Ryzen 5 5600（AVX2，无 AVX-512）。所有探针见 `tools/opt_probe9.cpp`、`tools/opt_probe10.cpp`（不参与主程序构建）。

## 一、已被我们实现、AI 只是"重新提出"的

| AI 建议 | 现状 |
|---|---|
| 内联 LCG、去掉 `new Random` | 早已内联（`javaSlimeFromTail`），且 3.6.16 起走 AVX2 |
| 预计算 F(x)、H(z)，行/列只算一次 | 已做：`javaRowBase(z)` + `xTail[x]` 查表 |
| 严格模拟 Java int 溢出 | 已做（`imul32` + 符号扩展语义） |
| 位图 + 偏移移位 AND（O(mN/W)） | 已是严格匹配主路径（`evalStrictRowBits`，一次 64 锚点） |
| 分块并行、块间 halo | 已做（行分块 + 结果去重） |
| 只找一个匹配时早停 | 已做（`stopAtTarget` + 智能范围） |
| `-O3 -march=native` | MSVC 用 `/O2 /GL`，AVX2 只在 3 个专用编译单元 |

## 二、实测否定的想法

### ① 「`nextInt(10)` 没有拒绝采样，可以删掉」——**错误**

- 拒绝区间是 `bits ∈ [2147483640, 2147483647]`（`bits - bits%10 + 9` 在 int32 里溢出为负），概率 **3.73e-9**。
- 探针实测 2.68 亿个状态没抽到（理论期望约 1 次），但对**正确性**必须保留：
  - 1 亿区块的搜索，平均会踩到 **0.37 个**区块；删掉就是"偶尔错一个区块"，且不可复现。
  - 我们的 AVX2 内核专门做了检测（发现即整批退回标量），这正是逐位一致的原因。

### ② 17 位分块查表（`q = (A31*hi + T[lo]) & 0x7FFFFFFF`）——**正确但更慢**

- 正确性：1000 万状态 **0 处不一致**（公式成立）。
- 速度（含状态推进，每区块）：

| 实现 | ns/区块 |
|---|---|
| 直接 64 位乘法 | 1.41 |
| 17 位查表（512KB，L2） | **1.82** |
| 现有 AVX2 16-lane | **0.86** |

查表输在 L2 命中延迟 + 额外一次 32 位乘法，比直接乘还慢 29%。

### ③ 模 10 去除法（16≡1 mod 5，半字节求和）——**正确但慢 3.3 倍**

| 实现 | ns/区块 |
|---|---|
| 魔术乘 `%10` | 1.31 |
| 半字节和 + `%5` | **4.29** |

1000 万状态 0 处不一致，但 8 次移位求和远比一条 `imul` 贵。

### ④ 多级筛选（"期望 1.111N 次判定"）/ 哈希连接 vs 现有位图 AND

同一份 10% 密度位图（4096×2048 锚点），ns/锚点：

| 图案 | m | 位图 AND（现有） | 多级筛选 | 双点哈希连接 |
|---|---|---|---|---|
| 3×1 | 3 | **0.052** | 2.24 | 1.35 |
| 3×3 | 9 | **0.120** | 2.32 | 1.48 |
| 5×5 | 25 | **0.300** | 2.46 | 1.39 |
| 12×12 | 144 | **1.65** | 2.38 | 1.39 |
| 32×32 | 1024 | 11.80 | 2.26 | **1.39** |

- 三种方法命中数完全一致（校验通过）。
- **m ≤ ~150：现有位图 AND 全面胜出**（m=25 时快 8 倍，因为 64 个锚点一起比）。
- **m ≥ ~200：双点哈希连接反超**，m=1024 时快 **8.5 倍** —— 这是唯一被证实"我们还没做、且值得做"的点。
- AI 说的 "1.111N 次判定" 只数了操作数，没算每次判定的分支/内存成本：实测每次判定约 2.2~2.5 ns（每
  锚点 1.4~2.5 ns），远高于一次 64 位 AND。

### ⑤ 「只找一个匹配：期望检查 10^m 个锚点」——**成立**

| 图案 | m | 理论 10^m | 实测平均检查锚点 |
|---|---|---|---|
| 3×1 | 3 | 1.0e3 | 1032 |
| 2×2 | 4 | 1.0e4 | 9003 |
| 3×3 | 9 | 1.0e9 | 1M 锚点内没找到（符合）|

推论：**5×5 全绿（m=25）期望 10^25 个锚点，正向扫描永远不可能**。想找这种图案只能逆向（格约化 / SMT），这也是
AI 列表里唯一有"改变游戏规则"潜力的方向，但它需要专门的数学实现，不属于本轮"简单检验"。

## 三、无法在本机检验 / 明确不适用

| 想法 | 判断 |
|---|---|
| AVX-512 批量 LCG | 本机 CPU 无 AVX-512（且程序基线是 AVX2） |
| FFT/卷积匹配 | 我们的 AND 是 m/64 次操作/锚点（m=25 时 0.39 次），FFT 的 N log N 反而更贵；且需要 N 为 2 的幂 |
| Roaring Bitmap | 密度 10% 且分布均匀，压缩收益抵不过间接寻址开销 |
| 位切片/CSA 加法器 | 已在密度计数上验证过：一般阈值只值 2×，且我们已有更快的 k=g² 快路 |
| LCG 跳跃（jump ahead） | 我们按行分块天然无重叠，不需要跳跃划分 |
| 大页 / `madvise` / `perf` | Windows + MSVC 平台不适用；瓶颈早已定位为乘法端口（探针 V0/V1/V2） |
| GPU 持久内核 | 之前的实测：基岩版 GPU 比 CPU 慢 6.3 倍（含回传），换内核才有意义，风险高 |

## 四、留给下一轮的候选（按收益排序）

1. **大图案（m ≥ ~200）的严格匹配改用双点哈希连接**：实测 8.5× 空间，且实现难度低（先做两点筛选，再验证其余
   偏移）。目前的 32×32 全绿图案会明显受益。
2. **5×5 全绿的逆向求解**（格约化/SMT）：唯一能突破 10^25 的方向，工程量大，需要独立验证正确性。
3. 其余想法（查表 LCG、半字节 mod5、多级筛选、FFT、Roaring、AVX-512）**均已实测或分析为不划算**，不建议再投入。
