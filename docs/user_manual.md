# 用户使用说明（user_manual.md）

史莱姆区块查找器 **v3.3.8.1**（纯 C++/Qt 重构版）

判定算法与已验证参考实现完全一致；exe 文件属性为 FileVersion 3.3.8.1 / ProductVersion 3.3.8.1。

**v3.3.8.1 主要变化（缓存不再漏存 + 历史缓存停用 + 性能分解）**：
1. **缓存覆盖声明与条目同步**：登记声明前先确认「本块确实有新条目」；加载/保存时清扫「条目支撑不足」的声明
   （判据：声明内条目数 < 期望条目数 × 50%，期望 = 面积 × 10%；小面积声明放行）⇒ 缓存不会再漏掉史莱姆区块
   （1 万点真值比对 96.67% → **100.00%**、假阳性 0）。
2. **历史缓存停用（重要，见 §1 缓存文件说明）**：v3.3.7.2 及更早版本的缓存首次启动即改名 `*.legacy`
   并**不再自动加载**，提示「漏存 ~34%，建议重扫」；旧文件保留 7 天可回滚，到期自动清理。
3. **覆盖声明口径**：分块搜索的声明域改为「锚点行域」（与匹配域一致，相邻块不再重叠）。
4. **性能日志新增字段**：`search.summary` 的 `fill=` / `slideWindow=` / `rowsPerChunk=` / `hollowSkips=`。
5. **缓存改为位图格式（v2）**：体积约缩到 1/6、加载快约 20 倍（实测 1.02 GB → 152 MiB、加载 251 ms）；
   旧格式缓存仍可读，首次保存自动升级；保存改为**原子替换**（先写 `.new` 并回读校验，失败保留旧文件，不会出现半截缓存）。
6. **命中缓存时直接复用其位图**：搜索范围若已被缓存完整覆盖，程序直接把缓存位图当作扫描结果使用，**跳过逐区块判定**
   （实测 4096 万区块区域：223 ms → **22 ms**），结果与不使用缓存完全一致。

**v3.3.7 主要变化（大范围搜索紧急修复）**：

* **「达到目标数量即停止」在大范围（分块）搜索中真正生效**：以前范围很大时走的分块路径会**忽略**
  这个勾选项，即使已经凑够目标也会一直扫完整个范围（439 亿区块时看起来像“卡死”）。现在
  ① 每个分块内部恢复**几何提前停止**；② 新增**跨分块剪枝** —— 已凑够 N 个结果、且某个尚未开始的
  分块**不可能**产出更近的结果时，直接跳过该分块。**结果仍然是「全局最近的 N 个」，精度没有任何降级**
  （范围内凑不够 N 个、需要完整扫完时，行为与以前完全一致）。
* **取消（大范围搜索）不再卡死 / 闪退**：取消响应实测**最差 86 毫秒**（远低于 1 秒），连续取消 10 次全部正常；
  修复了两个隐患 —— 搜索线程与界面生命周期的竞态，以及「取消后立刻再点开始搜索」时旧结果事件干扰新搜索；
  另外修掉了搜索进行中重复点「开始搜索」时提示弹窗阻塞界面的问题（自动化 / 无人值守场景不再卡住）。
* **搜索进度显示改为单一来源（不再重复）**：工具栏下方的进度行 = 进度条 + **一个百分比** + **一句阶段短语**
  （如「正在扫描区块…」「正在匹配图案…」「正在排序结果…」）；状态栏 = **统计信息**
  「扫描 N/M 区块（xx%）｜ 速度 X 万/秒 ｜ 找到 K 个」+ **一个**「预计剩余：mm:ss」。
  以前「同一屏 3 个百分比、2 个预计剩余」的现象已彻底解决。
* **「进度」分类的流水行改为带总量**：新格式
  `[23:04:45] 已用时 12.5 秒，扫描 250/1000 区块（25.0%），找到 7 个`（完成行格式不变）；
  扫描数来自引擎的**真实计数**，与进度条百分比**完全同源**（大范围下每 0.25 秒更新一次），
  不再出现「计数停住」。
* **崩溃诊断默认开启（独立于普通日志）**：「程序设置 → 高级 → 崩溃时生成转储文件」现在**真正生效**
  （默认开启，改完立即生效、无需重启）；新增**关键信息日志** `logs/crash-YYYY-MM-DD.log`
  （始终记录，与「启用日志」无关）；崩溃时（含访问违例、未捕获异常、CRT 非法参数、内存分配失败）
  在 `crashes/` 生成 `.dmp` 与 `crashes/crash_report.txt` 摘要；若上次运行没有正常退出，
  **下次启动**会在反馈栏与状态栏提示。详见 §3.5。
* **内存占用可控**：分块搜索的并发数按内存预算决定（默认 **1.5 GB** 位图预算 → 本机 12 并发；
  439 亿区块级别实测峰值 **1.48 GB**）；高级用户可用环境变量 `SLIME_CHUNK_BUDGET_MB` 调小
  （如 512 → 4 并发、内存峰值约 0.5 GB，但速度会明显变慢）；基岩版 + 缓存搜索改为
  「逐块即时写入缓存并释放」，峰值不再随范围增长。详见 §3.6。

## 1. 运行环境与启动

- Windows 10/11 x64（发布目录已附带运行库，普通环境直接双击 `SlimeFinder.exe` 即可）。
- 程序在**程序所在目录**自动创建：
  - `logs/SlimeFinder_YYYY-MM-DD.log`（运行日志）、`logs/performance.log`（性能日志）
  - `logs/crash-YYYY-MM-DD.log`（**关键信息日志**，v3.3.7 起
    **始终记录**，与「启用日志」无关：启动环境、搜索参数、约每 5 秒一条进度与内存、取消 / 完成 / 错误与崩溃事件）
  - `crashes/`（崩溃转储 `*.dmp` 与 `crashes/crash_report.txt` 摘要；由「设置 → 高级 → 崩溃时生成转储文件」
    控制，**v3.3.7 起默认开启且改完立即生效**；排查方法见 §3.5）
  - `config.json`（配置文件，首次运行自动生成）
  - `slime_cache.slimecache`（基岩版缓存，启用后自动生成；**v3.3.1 起扩展名统一为 .slimecache**）
  - `slime_cache.slimecache.legacy`（**v3.3.8 起**：v3.3.7.2 及更早版本留下的历史缓存改名保留，**7 天后自动清理**）
  - `slime_cache.migrated`（**v3.3.8 起**：历史缓存一次性改名迁移的标记文件，勿删）
- 请确保程序目录可写（勿放入只读系统目录）。

> **缓存文件说明（v3.3.2 起）**：缓存固定存放在**程序目录**，文件名为 `slime_cache.slimecache`。
> 点「导入缓存」时，对话框会**直接定位到程序目录并预先选中当前缓存文件** —— 刚搜索生成的缓存
> 一定看得到、也一定选得中，直接点「打开」即可载入。
> 对话框提供 5 组过滤器：
> 1. `史莱姆区块缓存 Slime Cache (*.slimecache *.cache *.pkl *.pickle *.legacy)`（默认）
> 2. `新版缓存 New (*.slimecache)`
> 3. `旧版二进制缓存 Legacy (*.cache *.slimecache.legacy *.cache.legacy)`
> 4. `Python 旧版缓存 (*.pkl *.pickle)`
> 5. `所有文件 All Files (*.*)`
>
> **历史缓存停用（v3.3.8，重要）**：v3.3.7.2 及更早版本生成的缓存存在缺陷 —— 覆盖声明可能**没有条目支撑**
> （实测漏存约 34% 的史莱姆区块、且不产生假阳性），继续用它做「已覆盖 ⇒ 跳过计算」的判定只会漏结果。
> 因此升级到 v3.3.8 后**首次启动**时：程序把已有缓存改名为 `slime_cache.slimecache.legacy`（与旧名
> `slime_cache.cache.legacy`）、**本次启动不加载它**，并在反馈栏/状态栏提示「历史缓存已停用（漏存 ~34%）：
> 建议重扫」；旧文件**保留 7 天**（可回滚：在「导入缓存」过滤器里选中 `*.legacy` 手动导入，导入后仍会做
> 支撑度清扫），到期自动删除。
> v3.3.8 起新生成的缓存是**可信**的：登记覆盖声明前会先确认「本块确实有新条目」，且每次加载/保存都会
> 清扫「条目支撑不足（声明内条目数 < 期望条目数 × 50%）」的声明 —— 被清扫的区域会返回「未覆盖」并在
> 下次搜索时重扫，**不会再被误判为「已知非史莱姆」**。
>
> **历史格式兼容**：`.cache`（v3.1.1~v3.3.0）可直接导入，程序启动时若只存在旧文件会自动加载
> 并另存为新格式（旧文件保留不删）；`.pkl`/`.pickle`（v3.1.0 及更早的 Python pickle）**不能直接
> 加载**，选中后会提示先用 `py -3 scripts/convert_pkl_cache.py 旧缓存.pkl` 转换；`.bin` 是本程序
> 从未使用过的扩展名（任务书列为假设格式，无需兼容）。
>
> **修复前的问题（v3.1.1~v3.3.0）**：对话框未指定起始目录（Qt 回退到进程工作目录/上次目录），
> 缓存文件虽在程序目录却看不到；且过滤器只列 `*.cache`。v3.3.1 统一了扩展名，v3.3.2 补齐
> 「定位 + 预选 + 全历史格式过滤」，彻底消除「缓存存在但选不中」。

### 2.0 帮助 / 使用教程（v3.3.3）

| 【常见问题】 | 结果太多 / 搜索太慢 / 程序闪退 / 缓存是什么 / 能同时开两个程序吗 等 |

## 3. 典型流程

### 3.1 Java 版严格图案匹配
1. 选 Java 版 → 输入种子 → 点「附近(±1000)」或手动设范围；
2. 模式选**严格图案匹配** → **绘制图案**（左键：灰→白→绿循环；右键：忽略；行列 1~64）；
3. 「方向锁定」默认勾选（不旋转，与参考程序一致）；取消则匹配 4 个 90° 旋转；
4. 设查询起点与目标数量 → 点工具栏 **「开始搜索」**。

### 3.2 Java 版密度搜索
模式选**密度搜索**：网格大小（默认 5 区块）× 最小密度（默认 0.30）→ 点工具栏「开始搜索」。
若需在“速度/完整性”之间取舍，见 §5A「搜索算法模式」。

### 3.3 基岩版与缓存
1. 选基岩版（种子不影响判定）；
2. 勾选**使用缓存**：完整覆盖直接读取；部分覆盖自动补扫后**增量合并保存**；
3. 缓存可导入迁移：**新版扩展名 `.slimecache`**，旧版 `.cache` 同样可以导入（程序启动时
   若只存在旧文件会自动加载并迁移为新格式，旧文件保留）；旧 Python `.pkl` 缓存先用
   `py -3 scripts/convert_pkl_cache.py 旧缓存.pkl` 转换（默认输出同名 `.slimecache`）；
   「导入缓存」对话框会定位到程序目录并预选当前缓存文件（v3.3.2）；
4. 缓存容量：受 `config.json` 的 `cache.maxSizeMB` 限制（默认 1024 MB，可在
   「设置 → 缓存 → 缓存容量上限」中修改），超限自动丢弃最旧区域（增量更新语义不受影响）；
5. 说明：基岩版判定需完整 MT19937 初始化，v3.3.0 起由 **AVX2 批量内核**处理
   （单核实测 3600 万区块/秒，v3.2.1 为 130 万/秒，约 24 倍），大范围也建议配合缓存。
6. **状态标签（v3.3.3）**：只要有缓存数据就显示
   **「缓存已加载，共 N 个区块（覆盖 R 个区域，约 X MB）」** —— 首次搜索生成缓存后、启动
   自动加载后、导入/清除后、勾选或取消「使用缓存」后都会**立即刷新**；若磁盘上已有缓存文件
   但尚未载入内存，会提示「未加载缓存（磁盘上已有 …，可点「导入缓存」或重启载入）」。
   每次搜索写盘后状态栏还会提示「缓存已更新：共 N 个区块」。

### 3.4 搜索进度与取消（v3.3.7）

搜索在后台线程执行。**进度显示只有一个来源**（v3.3.7 起不再重复，也不再出现
「同一屏 3 个百分比、2 个预计剩余」）：

* **工具栏下方的进度行**（约 28 px 高、横跨整个窗口）：进度条 + **一个百分比** + **一句阶段短语**；
* **状态栏**（窗口最下方）：**统计信息**「扫描 N/M 区块（xx%）｜ 速度 X 万/秒 ｜ 找到 K 个」，
  外加**一个**「预计剩余：mm:ss」；
* **底部面板「进度」分类**：每 0.5 秒一条文字流水（v3.3.7 起**带总量** `N/M（xx%）`，见 §2.0B），
  取消搜索会留下一条「已取消」记录。

| 阶段 | 进度行显示 |
|---|---|
| 扫描 | `进度: [████░░] 65% 正在扫描区块…` |
| 进入匹配 | `进度: [██████] 100% 扫描完成，正在匹配图案…` |
| 匹配 | `进度: [████░░] 45% 正在匹配图案…` |
| 生成结果 | `进度: [██████] 100% 正在排序结果…` → `搜索完成（结果可在上方按距离/密度排序）` |

* **流水行格式（v3.3.7）**：`[23:04:45] 已用时 12.5 秒，扫描 250/1000 区块（25.0%），找到 7 个`；
  完成行格式不变：`[23:04:46] 已完成：共扫描 401234567 区块，找到 10 个结果，耗时 2.1 秒`；
* 扫描数来自引擎的**真实计数**，与进度条百分比**完全同源**（大范围分块搜索下每 0.25 秒更新一次），
  **不会再出现「计数长时间不变 / 计数停住」**；
* **「达到目标数量即停止」（及时反馈）v3.3.7 起对大范围（分块）搜索同样生效**：
  ① 每个分块内部恢复**几何提前停止**；② **跨分块剪枝** —— 已凑够 N 个结果、且某个尚未开始的分块
  **不可能**产出更近的结果时直接跳过。结果仍然是**全局最近的 N 个**，精度没有任何降级
  （范围内凑不够 N 个、需要完整扫完时，行为与以前完全一致）。
  实测：常见图案 + 目标 1 时扫描量由 314,572,500 区块降到 **267,596,340 区块**，结果逐位一致；
  另一组 63 分块的实测由 **41.0 秒降到 7.0 秒**（跳过 51 个分块）；
* **搜索过程中不会再出现「范围较小，建议关闭 GPU 加速」之类的提示**（v3.3.6 起已移除）；
* **「取消」在任何阶段都立即生效（v3.3.7 起大范围搜索也不会卡死 / 闪退）**：
  - 取消响应实测**最差 86 毫秒**（远低于 1 秒）；连续取消 10 次全部正常；
  - v3.3.7 修复了两个隐患：搜索线程与界面生命周期的竞态，以及「取消后立刻再点开始搜索」时
    旧结果事件干扰新搜索；另外修掉了搜索进行中重复点「开始搜索」时提示弹窗阻塞界面的问题
    （自动化 / 无人值守场景不再卡住）；
* 结果上千条时按批创建卡片，期间窗口保持可拖动、可点击，不会出现「未响应」。

### 3.5 崩溃排查与诊断（v3.3.7）

v3.3.7 加强了崩溃诊断能力，遇到异常退出时请把下面的文件连同 `logs/` 一起反馈：

| 内容 | 位置 / 说明 |
|---|---|
| 崩溃转储 | `crashes/*.dmp`，文字摘要见 `crashes/crash_report.txt` |

| 关键信息日志 | `logs/crash-YYYY-MM-DD.log`，**始终记录**（与「启用日志」无关）：启动环境、每次搜索参数、约每 5 秒一条进度状态与内存、取消 / 完成 / 错误事件、崩溃事件 |
| 上次异常退出提示 | 若上次运行没有正常结束，**下次启动**时会在反馈栏与状态栏提示「上次运行未正常结束…关键信息见 logs/crash-*.log；转储见 crashes/」 |

* 普通运行日志仍是 `logs/SlimeFinder_YYYY-MM-DD.log`（由「工具 → 启用日志」控制，默认关闭），

### 3.6 内存占用与分块预算（v3.3.7）

* 大范围（分块）搜索的**并发数由内存预算决定**：默认位图预算 **1.5 GB**，本机对应 **12 并发**；
  439 亿区块级别的整图搜索实测内存峰值 **1.48 GB**（远低于 4 GB 的验收要求）。
* **高级用户**可用环境变量 `SLIME_CHUNK_BUDGET_MB` 调小预算：例如设为 `512` → 约 **4 并发**、
  内存峰值约 **0.5 GB**，但**速度会明显变慢**（并发数减少）。
* 基岩版 + 缓存搜索改为「**逐块即时写入缓存并释放**」，内存峰值**不再随搜索范围增长**。

## 5. GPU 加速（v3.2.1 起默认关闭，完全用户可控；v3.3.6 起不再有任何临界值说法）

- **默认关闭**（复选框“启用 GPU 加速（实验性，默认关闭）”不勾选），避免在无
  OpenCL 驱动/驱动异常的环境中自动触发 GPU 初始化；程序始终以纯 CPU 路径稳定工作。
- **唯一保留的提醒（v3.3.6）**：GPU 开关的 tooltip 与「工具 → GPU 状态」对话框都显示：

  > GPU 加速不一定比纯 CPU 强。实际效果取决于你的硬件配置和搜索范围，建议实际测试后决定是否启用。

  v3.3.6 **彻底移除了「临界值 / 交叉点」相关说法**：不再做用于估算临界值的动态基准测试、不再用公式估算
  「临界值约 XX 万区块」，`config.json` 中 `gpu.threshold` 等字段一并移除，
  搜索时也**不再出现「范围较小，建议关闭 GPU 加速」的状态栏提示**。
  「工具 → GPU 状态」仍然显示**设备名、显存、计算单元数**与本机**实测吞吐率（CPU vs GPU）**，
  但不再据此给出任何建议阈值——是否启用请自行实测（可用「工具 → GPU 状态」对比 CPU / GPU 吞吐率）。
- **启用**：勾选复选框即可（选择会立即写入 `config.json` 的 `gpu.enabled`，重启仍保持）。
  首次启用可能需几秒初始化；勾选后若检测到 GPU 不可用，会**自动回退 CPU**——
  不弹窗、不崩溃，仅在 `logs/` 记录回退原因（「反馈」分类也会记一条 ❌ 消息）。
- **可用性检测（勾选启用时执行一次）**：勾选后程序同步检测一次 OpenCL 设备可用性并写
  `logs/`（“GPU 可用性检测结果：可用/不可用”）。**启动阶段程序完全不接触 OpenCL**
  ——无/异常驱动环境下驱动初始化可能原生崩溃（无法被捕获），因此启动与默认关闭状态下
  的搜索 100% 纯 CPU，绝不因 GPU 相关代码闪退。
- 搜索仅当 **勾选 且 检测可用** 时注入 GPU：
  1. **判定扫描**（v3.2.0 起）：范围 ≥ 约 104 万区块时由 GPU 生成区块位图（与 CPU 逐位一致）；
  2. **密度匹配**（原计划的 v3.3.1 增强）：**本版本未交付**——该内核开发已按指示暂停，
     代码保留在源码 `src/gpu/experimental/`（v3.4.0 起点）。因此密度搜索的**窗口匹配阶段
     始终由 CPU 完成**，GPU 只负责第 1 项的判定扫描，结果与 CPU 精确模式**逐位一致**。
     详见 [v3.3.1 验证报告](verification_report_v331.md) §5。
- **严格图案模式与 GPU（v3.3.7 说明，无代码改动）**：严格图案模式下引擎**不使用 GPU**
  （GPU 只参与密度搜索的匹配阶段）；勾选 GPU 会触发一次后台**实测吞吐率基准**，
  如果刚勾选就开始搜索，该基准可能短暂占用 CPU。
- **其他开关**：
  - 环境变量 `SLIME_GPU=0/1`（强制关/开，排障用）优先于配置文件；
  - 引擎级阈值 `SLIME_GPU_MIN_CHUNKS`（默认约 104 万区块）、瓦片预算 `SLIME_GPU_TILE_BYTES`
    （单块 ≤256MB，基岩版自动收紧至 ≤32MB 以保证取消响应 <1s）；
  - `SLIME_GPU_DEBUG=1` 设备发现与回退原因详细日志（stderr）。
- 并行计算组内的状态标签实时显示
  `GPU：未启用（勾选后检测）/正在检测…/可用（已启用）/不可用，使用 CPU`。
- 实测参考（本机 AMD RX 6750 GRE 10GB + Ryzen 5 5600，GPU 开/关同参数对比）：
  判定扫描 Java 16384² 端到端 27.1 ms（≈99.2 亿区块/秒，相对 CPU 单核 35.9×、
  相对 12 线程 6.3×）；基岩 2048² 71.8 ms（相对 CPU 单核 70.6×、12 线程 8.2×）。
  详见 [v3.3.1 验证报告](verification_report_v331.md) §6。

## 5A. 搜索算法模式（v3.3.0）

密度搜索下可在「搜索算法」中选择四种模式；**严格图案匹配不使用这些算法**
（图案匹配本身就是精确判定，界面会自动禁用算法选择）。

| 模式 | 说明 | 结果完整性 | 实测加速（本机 Ryzen 5 5600） |
|---|---|---|---|
| **精确模式（默认）** | 滑动窗口增量统计 + 严格匹配字级位并行（64 锚点/批）+ AVX2 内核 | **100% 完整**（与 v3.2.1 逐位一致，111/111 参考对照通过） | 密度 5×5：相对保守模式 **7.0×**（相对 v3.2.1：匹配阶段 5.7×）；g=10：**12.9×**；严格匹配：**13~15×** |
| **分层模式** | 粗块必要条件剪枝（16×16 / 32×32 / 64×64 + 阈值比例） | 比例 ≤ 1.00 时**无损**（结果与精确模式完全一致）；> 1.00 时可能漏检（界面警告条） | 稀疏场景（大网格、该阈值下无匹配）**63×**（相对保守模式）；密集场景自动回退滑动路径，与精确模式同速 |
| **快速估算模式** | 只扫描/评估采样网格上的区块（间隔默认 8，约 1/64 工作量），密度按采样格点比例**估算** | **估算值，可能遗漏高密度区域**（结果区显示警告条） | 大区域（16384²、g=32、间隔 8）**132×**（相对保守模式） |
| **保守模式** | 纯暴力逐窗统计（v3.2.1 字面实现），不使用任何优化 | 100% 完整（结果与精确模式一致） | 1×（作为同机对照基准） |

### 5A.1 如何选择

* **想要准确结果**（找史莱姆农场位置、需要完整列表）→ **精确模式**（默认，无需改动）。
* **范围极大、只想先看看哪里可能密集** → **快速估算模式**：把采样间隔调大更快（8 → 约 1/64 工作量），
  调小更接近真实（间隔 2 → 约 1/4 工作量）。**估算结果只用于粗筛**，确定候选区域后请用精确模式
  在该区域重新搜索。
* **需要“估算式的稀疏扫描”但又要求报告的密度值准确** → 勾选**精算采样**：
  位置仍然是采样网格（覆盖率约 1/间隔²），但每个位置的密度是**精确**的（与精确模式同位置完全一致，
  不会出现“密度 100%”这类假阳性），加速比约 1.4~5×。
* **网格很大（如 32×32 以上）且目标阈值很高、地图明显达不到** → **分层模式**：
  剪枝会整段跳过不可能达标的区域，加速显著且（比例 ≤ 1.00 时）结果与精确模式完全一致。

### 5A.2 采样估算的精度说明（重要）

「快速估算模式」用采样格点估计窗口密度。设采样间隔为 `s`、窗口内采样点数为 `m`，
估算值与真实窗口密度的相关系数上界为 `sqrt(m)/g`（`g` 为网格边长），
**即使用间隔 8 时相关性上限约为 1/8 = 0.125**（本机实测：间隔 2 → 0.60、4 → 0.39、8 → 0.19）。
这是 1/s² 采样的数学性质，不是程序缺陷：要想相关性 ≥ 0.7 就必须几乎逐格扫描（即精确模式）。
因此：

* **不要**用快速估算的结果直接建农场；它适合“整体密度概览 / 粗筛”。
* 界面在估算模式下始终显示 `⚠️ 当前为快速估算模式，结果为估算值、不代表精确分布…`；
  `logs/performance.log` 也会记录模式与与精确模式的差异（小范围自动对照）。
* 若需要“位置稀疏但数值准确”，用**精算采样**；若需要“完整且准确”，用**精确模式**。

## 附录 A：群系对史莱姆生成的影响（估算公式，供用户自行计算）

> 本程序（v3.0.0/v3.1.0）按任务书决定**不内置群系权重**；程序输出的“史莱姆区块”指
> **区块判定层面**（与群系无关）。群系只影响“该区块中史莱姆能否实际生成”的第二步判定。
> 以下资料供自行估算，勿当作游戏内精确数据。

### A.1 两层判定模型
1. **区块层**（本程序计算）：Java 版由种子+区块坐标经 LCG 判定（约 1/10 区块为史莱姆区块）；
   基岩版由区块坐标经 MT 判定（与种子无关）；
2. **生成层**（游戏内部）：在史莱姆区块内，史莱姆生成还要求：
   - 地下：Y < 40（1.18+ 需史莱姆区块且满足亮度/方块条件）；
   - 沼泽：任意史莱姆区块均不要求，但沼泽中不依赖史莱姆区块也能低概率生成；
   - 特定群系限制：如蘑菇岛等群系史莱姆不生成；末地/下界规则不同。

### A.2 “群系权重”估算公式
第三方工具常用“按群系加权”折算可生成面积：
```
有效密度 ≈ Σ_i ( 群系_i 面积 × 群系_i 权重 w_i ) ÷ 总搜索面积
```
权重建议（经验参考值，自行调整）：
- 普通主世界群系（平原/森林等地下史莱姆区块可生成）：w = 1.0
- 沼泽（含地表史莱姆机会）：w ≈ 1.3（生成机会额外受月亮相位影响）
- 蘑菇岛 / 深暗之域等禁止史莱姆群系：w = 0.0
- 海洋（其海底仍属区块生成层，按普通处理即可，实际取决于目标层高）

例：范围内 20% 面积为沼泽、80% 平原，则估算有效密度 ≈ 0.20×1.3 + 0.80×1.0 = 1.06，
即与全平原相比约 +6% 的“有效”生成面。请按自身版本与生成层目标自行核算，程序不代算。

### A.3 结论
- 找“区块”用本程序；找“能刷怪的位置”请叠加游戏内群系/层高/亮度条件；
- 任务书 3.2/13.3 的 `biomeWeight` 预留参数已在引擎 API 保留为占位（默认 nullptr=1.0），
  不暴露到界面，亦不影响任何计算结果。
