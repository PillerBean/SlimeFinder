# 3.13.7 当前速度状态审计

> 目的：把“速度”拆成可解释的部分，判断哪些部分已经充分利用、哪些还有余量。
> 本报告只记录当前工作树实测，不把旧版估算当成最终结论。

## 1. 环境与版本

```text
CPU：AMD Ryzen 5 5600，6C / 12T
GPU：AMD Radeon RX 6750 GRE 10GB，gfx1031，18 CU
线程：默认 12
构建：SlimeFinder 3.13.7
```

测量时显式关闭判定位图复用，除“复用后匹配”一组外。

## 2. 整体流程结构

CPU 路径：

```text
位图分配 → 判定扫描 → 匹配 → 结果堆 → 排序/返回
```

GPU 路径：

```text
宿主准备/设参/清零 → 内核 → CPU 阻塞等待/回读 → 宿主筛选/结果转换
```

当前没有 CPU/GPU 双缓冲，也没有扫描与匹配流水线重叠；因此总耗时是串行之和。

## 5. 四类上限的当前实测

### 5.1 指令/运算

本机新增微基准：

```text
vpmulld 纯乘法峰值：8.78~8.84 G 次 256 位乘法/秒
8 链内层循环（xor+shift+mul+add）峰值：0.3029 ns/链步
折合 64 chunk 批：15.03 ns/chunk
```

Bedrock CPU 8 链内核实测：

```text
14.9~15.1 ns/chunk
```

⇒ 内核约达到**同指令混合峰值的 99%~101%**。

这修正了“纯 vpmulld 分母”的误读：

```text
49.625 次乘法/chunk ÷ 8.84 G/s = 5.61 ns/chunk
14.9 ns / 5.61 ns ⇒ 纯乘法口径只有 37.6%
```

但纯乘法漏掉了 xor/shift/add，**不能拿 37.6% 说内核有 2.6 倍空间**。
按完整指令混合，Bedrock CPU 内核已经基本打满单核向量执行能力。

Java CPU 判定此前估算为 63~66 亿/s 上限、实测 63.7 亿/s，约 96%~100%；
本轮没有重新做 Java 混合指令峰值，因此仍按“接近但不是严格证明”记录。

### 5.2 访存

实测单线程拷贝带宽：

```text
32.0~34.2 GB/s（读+写合计）
```

Bedrock CPU 扫描输出：

```text
1 B/chunk × 4.19M ≈ 4.0 MB
9.8 ms → 约 0.41 GB/s
```

约为实测带宽的 **1.2%~1.3%**，不是访存瓶颈。

CPU 匹配读取的位图约 0.5 MB（2048²）或 8.4 MB（8192²），按匹配墙钟算也只有
约 1~3 GB/s 量级，低于拷贝带宽；匹配更可能是指令/延迟受限，而不是 DRAM 带宽受限。

GPU 结果回读量：2048² 命中约 1 万条 × 8 B ≈ 80 KB；相对总耗时也不是带宽瓶颈。

### 5.3 搜索节点

Bedrock 判定节点 = chunk：

```text
单线程：约 67 M chunk/s
12 线程：约 4.2 亿 chunk/s（4.19M / 9.8 ms）
```

按内层峰值 15.03 ns/chunk 折算单线程节点上限约 66.5 M/s，实测与它基本一致。
节点率不是独立于指令上限的指标，不能和指令利用率重复相加。

匹配节点（8192²，target=1）：

```text
Java 图案匹配 3.3 ms，节点约 6700 万锚点 → 约 20 亿锚点/s
Java 密度匹配 8.4 ms，节点约 6700 万锚点 → 约 8 亿锚点/s
Bedrock 图案/密度同量级
```

这些是“墙钟节点率”，还没有固定位图下的纯内核节点上限，不能当作极限。

### 5.4 并行

Bedrock CPU 4M 扫描，线程缩放：

| 线程 | 时间 | 加速比 | 相对线程数效率 |
|---:|---:|---:|---:|
| 1 | 64.17 ms | 1.00× | 100% |
| 2 | 33.72 ms | 1.90× | 95% |
| 4 | 17.60 ms | 3.65× | 91% |
| 6 | 13.21 ms | 4.86× | 81% |
| 8 | 13.89 ms | 4.62× | 58% |
| 10 | 10.93 ms | 5.87× | 59% |
| 12 | 11.36 ms | 5.65× | 47% |

解读：

- 相对 6 物理核，约 81% 效率；
- 相对 12 逻辑线程，只有约 47%；
- 按 12 线程拟合 Amdahl 串行比例约 8.3%，上限约 9.8×；
- 实测 5.65× 约为该上限的 58%；
- 10 线程反而略快于 12，说明 SMT/调度有抖动，不建议直接按“逻辑线程越多越好”处理。

GPU 并行上限没有 profiler/occupancy 数据，不能给出同样口径的百分比；
只能从等待拆分判断：Bedrock GPU 是内核主导，Java 密度 GPU 是宿主主导。

## 6. 当前有没有充分利用

### 6.1 已经接近利用满的部分

- **Bedrock CPU 单核向量执行**：同指令混合峰值 15.03 ns/chunk，实测 14.9~15.1 ns/chunk，
  约 99%~101%。
- **Bedrock CPU 访存**：输出约 0.41 GB/s，仅带宽的 1.2%。
- **Bedrock GPU 内核**：8192² 时 CPU 等 GPU 占 94%~99%，GPU 是主要执行方；
  宿主处理通常不到 0.4 ms。
- **Java CPU 判定**：旧数据约 96%~100% 估算上限，属于较强证据。

### 6.2 没有充分利用的部分

- **CPU 并行**：12 逻辑线程只有 47% 效率，6 物理核约 81%；SMT 调度还有余量。
- **Java GPU 密度**：8192² 时 GPU 等 CPU 约 66%，GPU 空闲在等回读/筛选/结果处理。
- **Java GPU 图案**：8192² 时 GPU 等 CPU 约 32%，小范围更明显。
- **CPU 匹配**：8192² 时 Java 图案匹配占 23%、Java 密度占 44%；
  target=200k 时 Java 密度匹配占 77%，且没有固定位图的内核极限数据。
- **GPU 硬件占用率**：没有 profiler，不能声称“GPU 利用率 100%”；只能从时间等待判断
  是否内核主导。

## 7. 结论

当前不存在一个统一的“60% 利用率”：

```text
Bedrock CPU 单核指令：约99%     → 已接近满
Bedrock CPU 访存：约1.2%        → 不是瓶颈
Bedrock CPU 12线程并行：约47%逻辑/81%物理 → 还有并行空间
Bedrock GPU：内核主导，94%~99%时间在等GPU → 算法/内核瓶颈
Java GPU：大量时间在等CPU/回读 → 流程瓶颈
Java CPU 大范围：匹配占比升高 → 匹配阶段是主要剩余成本
```

因此后续优先级应是：

1. **CPU 并行调度**：线程数、SMT、负载均衡，而不是继续改 Bedrock 单核内核；
2. **Java GPU 宿主/回读流水线**：这是当前最明显的 GPU 空闲；
3. **CPU 匹配固定位图内核基准**：确认匹配是否还有算法空间；
4. **GPU 占用率/内核-only**：需要 profiler 或事件计时；
5. 最后才考虑扫描/匹配整体流水线。

## 9. 限制

- 单机、非独占，后台负载会造成约 5%~15% 波动；
- 指令/访存为微基准，不等于所有指令组合的整机峰值；
- GPU 没有硬件 profiler/occupancy 数据；等待占比来自同步回读日志；
- `slideWindowMs` 是跨线程累加时间，不是墙钟；
- 匹配节点率还没有固定位图的纯内核上限。
