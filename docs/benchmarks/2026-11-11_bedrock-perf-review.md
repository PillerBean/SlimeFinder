# 基岩版性能优化：历史核查与 2026-11-11 实验记录

## 目的

v3.12.1 基岩版性能优化前的历史核查，避免重复已验证失败的路线；同时记录本轮新实验。

## 历史结论（先读，不再重复）

- **CPU 8 lane/链**已落地（v3.7.0），32 lane/8 链是当前最优；48/64 lane 在引擎中更慢。
- **简化/拟合算法**已否证：截断、少一步、跳过 twist/temper 等与真实判定独立，例外表等于存位图。
- **基岩 GPU 旧内核**比 CPU 慢；**398 步 init 捷径**换内核后 GPU 达到 ~1.6 B/s（v3.7.1）。
- **GPU 打包字**（每 work-item 64 区块 → ulong）已落地，回读量为 1/8（v3.7.4）。
- GPU 两条种子链交错**已实测无收益**，编译器已充分流水；不要再加链。
- GPU `%10` 魔数乘法、Java 64 位乘法拼装等微优化**无收益**。
- 当前基线：GPU Bedrock ~1.6 B/s；CPU 扫描 ~253 M/s（12 线程）。
- 因此不要重复：加链、拟合算法、旧字节内核、普通 kernel 微调。

## 2026-11-11 新实验

### 1. GPU 四链/每 work-item 4 区块

在 `scan_bedrock_words` 中把 `bedrock_pair` 改成 `bedrock_quad`（4 条独立 MT 状态交错推进），保持 64 区块/ulong 输出。

5 次 `slime_ocl_probe` Bedrock GPU 基准：

| 版本 | 中位吞吐 |
|---|---:|
| 原双链 | **1610.59 M/s** |
| 四链 | **1609.17 M/s** |

差异在噪声内，**无收益，已还原原内核**。结论与历史“两条链已无收益”一致，不能靠增加链宽提升。

### 2. GPU local work size

用 `SLIME_GPU_LOCAL` 测 32/64/128/256：

| local | 中位吞吐 |
|---:|---:|
| 32 | 1595.95 M/s |
| 64 | 1608.18 M/s |
| 128 | 1610.78 M/s |
| 256 | 1609.91 M/s |

差异噪声级，保持默认 64。

### 3. 引擎级开销观察

`slime_ocl_probe` 的 Bedrock 4096² 引擎级 GPU 扫描约 **18–19 ms**；裸打包字内核等效约 **10.4 ms**（4.19M 区块 2.6 ms × 4）。说明剩余优化空间可能在：

- 引擎级瓦片/缓存集成；
- `useCache/collectNew` 强制字节路径；
- GPU 扫描与位图/缓存合并。

## 下一步候选（未做）

1. **缓存感知的打包字路径**：当前 `wordsCapable = !useCache && !collectNew`，历史因缓存记账正确性强制回退字节路径；若实现按缓存覆盖过滤 newChunks，可让基岩缓存构建也吃打包字 GPU。
2. **引擎级 Bedrock GPU 集成 profiling**：拆分 kernel/回读/位图/缓存记账，定位 8~9 ms 固定开销。
3. **基岩 GPU 自动推荐/阈值**：GPU 1.6 B/s 对 CPU 253 M/s 优势明显，但默认关闭；可做安全的一键优化提示，而不是默认强开。
4. CPU FastMt 已接近上限，暂不再投入。

## v3.12.1 第一项落地实验：只读缓存 + 打包字

改动：`SlimeEngine::runGpuScanStage` 的 `wordsCapable` 从 `!useCache && !collectNew` 放宽为 `!collectNew`。

安全前提：只读缓存时 GPU 仍扫描整个区域，缓存位只是冗余已知结果；打包字 OR 全量结果
与字节路径逐位一致。只有 `collectNew`（构建缓存需要登记新命中）继续强制字节路径。

验证：全量单元、参考对拍 117/117、GUI 自检 0 FAIL 均通过。

待办：补一项「只读缓存 + 大范围」的端到端基准，确认相对原字节路径的实际提升；
如果提升不足，保留改动或回退需有数据依据。

## 真正缓存命中：跳过 GPU 重算（v3.12.1）

**重要修正**：之前记录的 2.81 ms 是“缓存全覆盖时仍用 GPU 扫描”，不是纯缓存命中；
该路径 `cacheSkipped=0`、`cacheHitPoints=0`。

正确的优化是：缓存完整覆盖时，GPU 阶段直接返回，让 CPU 走缓存位图填充快路径。

基准：Bedrock 2048×2048（4,194,304 区块），只读缓存覆盖全区域，GPU 开启/不开启均相同
（命中后不重算）。

| 路径 | 扫描中位 | 总耗时中位 |
|---|---:|---:|
| 优化前：缓存全覆盖仍 GPU 重算 | 23.91 ms | 25.95 ms |
| 优化后：真正缓存命中 | **0.22 ms** | **约 2.1 ms** |

- 扫描约 **100×**，总耗时约 **12×**；
- `cacheSkipped=1`、`cacheHitPoints=4194304`；
- 命中结果数一致（220,832）；
- 全量单元、参考 117/117、GUI 自检 0 FAIL。

当前 v3.12.1 的产品改动就是这一条“缓存完整覆盖跳过 GPU 扫描”；
之前尝试的 `wordsCapable=!collectNew` 对该场景实际无效，已回退。
