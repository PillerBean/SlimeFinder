# SlimeFinder v3.12.3 区块判定速度

测试日期：2026-11-14  
测试对象：v3.12.3 源码构建的 `slime_chunk_bench`  
测试内容：**只测区块判定**，不测密度/图案匹配。  
结果：连续运行 3 次，表中取中位数。

## 测试环境

```text
CPU：AMD Ryzen 5 5600 6C/12T
GPU：AMD Radeon RX 6750 GRE 10GB（gfx1031，18 CU）
线程：12
```

## 方法

- CPU：`SlimeEngine::fillSlimeRowJava` / `fillSlimeRowBedrock`，按行并行，12 线程；
- GPU：`GpuScan::scanRectWords`，包含 GPU 判定和结果回读；
- 每档尺寸预热后测量，程序内多次取较优值；
- 整轮测试重复 3 次，最终取 3 次中位数；
- GPU 结果与 CPU 逐块对比：Java、Bedrock 均通过；
- 不计入搜索范围、结果筛选、密度窗口、图案匹配。

## 结果（3 次中位数）

| 平台 | 后端 | 区块数 | 耗时 | 判定速度 |
|---|---|---:|---:|---:|
| Java | CPU | 16,777,216（4096²） | 6.13 ms | **27.39 亿/s** |
| Java | CPU | 33,554,432（8192×4096） | 12.14 ms | **27.64 亿/s** |
| Java | GPU | 16,777,216 | 0.59 ms | **285.57 亿/s** |
| Java | GPU | 33,554,432 | 0.86 ms | **391.31 亿/s** |
| Bedrock | CPU | 16,777,216 | 47.80 ms | **3.51 亿/s** |
| Bedrock | CPU | 33,554,432 | 99.35 ms | **3.38 亿/s** |
| Bedrock | GPU | 16,777,216 | 8.65 ms | **19.41 亿/s** |
| Bedrock | GPU | 33,554,432 | 16.70 ms | **20.10 亿/s** |

## 对比

以 33,554,432 区块为例：

```text

Bedrock CPU  3.38 亿/s  →  GPU  20.10 亿/s   约 5.9 倍
```

以 16,777,216 区块为例：

```text
Java    CPU 27.39 亿/s  →  GPU 285.57 亿/s   约 10.4 倍
Bedrock CPU  3.51 亿/s  →  GPU  19.41 亿/s   约 5.5 倍
```

```text
Java    4.19M：CPU 31.15 亿/s，GPU 110.73 亿/s

```

## 稳定性

3 次运行中：

- Java CPU 33M：27.13 ~ 27.70 亿/s；
- Java GPU 33M：374.24 ~ 394.43 亿/s；
- Bedrock CPU 33M：3.36 ~ 3.53 亿/s；
- Bedrock GPU 33M：20.09 ~ 20.19 亿/s。

GPU 比 CPU 稳定；CPU 受频率和后台负载影响，存在约 5%~10% 波动。

## 为什么和以前的数字不一样

同一台机器上至少有三条不同的判定路径：

| 路径 | 用途 | Java 33M | Bedrock 4M |
|---|---|---:|---:|
| 引擎扫描 `slime_tests --bench` | 搜索实际使用的 AVX2 批量扫描 | **63.7 亿/s** | **2.52 亿/s** |
| 本报告 CPU 行判定 | 直接调 `fillSlimeRow*` | 27.6 亿/s | 3.4 亿/s |
| 本报告最早的单块判定 | 每区块单独调用 | 11.6 亿/s | 0.058 亿/s |
| GPU 打包字扫描 | GPU 判定 + 回读 | 391.3 亿/s | 20.1 亿/s |

所以：

- 历史文档中的 CPU 57.8 亿/s 是**引擎扫描路径**；当前同路径跑出 63.7 亿/s，没有变慢；
- 本报告的 27.6 亿/s 是**行判定路径**，不是同一条路径；
- 历史 GPU 110.9 亿/s 是旧版 `slime_ocl_probe` 路径；当前 GPU 打包字路径约 391 亿/s，实际更快；
- 首次 GPU 431 亿/s 是单次高值，重复测试中位数约 391 亿/s，差异来自时钟/负载波动，不是路径变化。

## 理论上限占比（估算）

以下为**指令吞吐上限估算**，不是厂商规格的严格峰值；CPU 按 Ryzen 5 5600 6 核全核约 4.2 GHz 估算。

| 项目 | 估算依据 | 估算上限 | 实测 | 占比 |
|---|---|---:|---:|---:|
| Java CPU | 每区块约 4 次 32 位乘法，1 次/核/周期 | 约 63~66 亿/s | 引擎 63.7 亿/s | **约 96%~100%** |
| Bedrock CPU | 捷径初始化 396 次乘法/区块，VPMULLD 2 条/核/周期、4 区块/向量 | 约 5.0~5.2 亿/s | 行路径 3.4 亿/s | **约 65%~68%** |
| Java GPU | 约 4 次乘法/区块，GPU 整数乘法吞吐约 2.7~2.8 T/s | 约 680~720 亿/s | 打包字 391.3 亿/s | **约 54%~57%** |
| Bedrock GPU | 396 次乘法/区块，同一整数乘法吞吐上限 | 约 70 亿/s | 20.1 亿/s | **约 29%** |

说明：

- Bedrock CPU 的估算对 `VPMULLD` 实际吞吐很敏感；若按 1 条/周期，上限约 2.5 亿/s，引擎路径会接近 100%，行路径会超过估算，因此表中采用 2 条/周期的估计；
- GPU 数据包含结果回读，占比是相对纯计算上限的端到端比例；
- GPU Java 的旧版 110.9 亿/s 约为理论上限的 15%，当前版本已提升到约 54%；
- 这些百分比用于判断“还有多少优化空间”，不宜作为跨硬件绝对性能承诺。


## 说明

- Java 判定路径明显快于 Bedrock；Bedrock 每个区块需要初始化 MT19937 状态，单块成本更高；
- GPU 数据包含结果回读，因此是端到端判定吞吐，不是纯内核时间；
- CPU 使用 12 线程；
- 以上均为原始区块判定速度，不是搜索匹配速度。
