# SlimeFinder v3.12.3 各模式效率（含匹配阶段）

测试日期：2026-11-14  
测试对象：v3.12.3 源码构建的 `slime_mode_bench`  
测试环境：

```text
CPU：AMD Ryzen 5 5600 6C/12T
GPU：AMD Radeon RX 6750 GRE 10GB
线程：12
范围：2048×2048 = 4,194,304 区块
Java 种子：12345
目标数量：200,000，不提前停止
```

表中是**完整搜索总时间**，已包含扫描、判定、匹配、结果收集；连续 3 次取中位数。

## 搜索模式

| 模式 | 平台 | CPU | GPU | 说明 |
|---|---|---:|---:|---|
| 图案 2×2 全绿 | Java | 17.47 亿/s | 15.68 亿/s* | 命中 436 |
| 图案 2×2 全绿 | Bedrock | 2.30 亿/s | 2.35 亿/s* | 命中 410 |
| 密度 g=5 thr=0.3 | Java | 9.17 亿/s | 13.13 亿/s | GPU 匹配生效 |
| 密度 g=5 thr=0.3 | Bedrock | 2.10 亿/s | 7.49 亿/s | GPU 匹配生效 |

`*` 图案模式本次没有实际启用 GPU，CPU/GPU 两列差异属于运行波动。

## 密度算法模式（CPU）

| 算法 | Java | Bedrock | 说明 |
|---|---:|---:|---|
| 精确 | 9.17 亿/s | 2.10 亿/s | 基准 |
| 分层 | 7.22 亿/s | 1.92 亿/s | 4M 小范围下未体现优势 |
| 快速估算 | 13.44 亿/s* | 12.66 亿/s* | 只扫描 65,536 个采样点，结果估算 |
| 精算采样 | 12.53 亿/s* | 1.19 亿/s* | 扫描 1,638,400 个点，结果仍非全量 |
| 保守 | 3.11 亿/s | 1.36 亿/s | 纯暴力，结果与精确一致 |

`*` 采样类算法的“全范围等效速度”按 4,194,304 / 总时间计算，但它们没有判定全部区块，不能当作精确模式的同口径结果。

## 匹配阶段占比

按引擎统计：

```text
match = totalMs - scanMs
match% = match / totalMs
```

| 模式 | Java CPU | Java GPU | Bedrock CPU | Bedrock GPU |
|---|---:|---:|---:|---:|
| 图案 2×2 | 61.8% | 59.8%* | 8.8% | 8.0%* |
| 密度精确 | 78.4% | 53.6% | 17.6% | 30.5% |
| 密度分层 | 83.6% | — | 22.9% | — |
| 密度快速估算 | 90.9% | — | 87.2% | — |
| 密度精算采样 | 42.9% | — | 3.9% | — |
| 密度保守 | 92.8% | — | 43.0% | — |

`*` 图案模式本次没有实际启用 GPU。

说明：

- Java 判定快，匹配阶段占比通常更高；
- Bedrock 判定慢，匹配阶段占比通常更低；
- GPU 密度匹配把匹配工作合入 GPU 阶段，表里的“match”主要是回读/结果整理，不是完整匹配耗时；
- 采样模式扫描区块很少，匹配占比会被放大；
- 保守模式匹配阶段最重。

## 环形模式

Java，2000×2000，R=128，内半径 24：

```text
AfkPlanner::plan：31.6 ms
完整规划/候选统计：约 89.3 ms
返回候选：8 个
```

环形模式不是平铺扫描全部区块，不能直接用“区块/秒”与其他模式比较。

## 结论

- 图案和密度精确模式中，Java 明显快于 Bedrock；
- Bedrock 的 GPU 密度匹配收益明显大于 Java；
- 分层模式在当前 2000² 范围没有加速；
- 快速估算模式最快，但结果是估算值；
- 保守模式最慢；
- 环形模式应看“每次规划耗时”，不应折算成平铺扫描吞吐。
