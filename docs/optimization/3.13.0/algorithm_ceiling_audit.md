# 3.13.x 算法上限审计（流水线前置门槛）

> 结论先行：目前**不能**证明所有算法都已经接近极限。
> 只有 Java CPU 判定路径有较强证据接近估计上界；Bedrock GPU 判定、Java GPU 纯内核、
> 以及匹配阶段仍缺少“去掉回读/宿主处理后的内核计时”，现在直接做 CPU/GPU 流水线会掩盖
> 算法本身的缺口。

## 1. 判定为“接近极限”的标准

本文采用保守标准，三项同时满足才算接近：

1. 去掉回读、结果转换、进度回调后的**内核/扫描本体**已达到指令或带宽估计上界的 **85% 以上**；
2. 已知的等价算法变体没有稳定超过 **10%** 的实现；
3. 继续调参、改写法只能得到噪声级变化，或历史上已经被多次否证。

只满足“端到端比之前快”不算接近极限；端到端还包含回读和宿主处理，不能代表算法本体。

## 2. 现有判定证据

来源：`docs/benchmarks/2026-11-14_chunk_determination_v3.12.3.md`。
其中上限是**指令吞吐估算**，不是厂商规格的严格峰值；CPU 按 Ryzen 5 5600 全核约 4.2 GHz，
GPU 按整数乘法吞吐约 2.7~2.8 T/s 估算。

| 组件 | 实测 | 估算上限 | 占估算上限 | 现阶段结论 |
|---|---:|---:|---:|---|
| Java CPU 判定（引擎 AVX2 路径） | 63.7 亿/s | 63~66 亿/s | **96%~100%** | 强证据接近极限 |
| Bedrock CPU 判定（行路径，3.13.7 前） | 3.4 亿/s | 5.0~5.2 亿/s | **65%~68%** | 3.13.7 改为 8 链后为约 4.2 亿/s，见下文更新 |
| Bedrock CPU 判定（行路径，3.13.7） | 4.2 亿/s | 5.0~5.2 亿/s | **81%~84%** | 已接近但未过 85% 门槛；单线程 8 链为当前最优 |
| Java GPU 判定（打包字，端到端） | 391 亿/s | 680~720 亿/s | **54%~57%** | 端到端含回读/集成，纯内核未单独计时 |
| Bedrock GPU 判定（打包字，端到端） | 20.1 亿/s | 约 70 亿/s | **29%** | 最大缺口；但已是当前 398 步捷径内核，不能直接下结论 |

必须注意：

- Java CPU 的 63.7 亿/s 是**引擎扫描路径**，29.3 亿/s 是 raw 行判定路径，两者不是同一条路径；
- Bedrock CPU 的引擎路径与 raw 行路径也不同，不能拿低于估算上限的 raw 数字去和引擎数字混比；
- GPU 的端到端数字包含结果回读和逐行集成，尤其 Java GPU 的回读占比不低，所以 54%~57%
  不能直接解释成“内核还有一倍空间”；
- 上表只能说明“哪些路径还没有足够证据”，不能说明“哪些路径一定还能提速一倍”。

## 3. 阶段计时进一步说明

当前工作树 8192×8192、target=1 的 GPU 会话日志：

| 路径 | GPU 会话总计 | CPU 等 GPU | 说明 |
|---|---:|---:|---|
| Java 图案 | 1.15 ms | 0.78 ms | 准备/回读约 0.37 ms，内核+等待约 0.78 ms |
| Bedrock 图案 | 35.90 ms | 35.50 ms | 内核/等待占 98.9%，回读准备约 0.40 ms |
| Java 密度 | 3.57 ms | 1.21 ms | 宿主命中筛选/回读约 2.36 ms |
| Bedrock 密度 | 39.57 ms | 37.16 ms | 内核/等待占 93.9% |

这些数字说明：

- **Bedrock GPU** 的端到端瓶颈是 GPU 内核本身，不是回读；在开始流水线之前，必须先把
  “内核本体到底离 70 亿/s 的估算上限多远”测清楚；
- **Java GPU 密度** 的宿主处理已经占约 2/3，属于流程优化候选，但也要先确认匹配/筛选
  本体的算法上限，否则流水线只是把等待挪到别处；
- **Java 图案** 小范围固定开销明显，但这是宿主准备/清零，不是内核算法；
- **Java CPU 判定** 已有较强证据接近上限，是可以考虑流水线重叠的候选，但匹配阶段还没有
  同等强度的上界证据。

## 4. 匹配阶段的缺口

目前没有和判定阶段同等级的严格 roofline。已知：

- CPU 密度使用行内 AVX2 窗口统计/命中掩码，历史已做过可分离卷积、两字 popcount、tile
  尺寸、缓冲区复用等实验；
- CPU 图案使用字级位并行，历史已做整行/分块/锚点批量；
- GPU 密度和图案是融合路径，端到端吞吐不能直接拆成“匹配算法吞吐”。

因此匹配阶段只能先建立内核级基准：

1. 固定一张已生成的位图，只跑匹配内核，去掉扫描、回读、结果转换和进度回调；
2. CPU 密度记录窗口数/s、每行周期、每个锚点周期；
3. CPU 图案记录锚点/s、每行周期；
4. GPU 密度/图案记录纯内核时间与回读时间，分别和位宽/带宽上限比较。

在这些数据出来之前，不应把“匹配阶段还能优化”当成既定事实。

## 5. 不应重复的历史否证

在 Bedrock GPU 上，以下方向已有实验记录，不能作为“还没试过”的新方案：

- 四链 / 每 work-item 4 区块：1610.59 → 1609.17 M/s，噪声内，已还原；
- 48/64 lane：探针局部略快，推进引擎后更慢，已回退；
- 多命令队列：1/2/3/4 队列无收益；
- 种子查表：比直接乘法更慢；
- `%10` 魔数乘法、64 位乘法拼装等微优化：无收益。

这意味着 Bedrock GPU 的 29% 缺口更可能是**串行 MT 链/占用率**层面的问题，而不是简单调参；
在找到内核级证据前，不能承诺可补齐。

## 6. 流水线前置门槛

建议顺序：

```text
A. 先做算法上限审计（本文档补齐内核级数据）
   A1. GPU 判定：纯内核 vs 回读/集成分开计时
   A2. GPU 匹配：纯内核 vs 回读/筛选/入堆分开计时
   A3. CPU 判定/匹配：固定位图微基准 + 指令/带宽 roofline

B. 对每个组件给出结论
   - ≥85% 上限且无已知 >10% 变体：标记“接近极限”
   - <85%：先做最小算法实验；失败则留痕，再决定是否接受现状

C. 只有当判定/匹配本体都已标记“接近极限”后，才做流程重叠：
   - CPU 扫描/匹配流水线
   - GPU 异步双缓冲/多队列
   - 等待时间隐藏
```

流水线优化本身不是算法优化；如果内核只到上限的 30%~60%，先做流水线会把真正的算法缺口
掩盖成“等待变少”，但总时间仍有很大一块没被解释。

## 7. 当前判定

| 项目 | 状态 |
|---|---|
| Java CPU 判定 | 有较强证据接近估算上限 |
| Bedrock CPU 判定 | 证据不足，历史实现已接近现有形态，但不能宣称极限 |
| Java GPU 判定 | 端到端 54%~57%，纯内核未拆分，不能判定 |

下一步先做内核级基准，不直接改产品流水线。

## 8. 60% 的分母澄清与四类上限

### 8.1 之前的百分比是什么分母

之前出现的 29%/54~57%/65~68%/96~100% 来自
`docs/benchmarks/2026-11-14_chunk_determination_v3.12.3.md` 的“理论上限占比（估算）”：

- 分母是**估算的指令/整数乘法吞吐上限**；
- CPU 按 4.2 GHz、整数乘法 1 次/核/周期等假设；
- GPU 按整数乘法约 2.7~2.8 T/s 估算；
- 实测分子是**端到端吞吐**，GPU 分子还包含回读、集成和宿主处理。

所以它不是严格的“有效指令数 ÷ 实测峰值 IPC”，也不是访存、节点或并行上限。
“60%”只是口头概括，**没有精确分母，不能作为算法是否到极限的结论**。

### 8.2 本机新增的峰值微基准

`build/slime_roofline_probe.exe` 单线程结果：

```text
vpmulld 峰值：8.84 G 次 256 位乘法/秒
memcpy 带宽：34.22 GB/s（读+写合计）
```

这些也是**单一微基准**，不是整机所有指令组合的 IPC。

### 8.3 四类上限分别怎么定义

| 类别 | 公式 | 分子 | 分母 | 当前状态 |
|---|---|---|---|---|
| 指令/运算 | 有效指令数 ÷ 峰值 IPC/运算率 | 算法必需的向量/标量指令数 | 同指令混合下的实测峰值 | 部分：只有 vpmulld 峰值，缺混合 IPC |
| 访存 | 有效字节数 ÷ 实测/理论带宽 | 位图、输出、回读字节 | 34.22 GB/s 实测拷贝带宽 | 扫描输出约 1.2%，不是瓶颈 |
| 搜索节点 | 有效节点数 ÷ 理论节点率 | chunk 数或窗口数 | 由该节点算法本身给出的下限 | 只有实测节点率，理论节点率仍依赖指令上限 |
| 并行 | 实际加速比 ÷ Amdahl/Gustafson 上限 | 多线程/多单元实测加速比 | 串行比例推导的上限 | CPU 已测；GPU 缺 profiler |

### 8.4 Bedrock CPU 8 链的粗算

单线程实测：

```text
14.9 ns/chunk = 67 M chunk/s
```

每 64 chunk 批：

```text
8 链 × 397 步 = 3176 个链步
每个链步约 xor + shift + mul + add = 4 个向量指令
约 198.5 个向量指令/chunk
```

由此：

- **纯 vpmulld 分母**：每 chunk 49.625 次乘法，8.84 G/s → 5.61 ns/chunk；
  实测 14.9 ns ⇒ 仅 37.6%。但这个分母漏掉了 xor/shift/add，不能直接当作整段指令上限。
- **总向量指令分母**：198.5 指令/chunk ÷ 14.9 ns ≈ 3.17 向量指令/cycle（按 4.2 GHz）。
  如果该机器混合峰值是 3.2~4 指令/cycle，则实际约 79%~99%；仍缺混合指令峰值实测。
- **访存分母**：扫描输出 1 B/chunk，4.19M chunk 约 4.0 MB；9.8 ms 对应约 0.41 GB/s，
  仅为 34.22 GB/s 的约 1.2% ⇒ 访存不是瓶颈。
- **节点分母**：12 线程约 4.2 亿 chunk/s，1 线程 67 M/s；节点率没有独立于指令上限，
  不能与指令利用率重复相加。
- **并行分母**：线程 1/2/4/6/8/10/12 的 Bedrock 4M 扫描时间为
  64.17/33.72/17.60/13.21/13.89/10.93/11.36 ms，
  加速比 1/1.90/3.65/4.86/4.62/5.87/5.65×。
  相对 12 逻辑线程效率约 47%，相对 6 物理核约 81%；按 12 线程拟合 Amdahl 串行比例约 8.3%，
  实际 5.65× 约为 Amdahl 上限 9.8× 的 58%（测量有噪声，10 线程反而略快）。

### 8.5 还不能下的结论

- Bedrock CPU：**混合指令峰值未测**，不能把 37.6% 或 79%~99% 当成最终结论；
- GPU：缺 kernel-only 计时和设备内峰值微基准，29% 仍是端到端/估算口径；
- 匹配阶段：缺固定位图的纯内核节点率；
- 并行：GPU 并行上限没有 profiler；CPU 12 线程已接近物理核上限，但 SMT 调度仍有约 10% 抖动。

因此下一步应先补“混合指令峰值、GPU kernel-only、匹配节点率、稳定 Amdahl 拟合”，
再谈 CPU/GPU 流水线。
