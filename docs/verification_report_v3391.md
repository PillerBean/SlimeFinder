## 二、1.3 细节（为什么会出现 158%）

`startSearch()` 里 `prepareBuildRun()` 负责分段，但**启动任务用的是未裁剪的 `opt`**（minZ/maxZ = 用户范围）：

1. 第 1 段：引擎按**全范围**跑完（`m_buildDoneChunks` 一次就拿到 100% 的行数；`handleBuildBandFinished` 再加一次 `liveScannedCount` ⇒ 计数已超过范围内区块数）；
2. 第 2…N 段：每段只跑自己那 4096 行，而这 4096 行早已被第 1 段写入的缓存覆盖 ⇒ 引擎全部走「已覆盖跳过」分支，只累加「已跳过」，进度继续被抬高 ⇒ 用户看到 **158%** 且「不断重复记录」；
3. 若此时再叠加陈旧完成事件（runId 未校验）或段下标越界，就出现 1.2 的闪退。

修复后（自检日志实测）：

```
[构建] 段 1/16 结束：已记录累计=8396800  已跳过累计=0        保存=1
[构建] 段 2/16 启动：Z(4096~8191)
...
[UI自检] 多段构建：段数=16 已记录=134348800 已跳过=0 最大进度=100.00% 非单调=0
```

（134,348,800 = 16 段 × 4096 行 × 2048 列 + 末段重叠，与范围内区块数一致；「已跳过=0」说明没有重复记录。）

## 三、1.2 细节（为什么开详细日志就不崩）

| 位置 | 旧行为 | 新行为 |
|---|---|---|
| 分块循环入口 | 每个工作线程各自 `opt.cache->covers(tileRect)`（与其它线程的 `mergeRaw` 并发） | 启动线程池**前**串行预计算 `chunkCoveredFlags[]`，工作线程只读该数组 |
| 行填充 | `fillFromCacheRow()` 读缓存位图（并发） | 构建模式**不做位图直取**（`livePhase` 恒为「新区域扫描」），值重算后由 `setBit` 去重 |
| 归并准入 | 工作线程内 `opt.cache->covers(sub.region())` | 改用同一份预计算标志（锁内只做归并本身） |
| 完成回调 | 先按 `m_buildActive` 分支、后校验 runId ⇒ 陈旧事件进入构建处理 | **先校验 runId**（陈旧事件直接丢弃并记日志），再进入构建分支 |
| 段下标 | 直接下标访问 | 越界即记录并立即收尾（不再 UB） |

## 六、已知限制（如实声明）

1. 「启动时自动检查 GPU 状态」**默认关闭**：无/异常 OpenCL 驱动环境下，驱动层初始化可能原生崩溃（非 C++ 异常），这是 v3.2.1 起就存在的取舍；开启后若驱动异常，程序仍会在启动阶段崩溃——这属于驱动问题，日志会记录探测过程。
2. 构建模式的进度百分比按**去重口径**截顶（引擎「已记录」含块间重叠行），因此不会出现 >100%。
3. 构建模式仍**仅支持基岩版**（缓存位图语义），界面已禁用 Java 版并说明原因。
