# SlimeFinder 优化方案登记簿（2026-11-06）

本文件记录**所有被实测过的优化方案**：已整合、已验证待整合、已否证。
数字都来自本机（Ryzen 5 5600、AVX2、无 AVX-512）的探针或 `--bench`，标注了测量方式。

## 二、已验证、待整合（有明确收益）

| 方案 | 收益（实测） | 适用 | 备注 |
|---|---|---|---|
| **可分离位图 AND**（行内 W-1 + 行间 H-1） | 5×5 **1.8~2.4×**、12×12 **4.7~7×**、32×32 **11~17×** | 每行图案相同的矩形 | 真实公式数据复核通过（5×5 2.5×、32×32 17.2×） |
| **行内「倍增前缀 AND」**（log2 W 次移位） | 32×32 再由 11.1× 提到 **14.6×**；64×64 25.3× → 38.2× | 同上 | 移位次数 W-1 → ⌈log2 W⌉ |
| **行间「稀疏表」O(1) 查询** | 32×32 提到 **22.0×**；64×64 提到 **93.4×** | 同上，且 H 较大 | 预计算 log H 层；小 H（≤8）反而变慢，需按 H 选路 |
| 双点筛选（位测试形式） | 1.39 ns/锚点（m≥200 时曾优于全偏移 AND） | 大图案 | 有了可分离后优先级下降；仍可作为「图案不规则」时的备选 |

三种组合的实测对比（ns/锚点，只统计窗口落在字内的锚点）：

| 图案 | 全偏移 A | 可分离 B | 倍增行内 C | 倍增+稀疏表 D |
|---|---|---|---|---|
| 3×3 | 0.053 | **0.042** | 0.047 | 0.080 |
| 5×5 | 0.123 | **0.068** | 0.070 | 0.116 |
| 12×12 | 0.819 | 0.175 | **0.159** | 0.173 |
| 32×32 | 8.761 | 0.792 | 0.600 | **0.398** |
| 64×64 | 1432.3 | 56.62 | 37.46 | **15.34** |

结论：**小图案用 B（可分离）最省，中大型用 C，H 较大用 D**。三条都是逐位等价（命中数完全一致）。

## 三、已否证（不要再投入）

| 方案 | 实测结论 |
|---|---|
| 哈希二次差分 | 哈希只占 4.2%，上限 4% |
| 17 位分块查表 LCG | 正确但 1.82 ns/区块（直接乘 1.41、AVX2 0.86） |
| nibble 求和 mod 5 | 4.29 vs 1.31 ns（慢 3.3×） |
| 多级筛选 / 双点哈希用于 m ≤ 150 | 位图 AND 全面胜出 |
| 开放寻址哈希表做双点 | 11.03 vs 0.43 ns/锚点（慢 25×） |
| 差分递推生成 u(x) | 1.69 vs 1.23 ns（慢 37%），且引擎没有 800MB 表的前提 |
| q 奇偶预筛 | 2.8× 慢（`%10` 与 `%5` 都只有一次魔术乘） |
| q 位敏感性分层 | 翻转 x 任意一位，q 高 8 位 100% 改变（雪崩，无分层） |
| 位集化中间缓冲（匹配读） | 逐锚点比字节数组慢 1.8×；引擎已有 64 锚点字并行 |
| FFT / 卷积 | AND 只需 0.4 次操作/锚点，FFT 不可能更便宜 |
| Roaring Bitmap | 10% 均匀密度无收益 |
| LCG jump-ahead | 按行分块天然不重叠 |
| GPU 基岩内核 | 实测比 CPU 慢 6.3× |
| AVX-512 | 本机无此指令集 |
| 大页 / perf / `-O3 -funroll-loops` | Windows + MSVC 平台不适用（已用 `/O2 /GL`） |
| 逆向求解（Z3/SMT、线性 Δ 结构） | m=4 要 5~14 s；m≥9 不收敛；且 m≥16 的图案在真实世界**没有解**（4×4 期望 1.4e-3 个、5×5 期望 1.4e-12 个） |

## 四、算过但**不值得做**的

| 想法 | 量化理由 |
|---|---|
| 扫描与匹配融合（省位图往返） | 1 亿区块位图仅 12.5 MB，读写约 1.3 ms，而计算 86 ms ⇒ 上限 ~1.5% |
| 非临时存储（`_mm_stream`）写位图 | 同上，位图流量本来就微不足道 |
| 结果收集路径优化（海量命中） | 只在 `targetCount=∞` 才成为瓶颈（3.5.0/3.6.19 都是 6.7 s）；GUI 默认要前 N 个，用不到 |

## 五、探索方向（还没测、值得排队）

1. **把 B/C/D 三条路径 AVX2 化**：现在探针是纯标量；用 `_mm256_and_si256` 一次处理 4 个字，
   预期在 AND 受限的大图案上再快 2~3×。
2. **不规则图案的分解**：按「不同行图案的种数」分组做行内 AND（成本 = 种数×W + H），
   让棋盘/混排图案也能吃可分离的红利。
3. **列主序位图**：把位图转置成「按列存」，行内 AND 变行间 AND，可能对高瘦图案更友好
   （需要先量化转置成本）。
4. **扫描侧残余**：0.86 ns/区块里还有多少是打包/循环开销？用 VTune 风格的手工分段计时再切一刀。
5. **密度模式的一般阈值**：SIMD 窗口和之后还剩多少？当前 10000² 单核 9.3 ms（匹配）已接近扫描的 1/12，
   但 `k=g²` 快路是 5.8 ms/1 亿，说明还有空间。
6. **基岩版换算法**：MT 递推是串行链，唯一可能是「预计算 + 查表」或 GPU 重写内核（已证 GPU 现状更慢，
   但那是旧内核）。

### 附：本轮探索方法的说明

常规手段（SIMD 宽度、查表、位图、哈希、多级筛选、SMT 逆解）基本试完，剩下的收益都来自
**算法结构**而不是指令级优化 —— 可分离 AND / 倍增 / 稀疏表这三条就是「用结合律换掉重复工作」的产物。
后续探索会按「想到一个 → 写探针 → 量数据 → 记录结论」的节奏走，不追求每轮都出成果。

## 六、探索轮（2026-11-06 晚）：匹配侧继续挖，三个新结果

### 6.1 AVX2 化「倍增行内 + 逐行行间」—— 新最优

| 图案 | 全偏移（标量） | 倍增+逐行（标量） | **AVX2 倍增+逐行** | 相对全偏移 |
|---|---|---|---|---|
| 3×3 | 0.053 | 0.048 | **0.014** | 3.8× |
| 5×5 | 0.123 | 0.082 | **0.017** | **7.2×** |
| 12×12 | 0.819 | 0.166 | **0.040** | 20× |
| 32×32 | 8.761 | 0.613 | **0.104** | **84×** |
| 64×64 | 1432.3 | 38.08 | **5.053** | **283×** |

命中数与标量完全一致。这就是目前严格匹配的最优形态：**行内倍增 + 行间逐行 AND，全部 AVX2**。

### 6.2 行间「倍增」（垂直方向也做 2 的幂合并）—— 更慢，放弃

| 图案 | 行间逐行（AVX2） | 行间倍增（AVX2） |
|---|---|---|
| 5×5 | 0.023 | 0.092（慢 4×） |
| 32×32 | 0.128 | 0.287（慢 2.2×） |
| 64×64 | 7.680 | 11.647（慢 1.5×） |

原因：每层 G[k] 都是「几乎一张位图」大小的数组，6 层就 6 MB，直接把 L2 打爆；
而逐行版本每次只读当前窗口的 gz 行，天然局部。**垂直方向不要做倍增。**

### 6.3 整行批量 API（`scanRowJava`）—— 比逐字调用慢

| 写法 | ns/区块 |
|---|---|
| 逐字调用 `slimeMask64`（引擎现用） | **0.864** |
| 整行批量 `scanRowJava`（常量行内建一次） | 1.050 |

`/GL` 全程序优化已经把 `slimeMask64` 内联进循环并把常量提出去了，批量入口反而因为
「每字要处理尾块」的分支而更慢。**保持现状。**

## 七、由此得到的判断

1. **匹配侧已经基本没有油水**：典型图案（≤12×12）的匹配成本已降到 0.02~0.04 ns/锚点，
   而扫描是 0.86~1.1 ns/区块 —— 匹配只占 **2~4%**。继续优化匹配对端到端没有意义
   （唯一例外是 64×64 这种现实中不会出现的图案）。
2. **剩下的 1.28× 在扫描环节**：纯内核 0.864 ns/区块 vs 引擎实测 1.1 ns/区块，
   差在行循环/段循环/取消检查/位图写回这些「框架」上，属于工程打磨而非算法。
3. 因此下一轮的重点应放在**扫描循环的结构开销**（例如把「段」在行外预计算、批量提交行、
   减少每行的边界判断），而不是继续找匹配算法。

### 6.4 扫描循环「去分支」重构 —— 实测 **没有收益**

把逐字循环里的「对齐判断 + `min()` + `if (acc)`」摘出去，改成
「前导残字 → 整字直路（无分支）→ 尾部残字」：

| 版本 | 10000² 单核扫描（5 次取最小） |
|---|---|
| 重构前 | 111.1 ~ 112.0 ms |
| 重构后 | **110.9 ms**（中位 111.9） |

差异在噪声内（±1%）。说明引擎与纯内核之间那 0.86 → 1.1 ns/区块的差距**不是循环分支造成的**，
更可能是位图内存流量/缓存与测量口径（纯内核测的是 4 MB 缓冲，引擎是 12.5 MB 位图 + 每轮新分配）。

（该重构仍保留：逐位等价、略微更干净，且多核下从 18.6 → 17.0 ms 有过一次可见改善，但需更多样本确认。）

### 6.5 下一步：给引擎装 rdtsc 分段计时

既然循环结构不是瓶颈，下一步要在**引擎内部**直接量「行循环 / 内核调用 / 位图写回」的耗时，
而不是继续靠外部 bench 猜。计划：`SLIME_PROFILE=1` 时用 `__rdtsc()` 累加三段（行准备、
`slimeMask64` 调用、位图 OR 写回），搜索结束后打印 ns/区块 —— 一次就能定位剩余 20% 在哪。

### 6.6 rdtsc 实测结果（SLIME_PROFILE=1）

在引擎的行内循环上挂了 `__rdtsc()`，10000×10000 单核实测：

| 指标 | 数值 |
|---|---|
| **行内核（`slimeMask64` 调用 + 位图 OR 写回，仅整字部分）** | **0.889 ns/区块（3.91 周期）** |
| 扫描阶段总耗时 | 1.16 ns/区块 |
| 差额 | **0.27 ns/区块（约 23%）** |

结论：**内核本身已经是 0.89 ns，和探针的 0.864 基本一致**；剩下的 23% 完全在「行循环之外」——
每行的 `javaRowBase`、`grid.rowBits`、段遍历、任务调度、位图分配/清零、页错误等框架开销。
按 10000 宽的行算，每行要背约 2700 ns 才解释得通，这说明开销不在「每行几条指令」，而在
**分配/清零/页错误/线程调度**这一层。

### 6.7 下一步（明确）

1. 用同样的 rdtsc 手法把「扫描阶段」再切一刀：包住整个行循环，看差额到底在
   「行循环外层」还是「分配/清零」。
2. 若确认是位图分配/清零：改用**池化缓冲**（跨搜索复用同一块位图，只清用到的行），
   预计能收回大部分 23%。
3. 若确认是调度：调整 `rowBatch` 粒度做 A/B。

## 八、探索轮 2（2026-11-06 晚）：换三个轴，两个否证 + 一个正面确认

### 8.1 位图分配池化 —— 只值 1.2%，不做

| 做法 | 每次搜索耗时 | ns/区块 |
|---|---|---|
| 新分配 + 清零（12.6 MB） | 1.86 ms | 0.019 |
| 池化后仅 memset | 0.49 ms | 0.005 |

最多省 **0.014 ns/区块 = 扫描的 1.2%**，抵不上池化带来的状态管理复杂度。**放弃。**

（也说明上一轮 rdtsc 发现的 23% 缺口**不是分配/清零造成的**，需要另找。）

### 8.2 不规则图案（每行图案不同）的分组可分离 —— 更慢，否证

正确形态：为每个「行图案 dz」单独生成一份行内匹配位图 R[dz]（共 gz 份），
锚点结果 = AND_{dz} R[dz][z+dz]。实测：

| 图案 | 全偏移 AND | 分组可分离 | 倍率 |
|---|---|---|---|
| 8×8，2 种行图案 | 0.478 | 0.749 | **0.64×（更慢）** |
| 8×8，8 种行图案 | 0.462 | 0.664 | 0.70× |
| 32×32，2 种 | 7.291 | 7.953 | 0.92× |
| 32×32，32 种 | 8.094 | 6.910 | 1.17× |

原因：gz 份位图（每份都是一整张位图大小）把缓存打爆，多花的写带宽抵消了省下的移位。
**结论：可分离 AND 只在「所有行图案相同」（全绿矩形、单行、竖条）时有红利，不要推广到不规则图案。**

### 8.3 线程扩展性 —— 正常，无需改

`--bench` 的 Java 10000² 单核 111 ms → 多核 17.2 ms = **6.45×**（6 物理核 + HT），
接近线性，说明行分块调度没问题。CLI 侧因为进程启动 + 结果输出占比太大，不适合用来量扩展性。

### 8.4 当前仍未解释的：扫描阶段 23% 缺口

已知：内核 0.889 ns/区块（rdtsc）vs 扫描 1.16 ns/区块；分配只占 1.2%；循环结构重构无收益。
剩下的候选：跨编译单元调用 `slimeMask64` 的开销（每次 64 区块重建约 10 个向量常量）、
每行的段/行基座/边界处理。下一轮可用「每次调用处理 2~4 个字」的批处理版本再试一次
（上一轮整行批处理因尾块分支变慢，这次只处理「整字对齐的中间段」，不带尾块逻辑）。

## 九、探索轮 3（2026-11-06 深夜）：批处理内核 + 基岩加链，两条都负

### 9.1 整字批处理内核（`scanWordsOr`）—— 反而慢一倍 ❌

| 写法 | ns/区块（10000² 整字部分） |
|---|---|
| 逐字调用 `slimeMask64` + `\|=`（引擎现用） | **0.866** |
| 整字批处理 `scanWordsOr`（常量整批建一次、直接 OR 进位图） | 1.672 |

原因：`/GL` 已经把逐字调用内联并把常量提到循环外，手写批处理反而限制了编译器的调度
（16 个链的状态 + 常量超过寄存器数量）。**结论：内核调用形态已经最优，不要改写。**
`scanWordsOr` 保留在 FastJava 里以备后用，但引擎不调用。

### 9.2 基岩版加链（48 / 64 lane）—— 探针有微弱优势，进引擎是负收益 ❌

探针（1M 区块，逐位一致）：

| 配置 | ns/区块 |
|---|---|
| 32 lane（8 链，现用） | 28.80 |
| 48 lane（12 链） | 34.67（更慢，寄存器溢出） |
| 64 lane（16 链） | **27.10（快 6%）** |

但在引擎里实现 `draw64` + `scan64` 后实测 **143~144 ms vs 基线 132 ms（慢 8%）**，
已回退。说明探针的孤立热点和真实调用上下文（编译单元、寄存器压力、cache）差别很大，
**基岩侧不要再加链**。

### 9.3 本轮结论

「内核/批处理」这条线到此为止：逐字调用已经是最优形态。剩余 23% 缺口仍未定位，
但从 9.1 看，不太可能来自调用开销。下一步换轴：**环形规划（`--bench-ring`）**，
它是目前唯一没被深挖过的热路径（2000×2000 约 28 ms，粗扫占 25 ms）。

### 9.4 环形规划基线（--bench-ring 2000，2000x2000，R=128/内 24）

| 阶段 | 耗时 |
|---|---|
| 谓词全网格（4.08M 区块位图） | 10.1 ms |
| 1:64 权重网格 32x32 | 2.2 ms |
| **AfkPlanner::plan 合计** | **36.0 ms** |
| └ 粗扫（step=4，250k 中心） | **33.3 ms** |
| └ 精修 256 个候选 | 35.2 ms（含在上面） |

粗扫每中心约 130 ns，来源是 nnulusBoth 按行查前缀和（R=128 → 每中心约 256 次查表）。
**下一步实验**：把前缀和按 4×4 降采样（500x500），粗扫每中心只需 ~64 次查表（4× 加速），
精度误差只影响排名、且后面还有 256 个精确精修兜底；用 --bench-ring 对比候选集与耗时即可判定。

### 9.5 环形粗扫：预算磁盘轮廓 —— 无收益（但保留了代码）

把「每行半宽」按半径预算成表（原来每个候选都要重算 sqrt），粗扫从 33.3 → 31.5~33.0 ms，
**在噪声内**。说明 sqrt 不是瓶颈。

粗扫成本随区域面积线性增长（每中心 110~130 ns 恒定）：

| 区域 | 中心数 | 粗扫 | 每中心 |
|---|---|---|---|
| 500² | 250k（封顶） | 8.2 ms | — |
| 1000² | 250k | 15.0 ms | 60 ns |
| 2000² | 250k | 27.4 ms | 110 ns |
| 4000² | 327k | 77.5 ms | 237 ns |

每中心约 300 行查表 → 约 1.6 周期/行，已经接近「两次前缀查表 + 加减」的标量极限，
且与表大小无关 ⇒ **不是内存带宽/延迟瓶颈，是行循环本身**。
再快只能上 AVX2 gather（把 8 个 dz 的两次查表用 gather 做掉），预计 2~3×，
需要单独 AVX2 编译单元；考虑到环形规划只占一次搜索的 ~30 ms（扫描是 110 ms），**优先级低**。

## 十、落地：v3.6.20（2026-11-06）

本轮把「有明确收益」的一条改进正式整合：

| 改进 | 实测 | 说明 |

## 十一、基岩版真突破：8 lane/链（v3.7.0）

用户问「基岩太慢，能不能用更简单算法拟合 + 例外表」。先验证拟合路线（探针 opt_probe17）：

| 简化算法 | 与真实判定的符合率 | 需例外表覆盖 |
|---|---|---|
| 截断到 200 步 | 82.06% | 17.94% |
| 截断到 300 步 | 82.07% | 17.93% |
| 少 1 步（396） | 82.03% | 17.97% |
| 跳过 twist | 82.01% | 17.99% |
| 跳过 temper | 82.05% | 17.95% |
| 纯哈希 splitmix32 | 82.04% | 17.96% |

82% 正是「10% 正类 + 完全独立预测」的期望值 ⇒ **简化算法零信息量**；
例外表要覆盖 90% 的区块，等于直接存位图（而生成位图仍要跑 MT）。**拟合路线否证。**

真正的加速点是实现细节：**FastMt 每条链只用了 256 位寄存器的低 4 个 lane**，
而 init 递推与 twist 全是 32 位运算，8 个 lane 可以同时算 8 个区块。

| 实现 | ns/区块 | 吞吐 |
|---|---|---|
| 4 lane/链（原实现） | 42.15 | 23.7 M/s |
| **8 lane/链（4 链）** | **21.40** | **46.7 M/s（1.97×）** |

落地到引擎（draw32x8，逐位一致，内核测试 ALL PASS）：

| 基准 | 改前 | 改后 | 提升 |
|---|---|---|---|
| 基岩 2000x2000 单核扫描 | 132 ms | **97.5 ms** | **1.35×** |
| 基岩 2000x2000 多核扫描 | 28.7 ms | **15.5 ms** | **1.85×** |
