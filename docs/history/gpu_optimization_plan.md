# GPU 方向：历史踩坑、现状实测与优化方案（2026-11-06）

## 一、我们踩过的坑（来自 docs/gpu_phase1/2_report.md、architecture §9、src/gpu/experimental/README.md）

| # | 坑 | 表现 | 结论 |
|---|---|---|---|
| 1 | **位图坐标用绝对坐标** | GPU 回写字索引/移位越界，写坏内存 | 必须用行内相对坐标 `rx = x - x0`，单元测试 [13] 专门守这条 |
| 2 | **内核源码嵌入时转义错误** | `embed_kernel.cmake` 在换行处写入了 C 转义，把换行注入内核字符串 → OpenCL 编译报 `unknown type` / 非法 UTF-8 | 嵌入脚本要逐字节校验（现在已有回归） |
| 3 | **Ninja 依赖跟踪失效（中文 cl.exe）** | `/showIncludes` 的 GBK 前缀与 Ninja 规则不匹配 → 头文件依赖全丢 → 改了头不重编 → 结构体布局/虚表不一致 → `0xC0000005` 与**驱动侧堆损坏** | 不是算法问题；必须 `--clean-first` 全量重建 |
| 4 | **驱动初始化可原生崩溃** | 无/异常 OpenCL 驱动时 `LoadLibrary`/初始化直接崩（try/catch 抓不到），后台线程探测也一样 | GPU 默认关闭；只在用户勾选时同步探测一次；另有启动崩溃环检测 |
| 5 | **Java 向量化 LCG 内核与引擎不一致** | 自检显示位图数千处不一致（`lcg自洽=0`） | 48 位乘法在 GPU 上要拆 32 位做，容易写错；建议逐区块标量 LCG 起步再向量化 |
| 6 | **密度匹配内核半成品** | 编译错误 + 结果缓冲尺寸/去重表问题 | 已停用（`src/gpu/experimental`，不参与构建） |

## 二、本机现状实测（RX 6600 / gfx1031，18 CU，OpenCL 2.0，10 GB）

`slime_ocl_probe.exe`（今晚运行，一致性用例全 PASS）：

| 场景 | GPU | CPU 12 线程 | 对比 |
|---|---|---|---|
| Java 268M 区块 | **27.2 ms（9.85 G/s）** | 161.6 ms（1.66 G/s） | **GPU 快 5.9×** |
| Java 1M 区块 | 0.4 ms（2.59 G/s） | 1.3 ms（0.75 G/s） | 快 3.5× |
| **Bedrock 4.19M 区块** | **136.2 ms（30.8 M/s）** | 708.8 ms（5.9 M/s，探针用的是标量基线） | 探针口径 GPU 快 5.2× |

但**引擎级**（完整搜索，CPU=全核）：
- Java 8192²：CPU 扫描 12.2 ms，**GPU 扫描 103.7 ms** → GPU 反而慢 8.5×
- Bedrock 4096²：CPU 扫描 53.6 ms，GPU 扫描 522.9 ms → GPU 慢 10×

结论：**裸内核不慢，慢在集成路径与基岩内核本身**。

补充实测（探针 opt_probe19）：
- 引擎式「逐区块字节→位图」转换：67M 区块 13.19 ms（0.197 ns/区块）
- 改为「GPU 直接输出打包 64 位字、CPU 只按字 OR」：0.52 ms → **该步骤快 25.5×**

也就是说：转换只解释 103.7 ms 里的 13 ms，剩下的大头是**每瓦片的启动/回读/逐行集成与缓存区间处理**，
需要下一个探针把「瓦片内核算」「回读」「逐行集成」三段分别计时。

## 三、候选优化方案

### P1（低风险，先做）GPU 输出直接用引擎的位图字格式
- 现状：内核输出每区块 1 字节，CPU 逐区块打包；缓存区间还要逐行判断。
- 改法：内核按「一行 64 位字」组织输出（每个 work-item 算一个字的 64 个区块），
  CPU 只做 `rowW[w] |= word`。转换步 25× 已实测；预计引擎级 Java GPU 扫描从 103.7 → 60~70 ms。
- 可移植性：纯整数、无 64 位原子、无扩展，OpenCL 1.2 即可。

### P2（高价值，主攻）基岩内核重写
- 现状 30.8 M/s，而 CPU 单核已达 46.7 M/s（多核 ~250 M/s）⇒ GPU 在基岩上**没有存在意义**。
- 改法：一个 work-item 负责一个区块，寄存器里跑 396 步 init 递推（只用 2 个 32 位变量），
  然后 twist + temper + `%10`；全程 uint32，无 64 位、无分支发散、无 local memory。
- 预期：18 CU × 64 lane × ~2.4 GHz ≈ 2.7e12 次 32 位乘/秒，每区块 396 次乘 ⇒ 理论上限 ~6.9 G/s；
  按 20~30% 效率估 **1.5~2 G/s**，相对现在 30.8 M/s 是 **50~60×**，相对 CPU 全核 ~250 M/s 是 **6~8×**。
- 可移植性：只用 OpenCL 1.2 核心特性；workgroup size 由 `CL_KERNEL_WORK_GROUP_SIZE` 运行时选取。

### P3（可移植性框架）设备无关的运行时策略
- 只用 OpenCL 1.2 核心：无 subgroups、无 64 位原子、无 vendor 扩展；
- 每个设备运行时查询 CU 数 / 最大工作组 / 本地内存，选择 workgroup 与每线程区块数；
- 内核二选一：`v1`（每 item 1 区块，通用）与 `v4`（每 item 4 区块，用 uint4 提高 ILP），失败自动回退；
- CPU 兜底保持不变（现有 `GpuScan::available` + 异常兜底 + 崩溃环检测）；
- 驱动异常的防御：维持「默认关闭、勾选才探测」的现有策略。

### P4（暂不做）密度匹配上 GPU
- 上次在 `src/gpu/experimental` 半途而废（编译错误 + 结果缓冲问题），且 Java 密度匹配 CPU 已到 0.02~0.06 ns/锚点，
  GPU 收益不确定，优先级最低。

## 四、建议顺序

1. 先用探针把引擎级 GPU 路径三段拆开计时（估算/回读/集成），确认 P1 的真实收益；
2. 做 P2（基岩内核重写）——这是唯一能显著改变「基岩版慢」的路径；
3. 同步把 P3 的可移植性框架落进内核选择逻辑（先保证 NVIDIA/Intel/AMD 都能跑，再谈特异优化）；
4. P1 与 P2 都稳定后，再考虑把 GPU 默认勾选打开。

## 五、风险与验证

- **正确性**：所有 GPU 内核必须与 CPU 逐位一致（现有 `slime_ocl_probe` 的一致性用例 + `--unit [13]` 引擎等价 + 117 参考实现）；
- **稳定性**：无 OpenCL 驱动的机器上必须零接触；驱动异常要能回退 CPU 并记录日志（现有机制保留）；
- **可移植性**：至少在 AMD（本机）、NVIDIA、Intel 三类设备上各跑一次一致性 + 基准（如果条件允许）。

## 六、实测进展（2026-11-06 晚，v3.7.1）

### 6.1 已落地的最大收益：基岩 GPU 内核换用 398 步捷径

原内核 scan_bedrock_slime 调的是 edrock_is_slime（完整 624 步 init + 624 步 twist，
且把 624 个 uint 放在私有内存数组里）；而同一文件里早就有代数等价的
edrock_is_slime_fast（只需 init 到 mt[397]，纯寄存器、398 步）。
改成后者后（v3.7.1）：

| 指标 | 改前 | 改后 | 提升 |
|---|---|---|---|
| Bedrock GPU 基准（4.19M 区块） | 136.2 ms（30.8 M/s） | **2.6 ms（1607 M/s）** | **52×** |
| 引擎级 Bedrock 4096² 扫描 | 522.9 ms | **41.6 ms** | **12.6×** |
| 引擎级 Bedrock 4096² 总耗时 | 540.3 ms | **57.2 ms** | 9.4× |

正确性：slime_ocl_probe 全部一致性用例 PASS（含 Bedrock 1.05M 区块全量比对）、
--unit [13] GPU 引擎等价 PASS、117/117 参考、GUI 自检（GPU 开）0 FAIL。

### 6.2 下一步（Java 侧集成）

Java 裸内核 9.85 G/s（GPU）已经比 CPU 全核快 5.9×，但**引擎级** GPU 扫描 112.4 ms
（CPU 14.1 ms）—— 差距不在内核，在集成：瓦片切分 + 逐区块字节→位图转换（实测 13 ms/67M）
+ 逐行缓存区间处理。下一步按 P1 让内核直接输出「按行的 64 位打包字」，预计把引擎级
Java GPU 扫描从 112 ms 压到 30 ms 量级。

## 七、3.7.1：GPU 有效工作占比（2026-11-06）

用 SLIME_PROFILE=1 给引擎 GPU 阶段装了 rdtsc 分段计时，定位到瓶颈**不在内核**：

| Java 8192²（67M 区块） | 改前 | 改后 |
|---|---|---|
| 内核 + 回读 | 0.239 ns/区块（16 ms） | 0.248（16.6 ms） |
| **逐行集成（CPU）** | **0.967 ns/区块（65 ms）** | **0.084（5.6 ms）** |
| GPU 扫描合计 | 105.1 ms | **31.7 ms** |

| 基岩 4096²（16.7M 区块） | 改前 | 改后 |
|---|---|---|
| 内核 + 回读 | 0.638 | 0.638 |
| 逐行集成 | 1.241 | **0.081** |
| GPU 扫描合计 | 40.8 ms | **16.3 ms** |

改法：回读字节 → 位图的转换改用 SSE2 _mm_movemask_epi8（x64 基线指令，无需 AVX2），
一次出 16 位，替代「逐区块移位+或」的串行依赖。

**GPU 占用率上限**（新增设置项，10~100%，下次搜索生效）：
引擎在瓦片之间按占空比休眠（SLIME_GPU_MAX_PCT），实测线性生效 ——
Java GPU 扫描 100% = 31.2 ms、50% = 60.9 ms、25% = 122.0 ms；结果一致性不受影响。

## 八、3.7.2：双缓冲流水线（2026-11-06）

3.7.1 之后 GPU 路径仍是「扫完一块 → CPU 集成 → 再扫下一块」的纯串行，集成期间 GPU 空闲。
改为**双缓冲流水线**：GPU 扫第 N+1 块的同时，CPU 集成第 N 块。

瓦片大小做了扫描（Java 8192² 引擎级 GPU 扫描）：

| 每缓冲瓦片 | Java GPU 扫描 |
|---|---|
| 8 MB | 24.7 ms |
| **16 MB** | **24.1 ms（最优）** |
| 32 MB | 28.4 ms |
| 48 MB | 26.5 ms |
| 无流水线（3.7.1） | 31.7 ms |

最终取值 16 MB。注意：启用「GPU 占用率上限 < 100%」或 profiling 时自动回退到顺序路径
（避免休眠与重叠互相干扰）。

| 指标 | 3.7.1 | 3.7.2 |
|---|---|---|
| Java GPU 扫描（8192²） | 31.7 ms | **24.1 ms** |
| Java GPU 总耗时 | 71.1 ms | 62.0 ms |
| 基岩 GPU 扫描（4096²） | 16.3 ms | 15.8 ms |
| 基岩 GPU 总耗时 | 30.1 ms | 29.6 ms |

Java 侧仍慢于 CPU 12 线程（11.7 ms）——瓶颈是内核本身（0.25 ns/区块 vs 原始基准 0.10），
下一步要做「内核直接输出打包字」或「多块并行下发」。

## 九、3.7.3：Java 版打包字内核（2026-11-06）

3.7.2 之后 Java GPU 仍慢于 CPU，根因是**回读量**：每区块 1 字节 ⇒ 67M 区块要传 67 MB。
新增 scan_java_words 内核：一个 work-item 算 64 个区块、直接输出一个 ulong，回读量降到 1/8，
CPU 侧的「字节→位图」转换彻底消失，集成退化成按字 OR。

| 指标 | 3.7.2 | 3.7.3 |
|---|---|---|
| Java GPU 扫描（8192²，67M 区块） | 24.1 ms | **7.1 ms** |
| Java GPU 总耗时 | 62.0 ms | **48.7 ms** |
| Java CPU 12 线程扫描（对照） | 11.5 ms | 11.5 ms |

**Java 版 GPU 首次全面快于 CPU 多核（7.1 vs 11.5 ms，1.6×）**；基岩 16.8 ms vs CPU 52.0 ms（3.1×）。

实现要点（可移植性）：
- 内核只用 OpenCL 1.2 核心特性、纯 ulong 位运算，无扩展、无 64 位原子；
- 打包字内核创建失败时自动回退字节路径（scanRectWords 默认返回 false）；
- 瓦片必须行内 64 对齐且宽度为 64 的倍数才走字路径，否则该瓦片用字节路径（保证正确性）。
- 正确性：slime_ocl_probe 全部一致性用例 PASS、--unit [13] GPU 引擎等价 PASS、117/117 参考、GUI 自检（GPU 开）0 FAIL。

## 十、3.7.4：基岩打包字 + 位图合并 SIMD（2026-11-07）

### 10.1 基岩版打包字内核（回读量 1/8）

和 Java 一样新增 `scan_bedrock_words`（每 work-item 算 64 区块、输出一个 ulong）。
注意：3.7.3 的打包字路径只在**流水线分支**里接上，而基岩 4096² 只有 1 个瓦片 ⇒ 走的是顺序分支，
所以 3.7.3 对基岩没有任何收益。3.7.4 把顺序分支也接上打包字后才生效：

| 指标 | 3.7.3 | 3.7.4 |
|---|---|---|
| 基岩 GPU 扫描（4096²，16.7M 区块） | 16.7 ms | **9.6 ms** |
| 基岩 CPU 12 线程（对照） | ~50 ms | ~50 ms |
| 加速比 | 3.0× | **5.2×** |
| Java GPU 扫描（8192²） | 7.1 ms | **6.9 ms** |

### 10.2 位图合并改 128 位批量 OR

集成阶段从「每字读改写」改成 `_mm_or_si128` 两条一起处理：

| 指标 | 改前 | 改后 |
|---|---|---|
| 基岩逐行集成 | 0.078 ns/区块 | **0.008 ns/区块** |
| Java 逐行集成 | 0.106 ns/区块 | **0.027 ns/区块** |

### 10.3 缓存路径必须回退字节路径

打包字快路径绕过了「缓存覆盖段回读」与 collectNew 记账，实测会让「基岩+缓存覆盖」
场景的结果数翻倍（16094 vs 8062）。已加条件：`useCache || collectNew` 时强制走字节路径，
单元 [13] 的缓存等价用例恢复通过。

### 10.4 产品口径：默认关闭，但不再叫「实验性」

- 勾选框：「启用 GPU 加速（默认关闭）」；
- 设置项：「默认启用 GPU 加速（CPU 更强时建议关闭）」；
- 提示文案改为：GPU 判定稳定且与 CPU 逐位一致，但并非所有机器更快，可在设置里设为默认；
- 启用时后台实测 CPU/GPU 吞吐（现在也走打包字路径，测的就是实际路径），
  并在状态里给出**事实性**结论：「GPU 吞吐是本机 CPU 多核的 X 倍（启用更快）」或
  「只有 X 倍（建议保持关闭）」。

## 十一、新方向可行性：环形覆盖搬到 GPU（2026-11-07，仅验证不落地）

**动机**：环形规划里最贵的一步是「每个候选中心算一次环带覆盖」（CPU 实测 33 ms / 250k 中心，
约 1.6 周期/行查表）。这一步天然适合 GPU：所有中心互相独立，只需一张「每行前缀和」表。

**探针**：`tools/opt_probe20.cpp`（独立程序，用项目自带 ClApi 动态加载 OpenCL，不接产品代码）。
内核 `annulus_cov`：每个 work-item 算一个候选中心的覆盖 = Σ 行内前缀差（外环 − 内环），
sqrt 与整数修正和 CPU 完全同构，只用 OpenCL 1.2 核心特性（int / sqrt），无扩展。

**结果（2000×2000，R=128/内 24，step=4）**：

| 实现 | 中心数 | 耗时 | 每中心 | 与 CPU 不一致 |
|---|---|---|---|---|
| CPU（与内核同构的参照） | 190,969 | **230.85 ms** | 1208 ns | — |
| **GPU（含上传前缀表 + 回读）** | 190,969 | **3.25 ms** | **17.0 ns** | **0 个** |

**加速比 71×**（即使对比现在产品里已优化过的磁盘轮廓版本 —— 约 130 ns/中心 —— 仍有 **7.6×**）。
按产品现状折算：环形规划的粗扫阶段 33 ms → 预计 **4~5 ms**。

**结论**：方向成立。落地要点（下一版再做）：
1. 前端把「每行前缀和」表上传一次（2000² 的 int32 ≈ 16 MB，之后复用）；
2. 只在用户勾选 GPU 且区域中心数 ≥ 某阈值（如 5 万）时启用，否则保持 CPU 路径；
3. 结果与 CPU 逐项比对（本轮已验 19 万个中心全等），失败自动回退 CPU；
4. 与已有的「GPU 占用率上限」共用限速逻辑。

### 11.1 多配置验证（2026-11-07，仍不改产品代码）

探针 `tools/opt_probe21.cpp` 把「GPU 覆盖」与两种 CPU 参照放在同一个程序里跑，
并对每个中心逐项比对（不一致数 = 0 才有效）：

| 配置 | 中心数 | 前缀和构建 | CPU(旧，重算 sqrt) | CPU(现，预算轮廓) | GPU | 加速比 | 不一致 |
|---|---|---|---|---|---|---|---|
| 2000² step4 R128/r24 | 190,969 | 5.74 ms | 94.53 ms | 104.44 ms | **3.56 ms** | **29.3×** | 0 |
| 2000² step8 R128/r24 | 47,961 | 5.76 ms | 25.73 ms | 29.64 ms | **1.31 ms** | **22.6×** | 0 |
| 2000² step4 R128/无内环 | 190,969 | 5.74 ms | 94.46 ms | 88.56 ms | **1.06 ms** | **83.7×** | 0 |
| 1000² step4 R128/r24 | 34,969 | 1.45 ms | 17.16 ms | 18.62 ms | **0.54 ms** | **34.3×** | 0 |
| 3000² step4 R128/r24 | 471,969 | 12.94 ms | （跳过） | 262.40 ms | **2.42 ms** | **108.5×** | 0 |
| 2000² step2 R64/r16 | 877,969 | 5.72 ms | （跳过） | 224.65 ms | **42.79 ms** | 5.2× | 0 |

要点：
1. **全部配置逐中心一致（合计约 190 万个中心，0 处不同）**，说明 float sqrt 的近似被整数修正循环兜住了。
2. GPU 相对 CPU 的加速在 **5×~108×** 之间；半径大、中心少时优势最大。
3. **step2/R64 那一档只有 5.2×**：中心数翻倍而每中心行数减半 ⇒ 变成「sqrt 次数」瓶颈。
   内核里每个中心对每行都算一次 sqrt；如果把「磁盘行轮廓」预先算好上传（和产品 CPU 侧一样），
   这一档预计能快 3~5 倍。
4. **前缀和构建（5.7 ms）已经比 GPU 覆盖本身（3.6 ms）还贵**，落地时必须一并优化
   （逐行前缀可并行，或直接在 GPU 上算）。
5. 与产品实测的 CPU 环形规划对比：产品当前 250k 中心约 33 ms（约 130 ns/中心），
   GPU 3.56 ms/191k ≈ **9~10× 端到端收益**（还没算前缀和构建）。

## 十二、落地：GPU 环形覆盖（v3.7.6）

**只接管一条子路径，不替代 CPU**：

- 接入点：`AfkPlanner::planExactBlockLevel`（小范围、方块精度的精确路径）；
- 条件：勾选 GPU 且中心数 ≥ 2 万且非加权模式；否则**原 CPU 路径照旧**；
- 内核 `annulus_cov` 直接吃已建好的二维前缀和（不再额外 O(w·h) 预处理），
  结果逐项写回，CPU 端按行主序取出。

实测（`tools/opt_probe22.cpp`，直接调用产品入口 `AfkPlanner::plan`）：

| 场景 | CPU | GPU | 加速 | 候选一致 |
|---|---|---|---|---|
| 40×40 区块（精确路径，26.9k 中心） | 61.75 ms | **19.69 ms** | **3.1×** | 是 |
| 60×60 区块（精确路径，59.5k 中心） | 124.39 ms | **24.43 ms** | **5.1×** | 是 |
| 400×400 区块（区块级粗扫路径） | 7.16 ms | 5.53 ms | 1.3× | 是（未走 GPU） |

GPU 覆盖调用本身：26.9k 中心 3.03 ms、59.5k 中心 4.43 ms（含前缀表上传与回读）。

**边界说明**：大范围环形搜索走的是另一条「区块级 17×17 卷积 + 流式条带」路径
（本来就是 16× 缩小的网格卷积，CPU 已足够快），本轮**没有**把它搬到 GPU；
后续若要覆盖大范围，需要为那条路径单独设计（卷积在 GPU 上天然合适）。

## 十三、3.7.7：五个提升点的逐项冲刺（2026-11-07）

按「离理论上限还差多少」的分析，逐个动手；**五个方向都做了实验，成功 2 个、其余被实测否证**。

| # | 方向 | 结论 | 数据 |
|---|---|---|---|
| 1 | **密度匹配不再落计数数组** | ✅ 采纳 | 引擎级完整搜索（8192²，g=2/thr=0.5）：CPU 55.0→**46.3~48.8 ms**、GPU 44.6→**38.4~39.7 ms** |
| 2 | **环形覆盖前缀表常驻显存** | ✅ 采纳 | 单次调用 4.43→**3.76 ms**；40×40 区块仍是 3.2×、60×60 区块 5.3× |
| 3 | Java GPU 48 位乘法改 32 位拼装 + 行基座外提 | ❌ 无收益 | 6.8~7.2 ms 不变（说明内核不是 64 位乘法瓶颈） |
| 4 | 基岩 GPU 两条种子链交错 | ❌ 无收益 | 9.7→9.9 ms（编译器已充分流水，依赖链不是瓶颈） |
| 5 | GPU 端 `% 10` 换魔数乘法 | ❌ 无收益 | 编译器本来就会强度削减常量取模 |

### 13.1 为什么第 1 项是最大的一块

密度匹配原来会为**每个锚点**写一个 int32 计数（1 亿锚点 = 400 MB），再整段读回来做阈值判断 ——
纯内存带宽，和算力无关。改成 AVX2 直接出「命中位掩码」（每 64 个锚点 1 个 uint64，1 亿锚点只要 1.25 MB），
只遍历置位做精确判定，命中稀疏时几乎不花时间。

### 13.2 结论修正

上一轮估计的「端到端 30 ms 固定开销」实际是**密度匹配的中间数组带宽**，不是初始化开销；
现在这块已经消掉约 20%。真正的固定开销（线程池、位图分配）在 bench 口径下只有 ~1 ms。
