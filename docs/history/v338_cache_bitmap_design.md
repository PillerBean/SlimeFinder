## 1. 位图构建成本：存盘还是重建？

| 方案 | 存盘体积 | 加载耗时 | 说明 |
|---|---|---|---|
| **A 存位图**（推荐） | **229 MiB** | **≈1.2 s** | 位图按 range 存；加载即 mmap/read，无需遍历条目 |
| B 存坐标 + 加载时重建位图 | 975 MiB | 5.3 s 读 + 重建 | 重建 = 1.28e8 次「解包+置位」≈0.5~2 s（随机写 229 MiB，触发页错误） |
| C 存坐标 + 首次使用时惰性重建 | 975 MiB | 5.3 s | 每张 19 MiB 位图重建 ≈0.1 s，但查询前需判定是否已建 |

**结论：选 A**（体积 4.3× 更小、加载 4.4× 更快、查询 O(1)）。
**兼容旧缓存**：文件头 `ver` 字段（现为 1）升为 2；v2 = 「16 B 头 + 每 range（16 B 矩形 + 4 B 位图字节数 + 位图）」
并保留可选的坐标段（`entryCount` 段可为 0）。读取端同时保留 v1 解析（旧文件可继续用），
首次保存时自动升级为 v2 —— **不丢数据、不强制用户清缓存**。

## 2. 命中率 6.7% 异常：**不是漏存，也不是抽样问题**（已定论）

微基准给出两个**互相独立**的量，并且完全一致：

| 量 | 实测 | 说明 |
|---|---|---|
| 缓存条目 / 覆盖面积（12 range 面积和 1,917,633,960） | 127,842,361 / 1,917,633,960 = **6.6667%** | 由文件本身算出，与抽样无关 |
| 抽样命中点中史莱姆占比 | **6.7%**（覆盖点 70.8%） | 100 万随机点在 range 内取 |

两者相等 ⇒ 缓存里**该存的都存了**，「10% 理论值」只是与**本世界种子实际概率**不符
（本 seed 的史莱姆率为 1/15 = 6.67%，非常规整，说明是种子特性而非数据缺失）。
**排除项**：① 抽样偏差（两个独立量一致）；② 漏存（条目/面积 与 抽样率 相等）。
**仍需一句话确认**（列入实施前检查）：用 `SlimeEngine::isSlimeChunk(Bedrock, seed=0, x, z)`
对 1 万个覆盖点做真值比对，要求与缓存答案 **100% 一致** —— 这同时验证「缓存是否被不同种子污染」
（当前格式**不含 seed 字段**，跨种子混用会静默出错，建议 v2 头部写入 seed + 版本 + 算法参数，加载时校验）。

## 4. 实际 range 几何（12 个，全部同形）

```
#0..#11  minX=-104857 maxX=104857（W=209715）× 762 行（Z 各不同）
         每个 range 面积 = 159,802,830 区块；位图 = 19,507 KB（≈19.05 MiB）
覆盖 Z 范围：-104857 .. -91968（12 条不连续长条，彼此不重叠）
SUM-RANGE 面积 = 1,917,633,960（位图 229 MiB）
BBOX 面积      = 2,703,226,350（位图 322 MiB）  BBOX/SUM = 1.41
条目 / 面积    = 6.6667%
```

**位图效率测算**：
* 每 range 位图 19.05 MiB，**与引擎分块几何完全同形**（`209715×762` 正是 v3.3.7.2 在「开缓存」下的
  分块规格：`wpr=3277`、`rows=762`）⇒ **缓存位图可直接当作引擎的 `grid` 位图使用**（零转换）；
* 12 条互不重叠 ⇒ 按 range 分图无重复存储；用**单个 bbox 位图反而多花 41%**（322 vs 229 MiB）⇒ **必须按 range 分图**。

## 5. 「位图方案适用于哪种 range」——明确结论

设 `A` = 某 range 的区块面积（= W×H），则位图内存 = `A/8` 字节。判据（三条同时看）：

1. **形状判据（最重要）**：range 是**行条带**（W 固定、H 较小，与分块几何同形）⇒ **最优**，位图无空洞，
   且可直接复用为引擎 `grid`；
2. **内存判据**：Σ`A/8` ≤ **200 MB** ⇒ 全部 range 常驻位图（当前 229 MiB **略超**，需 ①降到 ≤1.6e9 覆盖面积
   或 ②对最旧 range 做 LRU 淘汰）；
3. **收益判据**：命中区占比 × (计算成本 − 位测试成本) > 位图加载/建图开销。
   以实测值代入：`0.708 × (100 − 3) ns × 点数` 远大于 1.2 s ⇒ **只要覆盖率 ≳15% 就划算**。

**不适用/需退化的情况**：① 高度碎片化的**任意矩形**（需按矩形单独建图并做 tile 对齐，否则空洞率 >50%）；
② 覆盖面积 > ~2.4e9 区块（位图 > 300 MB，收益被载入/页错误吃掉）⇒ 退回坐标集合（现状）或分片位图 + LRU；
③ 采样/分层算法（`Algorithm::Sample/Layered`）产生的「部分行已算」区域 —— **不得**用位图冒充全覆盖
（这也是 v2 头部要写算法参数与 seed 的理由）。

## 6. 当前缓存是负收益：事实陈述与转正路径

**事实陈述（全部实测）**：
1. 命中判定 523 ns/点 > 直接计算 100 ns/点（同机分块路径）⇒ **命中比不算慢 5.2×**；
2. 扫描遍历与计数**完全不受缓存影响**（`done += W` 与命中无关，`scanned` 恒为全量）⇒ 缓存省的是「计算」，
   而它自己比计算更贵 ⇒ **在已覆盖区域上，开缓存 = 纯亏**；
3. 加载 975 MiB 需 5.3 s（每次启动/导入）；
4. 体积 8 B/条 = 1.02 GB，而同样信息用位图只需 229 MiB。

**转为正收益的路径（任务 3 与 5 合流）**：
* 把「坐标集合 + 二分」改成「**按 range 的位图 + 位测试**」：判定 523 → 2~5 ns（≈100×）；
* 位图与引擎分块几何同形 ⇒ 覆盖区内**连位图填充都省掉**（直接以缓存位图当 `grid`），
  这才让「缓存命中 = 真正跳过史莱姆判定」成立（回应任务 3 验收：开/关缓存扫描计数**仍相同**，
  因为遍历必然发生；差异体现在**耗时**与「跳过判定」上 —— 我会把验收口径写成「耗时差 + 判定调用次数差」，
  并在日志里输出命中点数）；
* 体积 975 MiB → 229 MiB、加载 5.3 → 1.2 s；
* 与任务 4（缓存优先 + 命中即停）配合：位图使「先用缓存做匹配」变得廉价，
  否则任务 4 的流程在 523 ns/点下依旧无意义。
