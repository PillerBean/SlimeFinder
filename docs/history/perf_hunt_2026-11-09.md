## 阶段 4（07:00~07:15）：best 模式「复用普通内核」试验 —— 已回退（记录教训）

- 目标：让忽略阈值（最优 N 个）复用普通密度匹配内核（AVX2/多线程/分块），理论上可到普通模式水平（~136 ms）。
- 做法：TopNHeap 增加「按计数比较」模式；匹配阶段用 countMode + 有效阈值 0 + 每窗口写入 count。
- 实测：**反而更慢**（20k²：462 → 914 ms；70k²：7.5 → 26.6 s），且单元测试出现 26 项失败
  （对照发现是「有效阈值」自引用初始化 bug 引入的连锁破坏）。
- 结论：普通内核的 recordMatchAt 对**每个窗口**都计算 d2/rank/构造 Scored，阈值剪枝是它快的前提；
  countMode 必须对全部窗口入堆，单窗口成本远高于 runBestDensity 的「先计数、整块跳过」方案。
- 处理：**完整回退**到 3.10.10.2 行为（保留 byCount 占位但 countMode=false，行为与 .2 一致），
  单元 37 组、117/117、GUI 自检 0 FAIL，重新打包 3.10.10.2（新哈希）。
- 教训：覆盖全部窗口的模式不能直接借用「阈值剪枝优先」的内核；后续若要做，需为内核增加
  「只维护第 N 名计数阈值 + 仅对 cnt>=threshold 构造候选」的分支，而不是全部入堆。

## 阶段 6（08:05~08:35）：GPU 命中原子瓶颈定位与试修（未发版）

目标：8k² g5 阈值 0.3（15.36 万命中）从 106 亿/秒 提升到 ≥400 亿/秒。

实测拆分（SLIME_DEBUG）：
- 无命中（阈值 .7）：2.1 ms ⇒ **≈353 亿/秒**（判定+扫描已接近目标）；
- 常规阈值 .3：6.1~7.5 ms ⇒ **≈106 亿/秒**（差值≈4 ms 全部来自命中路径）；
- 根因：内核每个命中执行一次 **单一全局 atomic_inc(counter)**（15 万次全局原子串行化），
  加上 4M 条的 32 MB 命中缓冲分配、宿主 15 万条回读/转换。

试修 A（分条计数器 64/8/4 条）：内核命中原子从单计数器改为 N 条带各自计数器。
- 内核阶段从 ~4.3 ms 降到 **1.9~2.3 ms（≈300~350 亿/秒）**，证明原子串行化就是瓶颈；
- 但宿主需按条带分段回读（4~64 段），回读开销 +2~3 ms，端到端反而 8.4 ms（更慢）⇒ **已完整回退**；
- 结论：条带方案能救内核、救不了端到端；要达标必须让命中**连续写入**（每 workgroup 一次块预留原子 + 单次整段回读），
  并把 TopN/最近 N 的选择前移到 GPU（或按距离分带派发 + 提前停止），才能把 4 ms 命中开销压到 <1 ms。

当前状态：3.10.10.2 行为已恢复（单元 37 组、117/117、GUI 自检 0 FAIL），重新打包（zip SHA256=D6174C30…）。

## 阶段 7：3.10.11.1「结果自优化」开关（已交付）

- 开关位置：搜索页「GPU 设置 ▸」+ 设置页 GPU 区；名称「结果自优化（提前停止，默认关）」；
  说明写明适用场景：① 找最近 N 个 ② 阈值偏低/命中密集 ③ 大范围搜索 ④ 只要最近结果 ⑤ 想尽快出结果。
- 实现（只对密度 + GPU 精确匹配 + 非缓存生效）：把行带按「到起点的最小可能距离」排序逐个派发；
  每带回传后并入宿主 TopN（(d2,rank) 与 CPU 同口径），凑够目标数且下一条带最小距离 > 当前第 N 名距离（严格 >）即停止；
  先扫最近一带做探针，命中太少（阈值高/命中稀疏）则自动退回旧的全量路径，避免批次同步开销；
  返回结果数 = 保留数；不改变结果内容。

## T1 完成：GPU 流式密度匹配大改（3.10.12.1，14:29 交付）

改动前先核对的旧设计/教训：
- 块预留「存在意义」：v3.8.1 起每个命中 atomic_inc 同一全局计数器，命中密集时串行化；此前分条计数器试过（内核快了但分段回读拖垮端到端）→ 这次必须「连续整块写 + 单次连续回读」；
- keepCandidates 从 200×target 降到 max(256, 4×target)：最终 TopN 一定落在「按 (d2,rank) 最近 256 个」内（数学上安全）；
- 锚点循环旧版每锚点重算 g 行 popcount，g 越大越亏 → 改成按列滑窗（每列只算进入/离开两行）。

实现：
1) 内核命中回写：每 workgroup 局部暂存 ≤256 条（local atomic），循环末尾一次 atomic_add 预留连续区间后整块写；超过 256 条/组自动退回逐条全局原子（不丢结果）；
2) 内核锚点统计：DENS_ANCHOR_SLIDE 列滑窗（线程=列，初始 g 行求和，之后只 ±两行 popcount，无需 per-row barrier）；
3) 会话回读：只保留最近 keep 个候选（1024 桶 d2 直方图 + 连续收集 + 边界 rank 精确补齐），替代堆/nth_element；两次回读异步入队后一次 Finish；
4) 命中缓冲块预留/直方图均与引擎 (d2, rank) 口径一致（probe51 逐条对拍通过）。

## 第 4 轮：GPU 流式内核 tile 高度 64（3.10.12.5，15:34 交付）

改动前核对：
- 密度/图案两个流式内核的 tile 都是 256x32，host 侧硬编码 tileH=32；tile 间重叠 = (g-1)/tileH。
  提高 tileH 可减少重叠、减少 workgroup 派发数；但 local size 仍 256，故填充必须改成循环（每线程写多个字），
  且 host 的 tilesT/strideZ 必须同步（此前只改内核没改 host，导致结果错乱——已作为教训记录）。

实现：DENS_TILE_H/PAT_TILE_H 32→64；填充循环改为 for (wordIdx=lid; wordIdx<SHARED; wordIdx+=local_size) 的写法；
host matchDensityStream / 早停分支 / patternStream 的 tileH 同步为 64。

实测：

|---|---|---|
| 密度 8k² g5 阈值.3 GPU | 4.4~5.2 ms | **4.0 ms** |
| 密度 8k² 无命中 | 2.2 ms | **1.2 ms** |
| 密度 16k² g5 GPU | 10.4 ms | **10.1 ms** |
| 密度 20k² g8 GPU | 10.5~11.0 ms | 10.7 ms |
| 图案 2x2 20k² GPU | 9.0 ms | 7.9~9.0 ms |
| 环图案 20k² r=4 | 18 ms / 222 亿/s | **16.3 ms / 245 亿/s** |

## 失败教训（第 4 轮）：图案「64 锚点位并行」GPU 方案已回退

- 处理：完整回退标量「逐锚点 + 逐行早退」，结论写入日志（GPU 优化必须同时看指令数与并行度）。
