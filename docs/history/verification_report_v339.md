## 二、缓存架构重构（任务书 一）

### 1.1 缓存构建模式

**定位**：只做史莱姆判定 + 写缓存，**不做匹配**（唯一可写缓存的模式）。

实现要点：

- 引擎 `SearchOptions::buildMode`：走既有分块路径（内存有界、可并行），但在填充阶段结束后**直接返回**（跳过整个匹配阶段）⇒ 比同范围冷搜索省掉全部匹配开销；`validate()` 拒绝 Java 版（缓存位图语义与既有缓存一致）。
- **中断续传**：GUI 把用户范围切成若干「行段」（约 8M 字/段，单段约 20~60 秒），每段结束即 `saveFile()` 原子落盘；再次点「开始搜索」时，引擎对**已完全被缓存覆盖**的段直接跳过（`covers(tileRect)` 快速判定 + 行覆盖统计）。单元 `[25]` 实测第二次运行：新判定 8,192 区块 / 跳过 520,192 区块（首次 528,384）。
- **完成条件**：跑完整个范围，**或**达到缓存容量上限（`out.hitCacheBudget`）——构建模式**不做「边写边丢最旧」的剪枝**（那会让构建永远到不了终点）。单元 `[25]` 用 4 KB 预算实测：立即停止并如实报告，缓存体积有界（≤ 一次块级归并）。
- **构建前预估**：`预估 = 范围区块 × 1 bit`（位图口径，1/8 字节）并同时给出「旧坐标口径 10% × 8 B」；超过当前上限时弹窗提供「提高上限并继续（写入 `cache.maxSizeMB`）/ 按当前上限继续 / 取消」。
- **进度四项**（任务书指定顺序）：`已记录 N 区块(p%)，记录速度为 X 万区块/秒，已花费 S 秒`（+ 已跳过 M 区块）。进度行同时显示「缓存扫描（已覆盖区域）」或「新区域扫描」（任务 1.4）。
- **构建比搜索快**：单元 `[25]` 同范围对比（构造 17 ms / 冷搜索 17 ms，小范围匹配开销占比低）；大范围下省掉整个匹配阶段，收益随窗口数与网格增大而增大——如实说明「3~4 倍」是任务书的定位期望，实测倍数取决于匹配占比。

### 1.2 移除其他模式的写缓存逻辑

`collectCacheChunks`（分块路径）与 `collectNew`（经典路径）都只在 `buildMode` 下成立；GUI 不再把 `m_cache` 作为写句柄传给引擎、也不再做整区 `mergeRegion`。单元 `[12]` 断言「搜索前后缓存条目数与区域数完全不变 + `newCacheChunks` 为空」；GUI 自检 13.4c 同样断言。

### 1.3 缓存 + 及时反馈（v3.3.8.1 报 ✅ 但实测未生效）

**单元场景与实测的差异**：单元 `[23]` 通过是因为它**强制**了分块路径（`SLIME_FORCE_CHUNKED=1`）且缓存命中块宽度/`wpr` 与搜索完全一致；真实使用中：① 中小范围走经典路径（该路径根本没有缓存优先排序与硬停）；② 用户缓存的区域宽度与本次搜索宽度通常不同 ⇒ 旧判据（要求单个 range 同时覆盖整宽、覆盖整段 Z 且 `wpr` 相同）几乎不可能满足；③ 即使排序生效，也要**整块扫完**才检查停止标志。

**修复**：

1. 覆盖判定改为**按行覆盖率**：对每一行把缓存 range 的 X 区间排序求并集，整行被覆盖即记 1；块的全部数据行都覆盖才算「覆盖块」（不再要求同宽同 `wpr`）。
2. 路由：`opt.stopAtTarget && opt.useCache && cache != nullptr` 时也允许走分块路径（特性可达）。
3. 整区被缓存覆盖时（`cacheAllCovered`）堆一满即停；部分覆盖时在缓存覆盖块处理完后立即停。
4. 覆盖率与 `cacheFirst` 统计在 `SLIME_DEBUG`/详细日志下打印，便于事后核对。

**「缩小块粒度」的成本评估（任务书要求评估）**：块越小，停止粒度越细，但块间重叠行（每块 `hMax-1 = 4` 行）造成的重复扫描占比越高。实测（`SLIME_FORCE_CHUNKED=1` 同一自检场景）：

| 每块数据行 | 块数 | 引擎口径扫描量 | 相对默认 |
|---|---|---|---|
| 25600（默认，`SLIME_CHUNK_WORDS` 默认） | 2 | 1,600,160,000 | — |
| 419（`SLIME_CHUNK_WORDS=262144`，约 1/61） | 97 | 1,615,360,000 | **+0.95%** |

即「把块缩小 61 倍」只多扫 0.95% ⇒ 重叠行成本很低（重叠固定为 4 行/块），主要代价是块数变多带来的计划/调度开销与并行度下降。本版据此**不缩小默认块粒度**，而是把「覆盖判定放宽 + 整区覆盖时堆满即停」做对，从而让特性在真实场景可达（停止粒度 = 一个块，默认约 25,600 行；对超大范围单块约几百毫秒，用户可接受；如需更细可用 `SLIME_CHUNK_WORDS` 环境变量自行调小，代价如上表）。

**实测（单元 `[23]` ③-b，不强制分块路径）**：覆盖块 2 / 共 3、`cacheFirstStopped=1`、扫描 8,388,608 / 12,304,384 = **68.2%**（未覆盖块不再扫描）。

### 1.4 进度区分「缓存扫描」与「新扩展扫描」

引擎新增 `SearchOptions::livePhase`（每行置位：来自缓存位图 ⇒ 1，新判定 ⇒ 0）；GUI 进度行阶段文字与流水行据此显示「缓存扫描（已覆盖区域）」/「新区域扫描」，并同时显示「已跳过 M 区块（缓存已覆盖）」。

## 三、资源控制（任务书 二）

| 项 | 设置项 | 生效路径 | 验收 |
|---|---|---|---|
| 内存上限 | 设置 → 高级 →「内存上限: N MB」（0 = 自动 1.5 GB） | `AppSettings::memLimitMB` → `SearchOptions::memBudgetBytes` → 引擎 `chunkConcurrencyFor(userThreads, perChunkBytes, userBudgetBytes)`：预算 ÷ 单块位图字节数决定并发（超出即降并发；`SLIME_DEBUG` 打印实际并发） | 设置参与分块预算与实际并发计算（自检断言传参链路 + 引擎侧日志可核对） |

> 说明：CPU 上限以「线程数折算」实现（对 CPU 密集型扫描是最直接、可预测的手段）；若用户同时把线程数设得比上限更小，则取更小者（界面设置优先）。

## 七、未做 / 已知限制（如实声明）

1. **任务 6（滑窗访存优化）**：任务书 §六 明确不做（硬件受限，v3.3.8 已给出未达标实测）。
2. **缓存构建模式仅支持基岩版**：缓存位图与既有缓存文件语义一致（`validate()` 对 Java 版直接报错说明），避免 Java/基岩版判定混入同一缓存。
3. **CPU 上限为「线程数折算」**：对纯 CPU 密集型扫描可预测、可复现；GPU 扫描路径下 CPU 占用本就较低，不受影响。
4. **构建模式的「已记录」计数含块间重叠行**（与搜索的扫描计数同口径），界面百分比按去重口径截顶到 100%。
5. **托盘图标**仅在系统托盘可用时创建（`QSystemTrayIcon::isSystemTrayAvailable()`；无界面自检环境不创建），因此 GUI 自检不对其存在性做断言；exe 文件图标与窗口/任务栏图标已分别用「提取 exe 关联图标」与「qrc 资源加载」验证。
6. 单元 `[25]` 的「构建 vs 搜索」对比在小范围下差异不明显（匹配开销占比低），倍数随范围/网格增大而增大；报告中不夸大该倍数。
