# 社区效率参考（Java 环形/全图搜索）与硬件归一化对比

> 用途：实时参考。社区数据来自不同时间、不同工具、不同硬件，**必须经硬件归一化后才有一点可比性**。
> 本机基线：**Ryzen 5 5600（6C/12T，Zen3）+ RX 6750 GRE 10GB**。
> 记录版本：SlimeFinder **v3.10.11.1**（2026-11-09）｜维护：[perf_hunt_2026-11-09.md](perf_hunt_2026-11-09.md)

## 一、口径定义

**Java 全图**（世界边界 ±29,999,984 方块）：

```
单轴区块数 = 2 × floor(29,999,984 / 16) + 1 = 3,749,999
全图区块数 N = 3,749,999² = 14,062,492,500,001 ≈ 1.40625 × 10¹³ 区块
```

所有"全图时间"按此口径换算；社区工具可能使用提前停止/抽样/缓存，实际未必逐区块判定（见备注）。

## 一·补：⚠ 环形搜索口径修正（2026-11-09）

社区这份数据是**Java 环形搜索**（全图找挂机环心）的成绩；此前本文档把本工具的「密度/图案全图穷举」实测直接对照，**口径不对**。补充实测如下。

**本工具环形规划器（AfkPlanner，抽样/粗扫模式）**（Java，本机 12T，topN=5、R=128、内径 24）：

| 范围 | 用时 | 说明 |
|---|---|---|
| 2k² 区块 | 29.7 ms | 粗扫步长 4 方块 |
| 10k² 区块 | 87.0 ms | 自动抽样 625×625（步长 16） |
| 30k² 区块 | 82.2 ms | 自动抽样 625×625（步长 48） |

大范围是**抽样近似**（先 625×625 抽样粗扫，再对 48 个候选精修），给出 topN 候选、**不保证全图最优**；因此区块/秒不能与社区全图穷举折算，全图时间不可比。

**本工具环形规划器（强制逐区块精确模式）**：

| 范围 | 用时 | 等效速率 | 全图外推 |
|---|---|---|---|
| 0.5k² 区块 | 10.6 ms | 0.24 亿区块/秒 | ≈9956 分钟 |
| 1k² 区块 | 30.0 ms | 0.33 亿区块/秒 | ≈7038 分钟 |
| 2k² 区块 | 95.8 ms | 0.42 亿区块/秒 | ≈5614 分钟（≈94 小时） |

**结论**：本工具当前没有全图环形穷举能力（精确模式全图约 94 小时量级；大范围走抽样近似）。社区环形全图 CPU 117.79 亿/s（约 20 分钟）、GPU 1191.7 亿/s（约 2 分钟）对应的是**逐环心穷举 + 高效环带统计**的算法；要做同口径对比，必须先按同一规则实现全图环形穷举（例如 2D 前缀和/逐行滑窗环带覆盖 + 分块流式），届时才能把当前水平%填进第四节/第五节。在那之前，本文档第四、五节的本机数据只代表**引擎全图穷举（密度/图案）算力**，不能当作环形搜索成绩对比。

## 四、CPU 版对比（归一化）

### 4.1 归一化方法（CPU）

- 主指标：**每逻辑线程速率** = 速率 / 逻辑线程数（同代/相近 IPC 下可比）；
- 次指标：**本机等效速率** = 社区速率 × (本机多核能力 / 社区多核能力)，能力比按公开多核性能估算（标注"估算"）；
- 本机 CPU 能力基线：R5 5600 ≈ **10.5~11 千分（Cinebench R23 多核量级）**；13900K ≈ 2.0×；13980HX ≈ 1.35×；老 4 核 ≈0.4~0.5×。

### 4.2 数据

| 硬件 | 线程 | 速率 | 每线程速率 | 每条线程相对本机(4.82 亿/s/线程) | 归一化到本机估算速率 | 归一化全图时间 |
|---|---|---|---|---|---|---|
| i9-13900K | 24 | 117.79 亿/s | **4.91 亿/s** | **102%** | ~58.9 亿/s（能力比 2.0） | ~39.7 分钟 |
| i9-13980HX（笔记本） | 24 | ≥78.1 亿/s | 3.26 亿/s | 68%（移动端功耗限制） | ~57.9 亿/s（能力比 1.35） | ~40.5 分钟 |
| "i4" 老 4 核 | 4~8 | 58.6 亿/s | 7.3~14.6 亿/s | 152%~303% | 不自洽（≈130 亿/s） | — **异常，排除** |
| **本机 R5 5600** | 12 | **57.8 亿/s** | **4.82 亿/s** | 100% | — | **40.5 分钟** |

### 4.3 CPU 结论

- **每线程效率：本机与 13900K 几乎相同（102%）**，即本工具 CPU 扫描内核已达到社区 CPU 工具水平；
- 13900K 依靠 24 线程把全图压到 ~20 分钟；本机 12 线程全图约 **40.5 分钟**，与"13900K 归一化到本机 ≈39.7 分钟"一致；
- 笔记本 13980HX 的 30 分钟来自 24 线程 + 移动端功耗；归一化到本机同样约 40 分钟；
- "i4 40 分钟"若为老 4 核，其每线程速率是本机的 1.5~3 倍，与同代硬件不符 ⇒ 该数据大概率来自**不同算法/提前结束/缓存**，不参与 CPU 归一化。

**CPU 当前水平：≈社区同等 CPU 工具（约 100%）。**

## 五、GPU 版对比（归一化）

### 5.1 归一化方法（GPU）

- 主指标：**FP32 算力比**（slime 判定是整数/内存混合负载，FP32 只是粗略代理）；
- 本机 RX 6750 GRE 10GB ≈ **11.3 TFLOPS FP32**；
  - RTX 4060 Laptop ≈ 11.7 TFLOPS → 能力比 ≈ **1.04×**
  - RTX 3060 Laptop ≈ 13.0 TFLOPS → 能力比 ≈ **1.15×**
  - H100 SXM ≈ 66.9 TFLOPS → 单卡能力比 ≈ **5.9×**
- 另参考历史口径：此前将社区数据归一化到本机 GPU 为 **≈870 亿/秒**（与 3060L 归一值 886 亿/s 基本一致），本表同时列出两种口径。

### 5.3 GPU 结论

- 社区 GPU（4060L/3060L 级）全图 **2~2.6 分钟**；按 FP32 归一化到本机 ≈ **886~1146 亿/秒**；
- 本机当前产品端到端（密度流式大区域）**240~333 亿/秒**，约为社区归一化的 **24%~38%**；GPU 扫描单路口径 ≈11%，流式原型内核 ≈45%~52%；
- 差距来源已定位（见 perf_hunt 阶段 6）：命中回写/全局原子串行化、命中回读与宿主 TopN 处理；内核裸算力（≈350 亿/s）已接近社区归一化的 1/3~2/5；
- 若把"每 workgroup 块预留连续回写 + 连续回读 + GPU 侧 TopN"落地，预期端到端可到 **300~400 亿/秒**（社区归一化的 35%~45%），全图约 **6~8 分钟**；
- 命中稀疏时本工具已接近内核口径（如 8k² 阈值 0.7：≈350 亿/s），命中密集时才是主要差距。

## 六、速查公式（拿到新社区数据时用）

```
全图区块数 N = 1.40625e13

换算速率   = N / 全图秒数
每线程速率 = 速率 / 逻辑线程数
本机等效   = 社区速率 / (社区硬件多核能力 / 本机硬件多核能力)      # CPU
本机等效   = 社区速率 / (社区GPU FP32 / 本机GPU FP32)             # GPU
当前水平%  = 本机实测速率 / 本机等效速率
```

### 8.4 结论（最终）

1. **CPU：已达社区 CPU 水平**（≈100%），CPU 侧剩余空间很小。
2. **GPU 大区域：已达社区归一化的 60%~90%**（70k² 密度 722 亿/s、100k² 环图案 811 亿/s）。
3. **GPU 小区域（≤16k²）** 只有社区归一化的 15%~30%：固定开销（缓冲分配/派发/回读/宿主）占比高，是后续唯一明确的 GPU 提升方向。
4. **判定内核已达 int32 乘法吞吐上限**：每区块约 4 次 32 位乘法 ⇒ 本卡理论上限约 720 亿区块/s，实测填充 650~722 亿/s；
   4 路展开、int16 列和等尝试均无收益（已记录教训）。
5. 若社区环形工具实际是「AFK 环带覆盖穷举」而非「环状图案匹配」，则 8.2 的对比不成立，需要社区工具给出环定义才能对齐。

## 一·补2：环形搜索的「口径假设」与本机环形模式基准（2026-11-09 v3.10.12.4）

社区「Java 环形搜索」未给出明确定义。按其 CPU 117.79 亿区块/秒 ≈ 13900K 的位图判定速率推测，
它很可能不是「逐候选环形覆盖（O(R)/中心）」，而是**环状图案的位图匹配**（把环带做成 0/1 图案，用位并行 AND 全图扫描）。
本工具的模式匹配引擎可直接做这件事，于是新增 tools/opt_probe54.cpp 按「环带图案（Green=环带格，其余 Ignore）」实测：

| 场景 | CPU | GPU 图案流式（SLIME_GPU_PATTERN=1，AMD） |
|---|---|---|
| 20k² 环 r=4 厚 1 | 97.1 ms（41.2 亿/s） | 18.0 ms（**222 亿/s**，~5.4×） |
| 20k² 环 r=5 厚 1（无命中） | 91.2 ms（43.8 亿/s） | 8.8 ms（**453 亿/s**） |
| 100k² 环 r=4 厚 1 | 2263 ms（44.2 亿/s） | **127 ms（785 亿/s，~17.8×）** |

> v3.10.12.7 更新：图案 GPU 匹配改为 32 锚点位并行后，环形图案 GPU 成绩大幅提升：
> 20k² r=4 = 354 亿/s、20k² r=5 = 673 亿/s、100k² r=4 = **785 亿/s**。
> 按社区归一化 GPU（886~1146 亿/s）计，本工具环形图案 GPU 已达 **约 31%~89%**（100k² 大区域约 68%~89%）。

与社区参考（归一化到本机：CPU≈58 亿/s、GPU≈886~1146 亿/s）相比：
- **若社区=环形图案匹配：本工具 CPU 约 72~76%，GPU 约 19~51%**（环 r=5 无命中 453 亿/s 时约 40~51%）。
- 若社区实际是「逐候选 AFK 覆盖（annulus coverage）」口径，则两者不可比——需要社区工具明确
  「环的定义（半径/厚度/判定阈值）+ 是否全图穷举 + 输出什么」后才能做严格对照。

本工具的 AFK 环形规划器（AfkPlanner）仍是**采样/精确覆盖**语义（2k² 精确仅 0.40 亿区块/s），
与上述「环形图案匹配」不是同一问题；做全图 AFK 覆盖穷举需要另做流式前缀和实现（T2 剩余项）。

| **GPU 全图密度** | **717 亿/s** | **62.6%~80.9%** |
| GPU 密度 70k² | 324 亿/s | 28.3%~36.6% |
| GPU 密度 100k² | 332 亿/s | 29.0%~37.5% |
| **GPU 环形图案 100k²** | **813 亿/s** | **71.0%~91.8%** |
| GPU 环形图案 20k² | 388 亿/s | 33.9%~43.8% |
| GPU 密度 8k² | 143 亿/s | 12.5%~16.1% |

### 9.3 结论

1. CPU 纯扫描内核约到社区 CPU 的 **95%**；
2. CPU 全图产品路径约 **52%**（分块/密度匹配开销，纯扫描不是瓶颈）；
3. GPU 全图密度约 **63%~81%**（旧文档 24%~38% 已过时）；
4. GPU 环形图案 100k² 约 **71%~92%**；
5. GPU 中等范围（70k~100k²）只有 **28%~38%**，与全图差异大，是后续优化点；
6. 环形“快速全图”是**抽样近似**（约 0.1 s），与社区逐环心穷举不同口径，不能直接换算。
