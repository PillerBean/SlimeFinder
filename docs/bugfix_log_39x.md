## 四、已知遗留（未修，已记录）

1. **中等区域 GPU 反而慢**：12000² 密度全量 GPU 65 ms vs CPU 44 ms（分块路径派生；大区域 16384²+ 后 GPU 反超）。可在分块路径按块大小选择性启用。
2. **严格图案 + GPU 图案流式不响应提前停止**：仍整区跑完（结果正确，只是不早停）。
3. **全白/全灰图案**返回空结果且 `ok=true`（GUI 有校验，引擎层未报错）。
4. 位切片计数（原语 41.6×）因内存带宽与滑窗既有优势，**判定不可整合**。

## 五、3.9.8 追加发现（通宵长任务后半段）

| 版本 | 问题 | 根因 | 影响 | 验证 |
|---|---|---|---|---|
| **3.9.8** | **GPU 流式密度匹配长期静默失败并回退 CPU** | OpenCL 参数宽度错误：`bool` 按 1 字节传给内核 `int` 参数；`long` 在 Windows 为 32 位而内核 `long` 是 64 位 | GPU 匹配尝试一次（约 10~20 ms 浪费）后回退 CPU；所有 GPU 密度搜索实际都是 CPU 在跑 | 修复后 12000² 密度 43.4→7.5 ms、32768² 仅 27.4 ms；probe35/40 与 CPU 逐项一致 |
| **3.9.8** | GPU 命中总数统计错误 | 直方图回读裁剪后把裁剪条数当总数 | 密集搜索的 totalFound 偏小 | 增加 `outTotal`，回传裁剪前真实值 |
| **3.9.8** | GPU 行带早停与 CPU 有并列距离选取差异 | 行带下界在窗口中心/锚点映射上的边界处理 | 部分区域最近 N 名单不同（条数相同） | 暂时关闭行带分批（一次派发全量），结果完全一致；后续需专门处理并列 |

### 经验教训（值得记住）

1. **OpenCL 参数宽度是最隐蔽的静默错误之一**：不崩溃、不报错，只是 `matchDensity` 返回 false，引擎回退 CPU —— 而 CPU 结果永远正确，所以功能测试全绿。只有「分段计时 + 与 CPU 对比的单元测试 + 性能基线」三者组合才能发现。
2. 单元测试里 mock GPU 提供者（`MockGpuScan`）**不会**走真实 OpenCL 参数校验，所以真实驱动的参数错误测不出来 —— 需要真机探针（probe30/probe35/probe40）。
3. `scripts/perf_baseline.py` 再次证明价值：抓到了 163 ms 的严格匹配回归（100 倍）。

## 六、3.9.9 收尾：GPU 行带早停重新启用

* 问题：GPU 命中顺序由原子计数决定（每次运行不同），并列距离的 TopN 裁决不确定 —— 实测 probe40 时对时错。
* 修复：① 入堆前按 (d2, z, x) 排序，使并列裁决与 CPU 光栅顺序一致；② 停止判据加「半窗口 + 1」安全余量。
* 结果：probe40 连续 5 次 0 差异；`scripts/run_all_tests.ps1` 全套回归全绿。
* 性能（Java 32768² g=5 thr=0.5 N=8）：CPU 263 ms → GPU 27.4 ms → 早停 11.6 ms（22.6 倍）。
* 顺带测量：GPU 密度在 36M 区块以上开始明显领先（6000²：2.9 倍；8000²：4.4 倍），低于阈值仍走 CPU。
