## 一、P0-A：界面四项

### 一.1 进度行两个百分比（已复现）

**代码事实**（`src/gui/MainWindow.cpp`）：

- 第 887-891 行创建进度条：`new QProgressBar(...)`，`setRange(0,1000)`，`setMinimumWidth(160)`，**没有调用 `setTextVisible(false)`** → Qt 默认 `textVisible = true`，格式 `%p%`；
- 第 892-894 行又创建 `progressPercent` 标签（`setMinimumWidth(40)`）；
- 第 3528-3530 行把同一个 `frac` 同时写进进度条数值和该标签文本。

**本地最小复现**（`temp_progressrow.cpp`，与产品同布局参数：`进度:` + bar(stretch1) + `25%`标签(min40) + 阶段标签(stretch2)、`spacing=8`、`margins=8,2,8,2`）：

```
style           : windowsvista          （真实平台样式；用户环境为 qmodernwindowsstyle）
label  progress : x=8   w=27
bar             : x=43  w=294   textVisible=1 format='%p%'      ← 进度条自己会画百分比
label  percent  : x=345 w=40  text='25%'                        ← 我加的标签
label  stage    : x=393 w=589
渲染结果（深色簇）：43..106 蓝色填充 | 306..328 [25%] | 346..368 [25%] | 393..473 正在扫描区块…
```

- `306..328` 落在**进度条控件内**（43..337）→ 这是**进度条内置文字**（Windows 现代样式下靠右绘制，紧贴沟槽末端）；
- `346..368` 落在**我的标签内**（345..385）→ 这是 `progressPercent`。

**与用户截图逐像素一致**（`屏幕截图 2026-09-21 123437.png`，990×948）：

| 元素 | 用户截图 x 区间 | 归属 |
|---|---|---|
| 蓝色填充 | 42..106（65 px） | 进度条 25% 填充（沟槽 42..299，65/257 = 25.3% ✓） |
| 第一个 `25%` | 304..329 | 进度条内置文字 |
| 第二个 `25%` | 346..370 | `progressPercent` 标签 |
| `正在扫描区块…` | 394..464 | `progressStage` 标签 |

**根因**：同一信息被两个控件各画一次，且两个数值同源（都取 `frac`），所以永远成对出现 —— 这不是偶发渲染问题，是**必然**。

**修法（二选一，不允许两个都留）**：
1. 保留自建标签：`m_w->progress->setTextVisible(false)`（改动最小，显示位置由布局决定，最稳）；
2. 保留进度条内置文字：删除 `progressPercent` 控件及其全部 `setText` 调用（要同时改自检断言，见 §八）。

> **明确禁止**：①保留两个百分比（无论是否相同）；②只把其中一个改成不同数值/不同口径来「看起来不重复」；③用样式表把内置文字颜色设成与背景同色来「隐藏」（属于欺骗性隐藏，深色主题会露馅）。推荐方案 1。

### 一.2 「状态栏分子少 10 倍」——未复现，判定为低分辨率截图误读

**像素级测量**（对 y=928..944 行做深色列簇投影，x=100..989）：

```
[ 6]  162..164 宽 3      ← 数字 1（墨迹窄）
[ 7]  169..171 宽 3      ← 数字 1
[ 8..16] 176,183,190,197,204,211,218,225,232 宽 5（间距 7）  ← 9 位数字
[17]  238..249 宽 12     ← '/' + '4'
[18..27] 252,258,265,272,280,286,293,300,307,314（宽 4~5，间距 7）  ← 10 位数字
[28..29] 325..346 宽 10  ← 「区块」
[30..36] 356..398        ← 「（25.6%）」逐字符对齐（"（"=356..358、"2"=361..365、"5"=368..372、"."=375、"6"=378..382、"%"=386..393、"）"=397..398）
```

- 分子 = `162..236` 共 **11 位**（前导两个 `1` 被我最初的 16× 裁剪起点 174 切掉，所以肉眼只看到 `2659800`）；
- 分母 = `245..318` 共 **11 位**；
- **11,265,898,000 ÷ 43,980,318,225 = 25.62% → 屏幕显示 25.6%**：分子、分母、百分比三者自洽。

**结论**：屏幕上的分子**没有**少 10 倍。若真少 10 倍，同屏百分比必须是 `2.6%`（同一函数、同一变量、同一 `std::snprintf`/`QString::arg` 调用链产出，见 `progressStatsText`）。此条建议从缺陷单中撤销，改为下面这条**真实存在的缺陷**。

**真实缺陷：进度条百分比与状态栏百分比分母不同源**

- 进度条/百分比标签用的是**引擎自己的比例**：`frac = liveScanned / totalEvals`（`SlimeEngine.cpp` 2232-2235、2165-2166，并 `min(0.999,…)`）；
- 状态栏统计文本用的是 `m_streamScanned / m_runTotalChunks`，其中 `m_runTotalChunks = area × areaZ`（`MainWindow.cpp` 3447）；
- 而引擎的 `totalEvals = plan.totalDataEvals × W`，`plan.totalDataEvals` **含块间重叠**（每块多扫 `hMax-1` 行，`SlimeEngine.cpp` 436-477）。

用用户这次 439.8 亿的参数实算（`W=H=209715`，`gridSize=5`，Bedrock）。**注意：`collectCacheChunks`（基岩 + 启用缓存）会把分块上限压到 250 万 words**，几何因此完全不同：

| 量 | 不开缓存（16M words/块） | **开缓存（2.5M words/块，用户场景）** |
|---|---|---|
| 位图每行 words | 3277 | 3277 |
| 每块行数上限 | 4882 | **762** |
| `hMax`（密度窗口行高） | 5 | 5 |
| 每块新增锚点行 | 4878 | **758** |
| 块数 | 43 | **277** |
| 引擎总扫描量 `totalEvals` | 44,015,613,345 | **44,211,906,585** |
| GUI 分母 `area` | 43,980,318,225 | 43,980,318,225 |
| 比值（状态栏最大百分比） | 100.08% | **100.53% → 显示 100.5%** |

**与用户截图 2 的分子完全一致**：截图 2 里读出的分子正是 **44,211,906,585**（= 277×762×209,715 + 尾块），百分比 **100.5%** —— 即「超过 100%」的数值可由**缓存路径的分块几何**精确复现，误差为 0。而进度条一侧被 `min(0.999,…)` 夹在 99.9%，两者在同一时刻还会差 0.1~0.6 个百分点（用户截图 1 正是：**进度条 25% vs 状态栏 25.6%**）。

**修法**：让界面显示的分子/分母/百分比**全部取引擎同一口径**（把 `totalEvals` 或等价的 `plan` 结果通过 `SearchOutcome`/进度回调暴露给 GUI），并把「已扫描/总量」的定义在界面上说清（区块数含窗口重叠 vs 去重区域）。**禁止**为了显示 ≤100% 而对数值做截断或夹取（那会把真实的重复扫描隐藏掉）。

### 一.3 状态栏文案拼接无分隔（已复现）

**代码事实**：

- `MainWindow::setStatus(text)` = `statusBar()->showMessage(text)`（2650-2653 行）→ Qt 把该文本画在**永久控件左侧的剩余空间**里，与永久控件之间**没有分隔符**；
- 永久控件是 `progressInfo`（统计文本）与 `progressEta`（预计剩余）；
- 搜索阶段切换时（3547 行）调用 `setStatus("扫描完成，正在匹配图案…")`，而同一时刻 `progressInfo` 正显示 `扫描 11265898000/43980318225 区块（25.6%）｜速度 …｜找到 0 个`；
- 用户在截图中看到的正是：`扫描完成，正在匹配图案` **紧贴** `扫描 11265898000/…`，读起来像一句话。

**加重问题（死写）**：完成流程对同一个永久控件连续 `setText` 三次：3689（统计）→ 3701（`搜索完成（结果可在右侧按距离/密度排序）`）→ 3707（`搜索完成：共 N 条（显示 M 条）｜…`）。第 3701 行文本**立即被 3707 覆盖**，属于无效代码，且让「最终显示什么」变得不可预期。

**修法**：阶段短语**只**出现在进度行（`progressStage`）或状态栏**唯一一处**；状态栏里给消息与统计加明确分隔（例如消息统一带 `｜` 前缀或把统计放进带边框的永久控件），并删除 3701 行的死写。**禁止**继续用「临时消息 + 永久控件」拼句子来表达同一状态。

### 一.4 密度搜索显示「正在匹配图案」（已复现）

**代码事实**：

- `progressStageName(int stage)`（258-269 行）**没有模式参数**，`case 1/2` 文案写死为图案匹配：`扫描完成，正在匹配图案…` / `正在匹配图案…`；
- 阶段序号来自 `scanning` 布尔量（3537 行）：`m_w->progressStage->setText(progressStageName(scanning ? 0 : (m_stageWasMatching ? 2 : 1)))`；
- 3547 行的 `setStatus("扫描完成，正在匹配图案…")` 无条件执行；
- 自检还把这两句文案写死成断言（4823-4824 行），因此「改文案必须同时改自检」。

**为什么是错的**：密度模式下第二阶段并不是「匹配图案」，而是**对满足网格密度阈值的窗口做统计/筛选**（引擎侧 `windowsTotalFor()` 对 `Mode::Density` 走 `nAx×nAz` 密度窗口分支，`SlimeEngine.cpp` 481-506）。用户这次是 `密度搜索 grid=5 ≥0.750`，界面上却提示「匹配图案」，语义完全不符。

**修法（按模式分派，文案表）**：

| 阶段 | 严格模式（Strict） | 密度模式（Density） |
|---|---|---|
| 0 扫描 | 正在扫描区块… | 正在扫描区块… |
| 1 阶段切换 | 扫描完成，正在匹配图案… | 扫描完成，正在统计密度窗口… |
| 2 进行中 | 正在匹配图案… | 正在统计密度窗口… |
| 3 排序 | 正在排序结果… | 正在排序结果… |
| 4 完成 | 搜索完成 | 搜索完成 |

实现要点：把模式在 `startSearch()` 时捕获进 lambda（不能实时读界面控件，避免用户中途切换），`progressStageName(stage, mode)` 增加参数。**禁止**只改「正在匹配图案…」而漏掉「扫描完成，正在匹配图案…」与状态栏消息（三处必须同一口径）；**禁止**用「匹配/筛选」这类含糊词同时覆盖两种模式。

## 二、P0-B：性能回归（分块 + 缓存路径）

### 二.1 与 v3.3.6 的同机 A/B（算法内核无回归）

同机、同参数、同一 `--bench` 套件，v3.3.6（dist 包内 `slime_tests.exe`）与 v3.3.7（`build/slime_tests.exe`）各跑 2 次、并各加跑 1 次 512MB 档，全程 CPU 采样：

| 运行 | 环境 | wall | avgCPU | maxCPU |
|---|---|---|---|---|
| v3.3.6 | 默认 | 71.56 s | 10.2% | 97.2% |
| v3.3.6 | `SLIME_CHUNK_BUDGET_MB=512` | 69.12 s | 10.2% | 89.2% |
| v3.3.7 | 默认 | 74.32 s | 10.2% | 91.9% |
| v3.3.7 | `SLIME_CHUNK_BUDGET_MB=512` | 79.36 s | 9.9% | 86.1% |
| v3.3.7 | 默认（重复） | 68.45 s | 10.3% | 86.0% |

**同一二进制重复运行的最大 wall 差 = 74.32 s vs 68.45 s（8.6%）**；逐项（用例级）相对差 **均值 8.3%、最大 23.5%**。而 v3.3.6 vs v3.3.7 的逐项差异最大 29%（出现在 1.4 ms vs 1.8 ms 这种绝对量 0.4 ms 的用例上），**全部落在同一二进制自身的噪声范围内** → **结论：v3.3.7 没有让扫描/匹配内核变慢，也没有让这套（≤4 亿区块、经典路径）场景变慢。**（`avgCPU≈10%` 是因为 bench 由几十个毫秒级用例组成、用例之间有进程调度空档，此处只能看相对值。）

### 二.2 512MB 内存预算对照实验（任务书要求）——**在 4.4 亿场景下无效**

任务书要求：「用 `SLIME_CHUNK_BUDGET_MB=512` 在 4.4 亿范围做对照」。实测结果是**该设置在此规模下不产生任何影响**，原因是**路径不同**：

- 分块路径的触发条件是整区位图超过 `kClassicWordsLimit = 64,000,000 words`（512 MB 位图）；方形范围阈值约 `H > 64000`，即 **≈41 亿区块**；
- 用户报告的 4.4 亿（≈21000²）→ `words = 21000×329 ≈ 6.9M ≪ 64M` → 走**经典单图路径**，与 `SLIME_CHUNK_BUDGET_MB`（只影响分块几何/并发）**完全无关**；
- 439.8 亿（209715²）→ 走**分块路径**（43 块），预算才生效。

由于所有 bench 用例都 ≤4 亿区块（经典路径），512MB 档与默认档的逐项差异为 **-17% ~ +35%（均值 8%，绝对量多在 0.5 ms 上下）**，即完全落在噪声内 → **该设置在这类规模下确实不产生任何影响**（`temp_ab_work/bench_v337_b512.txt` vs `bench_v337_now.txt`）。
真正需要对照的是**分块路径**：v3.3.7 我自己的验收记录里，`SLIME_CHUNK_BUDGET_MB=512` 会把并发从 12 压到 4，同一分块搜索 **116 s → 284 s（2.4× 更慢）**，内存峰值 1479 MB → 499 MB。→ **512MB 只能当内存兜底，不能当提速手段**；把它当「提速开关」写进验收标准是错的。（分块路径在 4 亿级范围上的强制对照见 §二.4。）

### 二.4 强制分块路径的对照（`SLIME_FORCE_CHUNKED=1`，同一 bench 套件）

为避免「只在 439 亿才进分块」导致无法在可接受时间内做对照，用引擎内置开关 `SLIME_FORCE_CHUNKED` 在**同一套 bench（≤4 亿区块）**上强制走分块路径，三档对照：默认档 / `SLIME_CHUNK_BUDGET_MB=512` / `SLIME_CHUNK_WORDS=2097152`（更小分块 ⇒ 更多块、更多次合并）：

| 档位 | wall | avgCPU |
|---|---|---|
| 经典路径（参考） | 59.66 s | 10.6% |
| 强制分块（默认预算） | 64.70 s | 8.1% |
| 强制分块 + 512MB 预算 | 66.39 s | 8.1% |
| 强制分块 + 2M words 小分块 | 63.34 s | 8.5% |

逐用例**扫描吞吐**（万/秒）：

| 场景 | 经典 | 强制分块 | 分块+512MB | 分块+小块 |
|---|---|---|---|---|
| Java 1000×1000 单核 | 49,982 | 25,413 | 21,936 | 23,667 |
| Java 1000×1000 多核 | 82,795 | 28,176 | 28,485 | 29,129 |
| Java 10000×10000 单核 | 61,283 | 31,584 | 31,878 | 32,726 |
| Java 10000×10000 多核 | 271,360 | **31,865** | 31,973 | 31,457 |
| 基岩 2000×2000 单核 | 3,050 | 3,267 | 3,258 | 3,246 |
| 基岩 2000×2000 多核 | 13,483 | **3,288** | 3,268 | 3,262 |
| 严格 2x2全绿 2000×2000 多核 | 209,446 | **46,175** | 47,171 | 47,785 |

**两条硬结论**：
1. 分块路径的多核吞吐 ≈ 它的单核吞吐（28,176 vs 25,413；3,288 vs 3,267）⇒ 在**这些范围上它几乎没有并行**：因为 `conc = min(conc, nChunks)`，而小范围只切出 1 个块 ⇒ **退化为单线程**（详见 §六.F-4，这是新发现的隐患，不是用户这次的场景）。
2. 分块路径在相同用例上比经典路径慢 **2~8 倍**（多核用例 0.12×），512MB 预算与更小分块都改变不了这个数量级 ⇒ 分块路径的**固有成本**（每块单线程 + 大位图内存访问）是主要因素，**这解释了为什么 439 亿那类分块场景达不到经典路径的「≥3 亿/秒」期望**。

### 二.5 诚实声明：哪些已归因、哪些还没归因（v3.3.7.2 阶段补充：已基本归因）

**已用实测证据归因的**：
1. 缓存合并：每块一次 O(N) 全表重建（43 块、1.2 亿条目 ⇒ 合计 **20.6 s**，全程持锁）；
2. 缓存剪枝：每次丢弃 O(N×R)（三档规模实测线性；1.34 亿条目外推 **≈4.5 s/次丢弃**，每块调用一次 ⇒ 压线时可解释**数百秒**）；
3. 经典路径（≤4 亿）无回归（§二.1/§二.2 同机 A/B）。

**v3.3.7.2 阶段的重要修正（把「60% CPU」也算清了）**：用户是**开着缓存**跑的，此时 `collectCacheChunks` 会把分块上限压到 250 万 words ⇒ **块数 = 277（不是 43）**。于是：

- 每块一次全表重建 ⇒ 合并总量按 `块数 × 缓存规模` 增长：按实测曲线（181→718 ms/块 @ 1.2 亿条目、43 块）折算，**277 块 ≈ 130 s 级别的串行合并**（20.6 s × 277/43 ≈ 133 s），且全部**持全局互斥 `mu`**；
- 同时**每块**还会尝试一次 `pruneToFit`（277 次机会，而不是 43 次）；一旦缓存压线/超线，每次丢弃 ≈4.5 s ⇒ **数百秒**；
- 二者都发生在锁内：持锁线程在做 1GB 级内存搬运时，另外 11 个线程阻塞在同一把锁上 ⇒ **CPU 占用掉到 ~60%**，吞吐同步下降。

这与用户观测（10.7 分钟、60% CPU、6866 万/秒、缓存 1.2 亿→1.34 亿后 100× 更小的范围也慢）**在数量级上完全吻合**。
**仍需日志确认的部分**：合并/剪枝各自的精确累计耗时与锁等待时长 —— 由步骤 2 的 `chunk.merge` / `cache.prune` / `cpu.sample` 事件给出（v3.3.7.2 实施后在同机同参数下复测）。

### 二.3 真正的回归点：逐块合并 + 逐块剪枝（v3.3.7 的 P0-4 取舍）

`SlimeEngine.cpp` 2218-2225（v3.3.7 新增）：

```cpp
// v3.3.7（任务书 P0-4）：缓存改为**逐块即时归并**并立即释放该块条目，
// 峰值 = 并发数 × 单块条目（旧实现会保留最多 cacheBudget=1GB 的分块片段）。
if (collectCacheChunks && opt.cacheWrite && !opt.cache->covers(sub.region())) {
    opt.cacheWrite->mergeRegion(sub.region(), so.newCacheChunks);
    if (cacheBudget > 0) opt.cacheWrite->pruneToFit(cacheBudget);   // ← 每块都剪一次
    so.newCacheChunks.clear();
    so.newCacheChunks.shrink_to_fit();
}
```

该块代码运行在 `std::unique_lock<std::mutex> lock(mu)`（2191 行）之内，而 `mergeRegion` 是 O(N) 全表重建、`pruneToFit` 是 O(N×R)/次丢弃（见 §三）。于是：

1. 每块完成都要**独占**全局锁做一次全表重建（实测 181→718 ms，43 块合计 **20.6 s**）；
2. 缓存一旦达到预算，**每块**都要跑一次 `pruneToFit`（实测一次丢 41 个 range 要 **28.5 s**，20.2M 条目；用户的缓存是 1.2~1.34 亿条目，量级再 ×6.6）→ 单块可能阻塞几十秒；
3. 期间其余 11 个线程要么在等锁、要么在同一个内存带宽上争抢 → **CPU 占用从 ~95% 掉到 ~60%**，吞吐同步下降。

而 v3.3.6 的做法是「搜索期间只收集，搜索结束后一次性合并」——慢点只在收尾，不阻塞扫描，所以用户感到 v3.3.7「搜索阶段变慢」。**代价换来的是内存峰值可控（1479 MB → 预算内）**，属于取舍而非纯 bug。

**修法方向**（不实施，等确认）：
- 合并/剪枝**摊还**：每 k 块（或每累积 X MB）做一次，而不是每块；
- 剪枝**高水位**：达到预算才剪，且剪到 80% 预算，避免「刚好超一点 → 每块都剪」；
- 合并**移出临界区**：各块结果先入无锁队列，由单独线程串行合并；或按 region 分片（每分片一把锁，分片内合并）；
- 保留 P0-4 的峰值收益（这是它唯一的正当目标），但不要把它放在扫描热路径上。

## 三、P0-C：缓存越大越慢（量化）

### 三.1 `mergeRegion` = O(N+k) 全表重建

`src/core/CacheManager.cpp` 60-86：

```cpp
std::vector<uint64_t> merged;
merged.reserve(m_entries.size() + add.size());
std::sort(add.begin(), add.end());
add.erase(std::unique(add.begin(), add.end()), add.end());
std::merge(m_entries.begin(), m_entries.end(), add.begin(), add.end(), std::back_inserter(merged));
merged.erase(std::unique(merged.begin(), merged.end()), merged.end());
m_entries.swap(merged);          // ← 每次调用都重建整表 + 两遍去重
```

**实测曲线**（`temp_cache_bench`，`W=209715`、每块 4,881 行、每块新增 2.8M 条目 —— 与用户 439.8 亿那一跑的 43 块几何一致）：

| 块号 | 累计条目 | 单块 `mergeRegion` 耗时 |
|---|---|---|
| 1 | 2,796,302 | 181.4 ms |
| 10 | 27,962,105 | 311.0 ms |
| 20 | 55,923,792 | 464.3 ms |
| 30 | 83,885,734 | 542.7 ms |
| 40 | 111,847,381 | 757.3 ms |
| 43 | 120,235,913 | 718.3 ms |
| **合计** | 120.4M | **20,611 ms ≈ 20.6 s** |

线性增长（首块:末块 ≈ 1:4，条目数比 ≈ 1:43 的平方根量级符合 O(N) 累加），**全部在全局锁内**。

### 三.2 `pruneToFit` = O(N×R) **每一次丢弃**

`CacheManager.cpp` 200-219：

```cpp
while (!m_ranges.empty() && sizeBytes() > maxBytes) {
    m_ranges.erase(m_ranges.begin());
    std::vector<uint64_t> kept;
    kept.reserve(m_entries.size());
    for (uint64_t e : m_entries) {          // ← 每个被丢弃的 range 都重扫整表
        const int x = unpackX(e), z = unpackZ(e);
        bool covered = false;
        for (const Rect& r : m_ranges) { if (r.contains(x, z)) { covered = true; break; } }
        if (covered) kept.push_back(e);
    }
    m_entries.swap(kept);
}
```

**实测**（`temp_cache_bench prune …`，每次固定丢弃 41 个 range：101 → 60；同一程序、同一数据源）：

| 缓存条目 | 缓存字节 | 丢弃 41 个 range 总耗时 | **每次丢弃** |
|---|---|---|---|
| 5,049,872 | 40.4 MB | 6,426.6 ms | **156.7 ms** |
| 20,198,018 | 161.6 MB | 27,293 / 28,466 / 28,766 / 29,235 ms（4 次） | **666 ~ 713 ms** |
| 40,392,049 | 323.1 MB | 55,749.9 ms | **1,359.8 ms** |

条目 ×4 ⇒ 每次丢弃 ×4.3；条目 ×8 ⇒ ×8.7 → **确认线性于 N**（range 数固定时），即 **O(N×R)**，与代码内层「每个条目线性扫 range 列表」一致；`pruneToFit` 幂等（预算内再次调用 0.0 ms）。

外推到用户的实际缓存（1.34 亿条目，约为上表 20.2M 档的 6.6 倍）：

- **每次丢弃一个 range ≈ 4.4 ~ 4.7 s**（range 越多越慢，内层与 R 成正比）；
- 一次 `pruneToFit` 若丢 k 个 range ⇒ **≈ 4.5×k 秒**；
- 而它被**每块**调用一次（§二.3）⇒ 43 块 × 每次丢 1~3 个 range ≈ **190 ~ 580 s**，与用户「439.8 亿跑了 10.7 分钟、CPU 只有 60%」以及「缓存涨到 1.34 亿（≈1022 MiB，正好压在默认 1024 MiB 预算线上）后，100× 更小的范围也变慢」的现象吻合。
- 注意区分：**预算之内**时 `pruneToFit` 的第一句 `while (sizeBytes() > maxBytes)` 不成立 → 立即返回（实测 0.0 ms），所以只有在缓存**压线/超线**时才会出现上述爆炸性开销。

**修法方向**（不实施）：
- 维护 **range→条目** 的反向索引（或按 range 分桶存储），丢弃 range 时只处理该桶条目 ⇒ O(k log N)；
- 或剪枝改为「按 range 逐出 + 位图标记」的增量结构，避免整表重建；
- `mergeRegion` 改为**增量插入**（有序向量 + 批量插入到新向量，仅当增长超过阈值才整理），而不是每次全表重建；
- 预算策略改为「高水位 + 一次剪到低水位」，避免临界区反复剪。

### F-4 分块路径的「1 块 ⇒ 单线程」隐患（本次新发现）
- 分块路径的并发度是 `min(conc, nChunks)`（`SlimeEngine.cpp` 2250），而块内固定 `sub.threads = 1`（2146 行）；
- 只要几何落在「**行数 ≤ dataRowsCap（默认 4881 行）但整图 words > 64,000,000**」，就会被判定走分块路径、却**只切出 1 个块** ⇒ **整个搜索只跑 1 个线程**（用户界面上的线程数设置完全失效，也没有任何提示）；

- 实测证据：§二.4 的强制分块多核用例吞吐 ≈ 单核用例吞吐（3,288 vs 3,267 万/秒）；
- 建议（属 P1，需与 P0 修复分开）：进入分块路径时若 `nChunks < 2` 或 `nChunks < 核数`，应回退经典路径或按列再切分，并在状态栏/日志明确告知实际并发。
