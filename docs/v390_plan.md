# v3.9.0 方案：早停验证 + 两级筛选 + 准确性产品化

> 背景：单机算法/结构/硬件三条线都接近边界（详见 process_optimization_plan.md）。
> 本方案不再追求单机吞吐，而是「**减少要算的区块数**」与「**让用户更快拿到可信结果**」。
>
> 用户已明确：
> * 目标数量自适应搜索**不做**（结果数由用户决定）；
> * 多机/多 GPU **不做**；预计算等价于已有缓存构建；缓存共享已支持；能效暂不做。
>
> 因此本方案只保留三件事：**A 早停/最近优先的验证与修复**、**B 两级筛选（采样→精确）**、**C 准确性产品化**。

---

## A. 先验证：早停与「最近优先」到底有没有生效（P0）

### A1. 现状（代码层）
* `SearchOptions::stopAtTarget`：达到 `targetCount` 后提前停止；
  * 分块路径：按块检查，块内还有「堆满 + 本块剩余不可能更近」的停止条件；
  * **GPU 流式路径（密度/图案）目前完全没有早停**：整区一次跑完再排序；
  * `smartRange`（由中心向外）与 `slideOk` 互斥，且**与 GPU 流式路径互斥**（开了 smartRange 就走 CPU 位图路径）。
* GUI 有「找到目标数量后停止」与「智能范围」两个选项，但**没有量化验证过它们是否真的减少了工作量**。

### A2. 验证项（可自动化，写成 `tests/verify_earlystop.py` 或 bench 子项）
| 编号 | 验证内容 | 判定标准 |
|---|---|---|
| V1 | `stopAtTarget=on` 时，实测扫描区块数 < 全量 | 扫描数应随 targetCount 增大而增大，且小于全量 |
| V2 | 早停结果 == 不早停的前 N 名 | 逐项一致（距离、密度、坐标） |
| V3 | `smartRange=on` 时，扫描区块数明显减少 | 实测扫描数/总区块数 < 1 |
| V4 | `smartRange` 与早停组合 | 结果一致，且扫描数进一步下降 |
| V5 | GPU 路径下开关的**实际行为** | 明确「被静默回退到 CPU」还是「不支持」——必须让用户可见 |

### A3. 预期问题（已从代码推断，待实测确认）
1. **GPU 路径吃掉早停**：用户开早停 + 开 GPU，实际走 CPU（因为 GPU 流式不支持），表现为「开了更快却更慢」；
2. **smartRange 与 GPU 互斥**：同上；
3. 若 V1/V3 不达标，说明早停确实没生效，需要修（这也是用户怀疑的点）。

### A4. 修复方向（视验证结果）
* 让 GPU 流式内核支持**环带派发**（先内圈后外圈），配合早停；
* 或在 GPU 路径下检测到 `stopAtTarget/smartRange` 时，**明确提示**并回退 CPU（当前是静默回退，需改成可见）。

## B. 两级筛选：采样 → 精确验证（P1）

### B1. 安全版（默认启用，结果与全量扫描逐项一致）
* **采样只用于排序，不用于排除**：把区域切成桶（如 64×64 区块），按采样步长 S 估算每桶得分，**按得分从高到低**依次精确扫描；
* 与早停配合：凑够 N 个即停；
* 因为最终仍会精确扫描（只是顺序不同），**结果不会漏**，与现有 117 项参考可直接对拍；
* 收益来源：真实用法（找最近几个）里，高分桶集中，早停前只扫了很小一部分面积。

### B2. 概率版（可选，默认关闭）
* 只精确验证前 K 个高分桶（K 由用户/自动决定），其余桶跳过；
* 必须向用户显示**可计算的漏检概率上界**（例如「本次跳过 12% 面积，漏检概率 < 0.3%」）；
* 漏检概率用超几何分布/二项尾概率给出，而不是拍脑袋；
* 只在这种模式下允许「结果可能不完整」的语义，并在结果区标注。

### B3. 验证方案
* B1：对 bench 全部参数组合 A/B，要求结果逐项一致，仅扫描区块数下降；
* B2：蒙特卡洛（同参数跑 1000 次不同种子），实测漏检率与理论值对比，误差不超过 2 倍；
* 边界：小区域、极端阈值（0/1）、严格图案 + 旋转变体下都要跑。

## C. 准确性产品化（P2）

1. **成功率预测扩展**：现有公式已给出「找到至少一个的概率」，补充「**预计扫描量/耗时**」与「**建议扩大/缩小范围**」；
2. **早停/采样语义提示**：结果区明确标注「已找到全部 / 已提前停止 / 跳过了 x% 面积（漏检概率 < y%）」；
3. **基岩缓存覆盖提示**：已有缓存标签，补充「本次有多少区块来自缓存、多少是现算」；
4. **搜索前体检**：参数不合理（如图案约束过多导致期望命中 < 1）时直接提示，而不是让用户等很久得到一个空结果。

## 附：A 阶段实测结果（2026-11-07，`tools/opt_probe32.cpp`）

区域 8192²（6710 万区块），密度 g=5 thr=0.5，target=8，12 线程：

| 配置 | Java 耗时 | 扫描区块 | Java 结果 vs 全量 | 基岩耗时 | 基岩结果 |
|---|---|---|---|---|---|
| 全量（无早停） | **23.91 ms** | 100% | — | 206.7 ms | — |
| 早停 stopAtTarget | 167.79 ms | **100%** | **不一致** | 440.3 ms | 一致 |
| 智能范围 smartRange | 183.83 ms | **100%** | 一致 | 402.1 ms | 一致 |
| 早停 + 智能范围 | 661.59 ms | **100%** | **不一致** | 1019.4 ms | 一致 |

### 三个意外结论（与预期不同，必须修正方案）

1. **「找够就停」省不到扫描时间**：引擎的早停发生在**匹配阶段**，扫描阶段仍要生成整幅位图（100%）。
   所以用户感知不到「更快」——真正该做的是让**扫描阶段也支持早停**（环带扫描 + 扫到 N 个即停）。
2. **早停/智能范围反而慢 3~7 倍**：因为它们会让引擎禁用 GPU 流式路径与 SIMD 快路径
   （条件 `!opt.smartRange && !opt.stopAtTarget`），退化成慢路径。这是**负优化**，比不支持更糟。
3. **Java 早停结果与全量前 8 名不一致**：说明「块内停止条件」在 Java 路径下不安全，
   属于**正确性问题**（基岩一致，Java 不一致）。

### 据此修正 A 阶段优先项

| 编号 | 事项 | 性质 |
|---|---|---|
| A-1 | 早停时不要禁用 GPU 流式/SIMD 快路径；若确实不支持，至少不要让它变慢 | 负优化修复 |
| A-2 | 修 Java 早停结果与全量不一致（正确性） | bug |
| A-3 | 让扫描阶段支持早停（需要环带扫描，与 B1 共用基础设施） | 新功能 |
| A-4 | 「GPU 流式被跳过」提示（已完成，v3.9.0） | 可见性 |

B（两级筛选）与 C（准确性产品化）保持不变，但 B1 的环带扫描基础设施与 A-3 相同，可合并实现。

### 更正（v3.9.1）

* 「Java 早停结果与全量不一致」**是验证脚本的误报**：早停的 `totalFound` 天生更少
  （停止后不再计数），只应比较**前 N 名**。改为只比前 N 名后：Java 早停结果与全量**完全一致**。
* 「早停慢 3~7 倍」已部分修复：早停此前把滑窗快路径一并禁用；放开后
  **Java 早停 167.8 → 59.6 ms（2.8×）**，结果仍与全量前 N 名一致。
* 剩余的「早停仍比全量慢」是因为早停走单线程行序路径（并行分块路径不支持提前停止）；
  真正让早停省时间的做法仍是 **A-3 环带有序扫描**（与 B1 共用基础设施）。

## A-3 / B1 设计依据（2026-11-07 补充测量）

`tools/opt_probe32.cpp` 的扫描/匹配分段计时（Java 8192²，密度 g=5 thr=0.5，target=8）：

| 配置 | 总耗时 | 扫描段 | **匹配段** | 结果 vs 全量前 N 名 |
|---|---|---|---|---|
| 全量（无早停，并行+滑窗） | 21.8 ms | 10.4 ms | **11.4 ms** | — |
| 早停（raster，单线程滑窗） | 53.0 ms | 10.4 ms | **52.6 ms** | 一致 |
| 智能范围（单线程逐行） | 186.4 ms | 10.7 ms | **186.2 ms** | 一致 |
| 早停 + 智能范围 | 675.1 ms | 11.4 ms | **674.8 ms** | 一致 |

### 两个关键结论

1. **扫描段恒定 ~10 ms，早停省不到它**（整图位图必须先建好）——
   所以「找够就停」要真省时间，必须让**扫描阶段也按距离顺序进行并提前停止**。
2. **智能范围路径的匹配段慢 13 倍**（186 vs 11.4 ms）——因为它禁用了滑窗与并行，
   退化成逐行标量判定。这是当前「开了更慢」的根因。

### 环形扫描的实际潜力（同一次测量）

* 第 8 名结果距起点 **3194 区块** ⇒ 环形扫描只需 **47.8% 的面积**。
* 注意：这个用例是**极稀疏命中**（67M 区块只有 17 个命中），所以收益只有 2 倍；
  真实用法（阈值更宽松、命中更多）时第 N 名近得多，收益会显著更大。

### 下一步实现（A-3 + B1 合并）

**带序扫描（band-ordered scan）**：把行切成高度固定的小带（如 64 行），
按「带到起点的距离」由近到远排序；每条带内部保持连续行 ⇒ **可以继续用滑窗快路径**；
每扫完一条带检查一次「第 N 名距离 ≤ 剩余带最近距离」→ 停止。

* 保留滑窗 12 倍的单核优势；
* 早停粒度从「行」变成「带」，仍有足够收敛性；
* 与 B1（采样给带排序加权）共用同一套带结构；
* 正确性：带内滑窗结果与全量逐位一致，只是顺序不同 + 可提前停，117 项参考可对拍。

### A-3 第一次尝试：行带排序 + 启用滑窗路径 —— 否证（已回退）

做法：把智能范围的行顺序从「逐行按距离排序」改成「按 64 行带排序」，并允许智能范围走滑窗快路径。

结果：
* **速度确实快了 9 倍**：智能范围 182.7 → **21.3 ms**（滑窗路径生效）；
* **但结果错了**：命中数 17 → **61213**（大量假阳性）。
  ⇒ 说明滑窗路径对「azRows 非全局升序」有隐含假设（不只影响垂直和初始化），
  盲目放开会算错，已**全部回退**，产品保持 3.9.1 的正确行为。

### 结论与后续

* 「智能范围慢 13 倍」的根因已确认：走逐行标量路径；
* 想修它必须**重构滑窗路径**，使其显式支持「分块有序」的行序列（每块独立初始化、
  块内连续、块间可跳），而不是简单的排序后重用；
* 这是一次真正的重构（影响滑窗、早停、并行三处），需要独立一轮做，且必须用
  「智能范围结果 == 全量前 N 名」的逐项对拍来验收（本轮已证明这条验收线能抓到问题）。

### 本轮净收益

* 结论明确：9 倍收益真实存在，但需要正确重构，不能靠排序+放行；
* 验证脚本 `opt_probe32.cpp` 现在能同时看「扫描/匹配分段」和「结果一致性」，
  可直接用于该重构的验收。
